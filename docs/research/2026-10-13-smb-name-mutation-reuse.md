# SMB name mutation: existing mechanism reuse

Research date: 2026-10-13. Source baseline: `1aeef7b50d20c0bcc81764106c59775cd2e9ddc9`.

This report records source and protocol evidence for SMB task 8.1. It is frozen research, not a description of shipped support. Inspection used the named repository revision and primary Microsoft protocol pages fetched on the research date. No implementation, runtime probe or native Windows qualification was performed for this report.

## Questions

Which parts of rename, move, replacement, ordinary delete disposition, current-name observation and FILE_SUPERSEDE are already implemented? Which missing guarantees require changes to existing neutral contracts? What must remain at the SMB edge so FUSE, HTTP and SDK operations retain their current object and authorization semantics?

The project requirements are [R-FS-6/8/9 and R-WIN-2/4/5/6/7 at the inspected revision](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/docs/spec/requirements.md#L30). They require immutable open-reference identity, complete unambiguous Windows names, atomic effects, original-action recovery, neutral remote contracts and separate ordinary disposition versus accepted close-delete obligations.

## Existing namespace mutation

1. [NamespaceAccess](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/capabilities.go#L21) already exposes `MutateName`. [NameCommand](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/capabilities.go#L497-L505) carries source identity conditions, destination conditions, action identity and exact reference uses. No separate guarded mutation entry is needed to carry more conditions.
2. [RenameTarget](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/capabilities.go#L387) already separates the observed destination raw leaf from the output leaf. [prepareNamespaceRename](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/namespace_mutations.go#L154) rejects an unobserved third output occupant, validates sharing, checks directory cycles and handles displaced objects.
3. [MutateName's final transaction](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/namespace_mutations.go#L236) calls preparation before and during the effect transaction. Extending preparation with guard validation reaches the actual effect point; preflight validation alone does not.
4. [The HTTP client](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/transport/httprest/file_capability_client.go#L230) already has `MutateNameWithBarrier`; [the HTTP DTO](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/transport/httprest/file_capability_wire.go#L286) and [server dispatch](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/transport/httprest/file_capability_server.go#L420) use the same operation. A second RPC would duplicate request validation, action recovery and barrier ownership.
5. [Existing namespace events](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/namespace_mutations.go#L367) already record old and new locations for rename. The source and destination relationship need not be reconstructed from two unrelated events.

The missing namespace condition is complete ancestry at the final effect. Source/target `ChildCondition.ExpectedMetadata` already carries the opaque Windows-property version; the missing field is one optional rooted `NamespaceGuards` union on NameCommand.

## Guards and authoritative observations

[NamespaceGuards](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/capabilities.go#L364) holds directory revisions, exact child edges and a root. [Its validation](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/capability_validation.go#L77-L152) supports a rooted acyclic graph, rejects duplicate directory/child/slot identities and limits the whole representation to 256 directories, 256 edges and 64 KiB.

[SQLite's checkNamespaceGuards](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/namespace_guards.go#L32) compares every directory revision and exact edge in the same transaction as its caller. RootID is structurally meaningful but must be tied to the actual volume root at an effect entry; accepting an arbitrary caller root would only prove membership in a caller-selected subtree.

The graph can carry two branches with a common prefix. Two separate source/destination fields would duplicate the prefix and require another consistency rule between versions. A single union uses the existing limits once. It still needs command-specific coverage validation: the actual source/target parents and present terminal leaves must be covered, without unrelated branches or omitted ancestors.

[resolveCreateName](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/namespace.go#L59) already performs complete bounded directory observation and Windows-name projection, retains present terminal child edges and generates `SameNode` or `Absent` conditions. It is reusable for rename's destination.

[ReferenceNameObserver](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/name_observation.go#L49) already observes an immutable retained NodeID's current parent and raw leaf with optional guards. It grants no metadata, listing or mutation permission. [DirectoryMetadataObserver's IncludeName option](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/directory_metadata.go#L9-L29) supplies the parent directory's own current association together with a complete capture.

These two existing observations can construct the source path upward from the retained reference. Each directory must be fully projected for invalid or ambiguous Windows siblings before selecting the exact descendant NodeID/raw leaf. The assembled source graph must be checked through a final reference ObserveName(sourceGuards), with equality of the captured binding, before any helper returns a pure normalized-name query or SET metadata capture. Without that check, captures from different moments can stitch a path that never existed. Rename additionally validates the merged source/destination union through ObserveName and its final effect transaction. The remaining helper is SMB-local graph assembly, not a remote path API or retained ancestor-reference chain.

[The existing list budget callback](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/namespace.go#L251) has a forward-traversal cycle assumption: it rejects entries matching previously traversed directories. During upward traversal a parent legitimately contains the descendant directory already visited. Reuse the byte-accounting part while giving upward traversal its own ancestry identity cycle check.

Both [objectstore canonicalization](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/objectstore/file_actions.go#L182) and [HTTP canonicalization](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/transport/httprest/file_capability_wire.go#L102) already clone and sort ChildSelection guards. Extracting a private guard helper within each current encoding layer lets NameCommand reuse the same canonical behavior.

## Ordinary pending disposition and close-delete

[SetPendingUnlink](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/pending_unlink.go#L361) already checks the retained object's live deletion use, ExpectedMetadata, attached state, exactly one current association and the file/directory unlink condition inside its write transaction. Ordinary SET therefore does not need a new Selection or ancestry-guard field: it changes the original referenced object's current disposition rather than selecting an object by an old path.

[ClearPendingUnlink](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/pending_unlink.go#L411) already uses a generation CAS and changes only the node's ordinary pending bit. At this baseline it rejects ordinary-false states and [command validation rejects an empty token](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/capability_validation.go#L316). A valid FALSE when no ordinary disposition exists requires a defined authorized no-op; it cannot be answered solely by host-local observation. The existing [planned-transaction no-effect branch](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/sqlite.go#L818) can return bounded state with publication checks without emitting events, changing time or invoking effect publication. Empty Generation is an explicit expected-not-pending CAS, while the HTTP field remains mandatory and canonical.

[Full ReferenceState](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/pending_unlink.go#L31) already has PendingGeneration. [StateScalars](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/pending_unlink.go#L61) already captures aggregate pending but omits the token. Exposing the existing bounded token in that projection permits a DELETE-only reference to coordinate clearing without granting access to metadata, times or link payloads. This applies to State(StateScalars), not to mutation results: existing SetPendingUnlink/ClearPendingUnlink call returnedReferenceState and retain their FULL result, metadata/link budgets and action receipts. A broad mutation-result projection or privacy change is outside task 8.1; existing full-result limits may still fail a mutation.

[activateExplicitPendingUnlink](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/pending_unlink.go#L338-L359) currently uses aggregate nodePendingUnlink to decide whether to increment. If DOC keeps aggregate pending true, ordinary clear/set can reuse the same token, allowing an old CLEAR token to clear a later ordinary episode. This is an ABA gap in the inspected baseline, not an already-correct ordinary episode implementation.

The shared counter also advances on [DOC trigger](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/pending_unlink.go#L668-L677) and [startup classification](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/pending_unlink.go#L930-L940) when aggregate pending changes false-to-true. Inference for the design: preserve those increments and change ordinary activation to inspect ordinary pending_unlink itself. Ordinary false-to-true increments even under DOC; repeated ordinary TRUE and CLEAR add no increments. No independent counter or schema is required.

[checkPendingNameTarget](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/namespace_mutations.go#L24) currently permits a pending target if a DeleteName use token is supplied. Project R-WIN-7 requires conflicting new name operations to fail after pending. The accepted close-delete cleanup uses its own trigger/discard path, so it does not require MutateName to retain this exception.

[Objectstore pending operations](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/objectstore/capabilities.go#L369) already pass through runFileAction. Keeping the same RPC/action path for CLEAR no-op preserves current backend authorization, immutable retry payload and original-result recovery.

Protocol evidence:

- [MS-FSA FileDispositionInformation](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/386d9ec5-e0f6-4853-b175-c05be01419e0) requires DELETE for set and clear. TRUE rejects READONLY and nonempty directories; FALSE does not perform those two checks.
- [MS-FSCC disposition layout](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/12c3dd1c-14f6-4229-9d29-75fb2cb392f6) is a one-byte Boolean, not an extended flag set. FSA requires INFO_LENGTH_MISMATCH for zero bytes; at least one byte reads the first Boolean and ignores surplus bytes.
- [WDK disposition documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information) states that clearing ordinary disposition does not cancel FILE_FLAG_DELETE_ON_CLOSE. The existing separate CloseIntent ledger expresses that distinction.

## Supersede and the existing reset effect

[ExistingEffect and InitialState](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/capabilities.go#L399) already distinguish Keep, ResetContent and ReplaceNode, with OnReset and Reset outcome. [applyAtomicOpen](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/atomic_open.go#L231-L251) applies ResetContent and initial fields to the existing object and records its change in one transaction. ReplaceNode instead unlinks/discards the old object and inserts a new object.

[OpenAtOptions validation](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/storage/capability_validation.go#L180) currently requires Write for ResetContent. [atomicOpenVolumeIntent](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/atomic_open.go#L176) uses WriteMutation, and [publication](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/publication.go#L260) validates content publication. This is the concrete contract gap for supersede: the fixed reset effect needs DELETE access while the resulting reference may have no data-write access. The effect and data grant must remain separate. DeleteName ResetUse belongs only to existing-object SameNode/Create=false; an absent target uses Keep/Create=true and no reset-use or removal authorization.

[SMB CREATE routing](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/commands_file.go#L350) currently routes metadata-only opens through NodeReferences. An existing-object metadata-only supersede still has a content-reset effect and must use AtomicFileOpener without granting false data permissions. Its effective access adds DELETE/WRITE_ATTRIBUTES/WRITE_EA through existing normalization while preserving original data rights. An absent-object branch retains ordinary incoming create rights: with data rights it uses AtomicFileOpener Keep/Create/TargetAbsent; without data rights it can use the existing regular OpenChildRef Create/TargetAbsent path. Both branches are frozen by the observed condition; switching branches requires a new action only after the original is proved NotExecuted.

[HTTP open authorization](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/transport/httprest/file_authorization.go#L28) already exposes actual OpenAccess.Write, effect Truncate and initial attribute/metadata operations. DeleteName reset can add the existing removal authorization while retaining actual data access, quota, strong-lock and publication checks.

Protocol evidence:

- [MS-FSA existing-file create](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/41f3734a-5bba-4c3b-9d04-7baafc9b7bfe) modifies the existing File/Stream for FILE_SUPERSEDE and reports FILE_SUPERSEDED. It requires DELETE instead of FILE_WRITE_DATA, plus the unnamed-stream metadata rights; requested attributes must include existing HIDDEN/SYSTEM.
- [MS-FSA existing-access checks](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/82b364ce-6d7b-422f-8d88-4db32eea809a) test READONLY against explicit requested data-write/append access and DOC. They do not justify a blanket READONLY rejection for DELETE-only supersede.
- [MS-FSA existing sharing](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/8c0e3f4f-0729-49f4-a14d-7f7add593819) uses the granted access/share relationship. Adding fake WriteData would reject otherwise compatible delete-share references.
- [MS-FSA modification-time guidance](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/75cdaba1-4401-4c53-b09c-69ba6cd50ce6) and [NtCreateFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile) describe update behavior. Project R-WIN-5 independently preserves access time unless explicitly set and requires ARCHIVE/content/last-write/change in the same effect.

Inference from the source and project contract: an explicit neutral ResetUse field expresses the missing effect-use choice. New SupersedeFile/OnSupersede/Outcome values would duplicate already-correct reset mechanisms. Actual data permissions remain unchanged, and native Reset becomes FILE_SUPERSEDED only for the supersede CREATE disposition at the SMB edge.

## SMB admission, codecs and result ownership

[Existing file-information admission](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/commands_file_info.go#L18) verifies the authenticated FileId, required rights, FIFO ticket, pending effects and authority identity. [The wire file-info module](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/internal/wire/file_info.go#L31) already parses QUERY_INFO and SET_INFO headers and bounded input fields. Extending it is preferable to creating a parallel SET_INFO codec/router.

[mutationOwner](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/mutation_owner.go#L18) already holds action/payload, result capture, retry limits, settlement and retirement state. [Its reconciliation](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/mutation_owner.go#L404) and [pending-file integration](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/mutation_owner.go#L506) preserve responsibility through FIFO and close. Supporting a private typed command union can reuse these transitions, resource reservations and public diagnostics instead of adding a new name-mutation registry.

[writeLedger reservation](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/write_diagnostics.go#L85-L165) records fixed initial payloadBytes and enforces server/export limits. The existing metadata retry in mutationOwner can replace its command without a new byte charge; variable ancestry makes that behavior insufficient. Inference: add a private atomic charge-adjustment operation on this same ledger, reserve the old-plus-fresh owned-payload peak before cloning/installing/dispatching a larger retry, then reduce to the new charge after release. Refusal must preserve the original NotExecuted diagnostic and perform no new dispatch. The observation builder can reuse [bounded directory capture staging and entry accounting](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/directory_snapshot.go#L91-L134); that charge remains distinct while the staged capture and old owner payload coexist.

The union must validate concrete result contracts before common Attr signatures. Name removal may legally return no Attr; pending operations return ReferenceState; neither can be treated as FileMutation by ignoring result fields. Unknown must retain the original command and action even when the native reference is released but an outer barrier remains unsettled.

Protocol evidence for rename:

- [MS-FSCC FileRenameInformation TYPE_2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/52aa0b70-8094-4971-862d-79793f41e6a8) is the network layout. Its seven reserved bytes and trailing padding are ignored, not interpreted as flags.
- [MS-FSCC Boolean](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/8ce7b38c-d3cc-415d-ab39-944000ea77ff) defines nonzero as true.
- [MS-FSA FileRenameInformation](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/87f86c9b-6c2a-4803-84b7-131a74a434fa) requires DELETE, remote RootDirectory zero and a destination without a leading backslash. It checks target existence, readonly/directory status, pending and output behavior. Source READONLY is not a rename prohibition in this algorithm.
- [MS-SMB2 SET_INFO processing](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/194c56d2-7fdc-4640-a2be-8bea6f8d177a) binds the authenticated Session/Tree/Open and validates request/credit/transaction limits before object-store processing.

The project intentionally preserves compatible old target references under replacement. MS-FSA's ordinary rename algorithm has a stricter opened-target condition. This source difference is a native qualification issue, not permission to weaken project object identity or to assert the standard generally allows replacement of any opened target.

The rename algorithm additionally requires denial when a source directory contains open descendant files or directories. Its [contains-open-files algorithm](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/133840e4-778e-44ca-9b41-da2323615075) examines descendant associations across clients and excludes the source itself. Strict descendant denial is the selected SMB admission contract; object-local source DeleteName checks alone would deviate from this MUST. A descendant's SHARE_DELETE does not exempt it.

The future mechanism can reuse existing data. [databaseCoordinator.pins](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/durable.go#L96-L107) already tracks physical references. [Reference admission](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/files.go#L195-L197), [atomic-open retention including uncertainty](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/atomic_open.go#L194-L215), [NodeReference paths](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/node_references.go#L20-L106) and [final close release](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/files.go#L527-L581) cover metadata-only/zero-use references and unresolved open/close responsibility. [fileDomain](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/files.go#L616-L646) and [MaxRetainedFiles](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/options.go#L55-L59) already bound volume-scoped retained references. The inspected defaults are [65,536 retained references and 1,000,000 integrity records](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/options.go#L12-L28); reuse of those options does not introduce a new product default.

Inference for the design: group the same coordinator.pins inventory as map[volume]map[NodeID]count and replace its eight production access sites through private helpers. Remove an empty group after its last settled release. This preserves coordinator lifetime and avoids coupling pin ownership to fileDomain retirement. Rehoming pins into fileDomain was also examined; it avoids another registry but changes lifetime ownership unnecessarily. Neither approach needs a parallel subtree index, counter or session registry.

For each bounded pinned candidate in the current volume group, the existing [nameObservationHeader](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/name_observation.go#L85-L147) validates kind/detach/association with indexed LIMIT 2 parent relations and no raw-name fetch. Follow those relations under the same coordinator.commit and [final namespace transaction](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/namespace_mutations.go#L240-L281), before exact same-name early return. Exclude source itself, ignore only fully validated Detached candidates, block any confirmed descendant pin with EACCES, and fail corruption/cycles/uncertainty. The existing [MaxIntegrityRecords](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/metastore/sqlite/options.go#L76-L79) can bound total candidate/ancestry work by widening its documented use. Budget, cancellation or I/O failure cannot establish absence of open descendants.

A neutral RequireNoOpenDescendants flag limited to NameRename selects this condition for SMB directories while FUSE remains false. The original directory's own references still follow normal source-sharing checks. This adds final-transaction work and changes the grouping of the existing pins; it does not claim that descendant enumeration is present at the inspected baseline. Its consistency with close, unknown results and cross-entry opens requires implementation acceptance.

## Allocation and information-class boundaries

[Current CREATE contexts](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/create_contexts.go) parse but ignore a well-formed AlSi. [MS-SMB2 allocation-context handling](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/3f343618-01b0-4aaf-b8a3-b270f9a6d334) requires the requested reservation to be passed to the object store, with failure reflected as disk-full. [The implementation appendix](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/a64e55aa-1152-48e4-8206-edd96444e7f7) describes Windows allocation handling. The existing ignore behavior is not evidence that the reservation was granted or universally optional.

This is an existing allocation-capability gap. Task 8.1 must not introduce an allocator merely to add supersede, and its new supersede path must decide supported contexts before effect. A reservation request cannot become claimed support merely because a zero-length content reset succeeded. The proposed new supersede mode rejects nonzero AlSi with STATUS_NOT_SUPPORTED after existing context-shape validation and before effects; absent/zero AlSi remains valid. This policy does not modify older CREATE modes.

[WDK file-information classes](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ne-wdm-_file_information_class) distinguishes ordinary rename/disposition from Ex classes 65/64 and kernel bypass class 66. POSIX or IGNORE_READONLY semantics are separate contracts; they are not hidden flags in ordinary rename padding. ADS, hard links, reparse traversal and unsupported property sets remain outside the project's existing Windows operation scope.

[MS-FSA FileNameInformation](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/a64d92b8-038b-470b-ad53-dd2218516507) specifies STATUS_NOT_SUPPORTED for a direct remote class-9 query. [MS-SMB2 QUERY_INFO rules](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/d64e0451-64a2-425a-848e-52a7dddab7b9) permit FileNormalizedNameInformation class 48 on SMB 3.1.1 and require share-relative normalized output.

[MS-FSA normalized names](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/3d5c68f8-fbc5-4f94-a51d-3600a319fd45) and [BuildRelativeName](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/280d599a-e920-4710-9e7c-611b64d5a15e) specify a leading backslash, backslash-separated components and backslash alone for the root. Known detached association has an explicit invalid-parameter result; unknown/unreachable association cannot become a cached name. [MS-FSCC FILE_NAME_INFORMATION layout](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/20406fb1-605f-4629-ba9a-c67ee25f23d2) is a four-byte little-endian byte length followed by counted UTF-16LE without a NUL. Supporting class 48 reuses these records without adding unrelated FileAllInformation fields or a new consistent-state API. OutputBufferLength below 8 requires INFO_LENGTH_MISMATCH using the SMB 3.1.1 error context. Otherwise a short result retains the full true FileNameLength, returns only an even-byte UTF-16 prefix, reports ByteCount as four plus that prefix and uses BUFFER_OVERFLOW.

[connection.responseBudget](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/connection.go#L582-L617) currently reserves fixed 128 bytes for file QUERY_INFO, while [relatedOperationFailed](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/connection.go#L619-L625) recognizes overflow warnings only for directory and filesystem queries. Class 48 must extend both existing rules: reserve its actual variable response before compound admission and recognize a validated class-48 overflow envelope so a related CLOSE executes. Signed compound boundary tests are necessary; a correct name encoder alone cannot prove these lifecycle effects.

## Conclusions and limits

The reusable authority mechanisms are MutateName/RenameTarget, rooted NamespaceGuards, original-reference name observations, ResetContent/OnReset, ordinary pending generation, independent CloseIntent, FileActions and the existing SMB owner/barrier chain. The concrete missing contracts are guarded NameCommand effect validation, explicit reset effect use, scalar generation projection, ordinary ABA repair, authorized no-op CLEAR CAS and variable retry-payload accounting. The standards-required directory descendant predicate has a researched mechanism using the existing pins inventory, with FUSE preserving its raw rename behavior. Codec and host observation work remain SMB-local.

The source review establishes where to extend these mechanisms; it does not prove their future implementation. Qualification must exercise final transaction rejection, object-identity preservation, DELETE-only reset rights, direct/HTTP/wrapper/FUSE parity, lost results and retained responsibility. The existing [native directory fixture](https://github.com/codetreker/remote-fs/blob/1aeef7b50d20c0bcc81764106c59775cd2e9ddc9/packages/smb/native_directory_fixture_test.go#L122) rejects IncludeName and must gain that real observation behavior for current-name tests; a second reduced authority model would hide the production contract.

No Windows 11 redirector, WNet mapping, cache invalidation, cross-machine visibility, resource default or cold-load performance result is established here. Windows Server CI native operation evidence and target Windows 11 release qualification remain distinct.
