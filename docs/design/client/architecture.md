# client 角色

命名空间的使用者。持有一份 remote storage，把命名空间呈现为本地目录，并维持这一呈现所需的全部本地状态。

本文只写 client 内部。角色边界、storage 与 RPC 两条契约的分工见 [`../architecture.md`](../architecture.md)。

## 一、内部构成

| 组件 | 职责 | 需求 |
|---|---|---|
| **remote storage** `packages/transport/httprest` | storage 接口的远端实现：每次调用一次 HTTP 请求，两次调用之间不留任何状态。超时策略随调用方给的 `http.Client` 而定。自身不缓存。 | R-INT-5、R-INT-9 |
| **挂载呈现层** `packages/fuse` | 把一份 storage 呈现为本地目录。本地只持有正在被打开的文件的内容，以及命名空间最后一次报出的剩余空间。仅 Linux。 | R-FS-1、R-CON-1~3、R-ERR-1、R-ERR-2、R-WS-5、R-INT-3、R-INT-8 |
| **生命周期** | 挂载的建立与拆除。 | R-WS-2 |

```
   程序 ──▶ 内核 VFS
                │
                ▼
        ┌──────────────────────────────┐
        │          挂载呈现层          │
        │  每个打开的描述符一个缓冲区  │
        └──────────────┬───────────────┘
                       │ storage 接口
                       ▼
        ┌──────────────────────────────┐
        │        remote storage        │
        │       一次调用一次请求       │
        └──────────────┬───────────────┘
                       │ RPC
                       ▼
```

挂载呈现层只认 storage 接口，因此把一份本地 storage 交给它即可得到一个不经网络的挂载点。

**FUSE 到这一层为止。** client 侧只有挂载呈现层说 FUSE 协议，它向下只用 storage 接口 —— 一份按路径寻址的命名空间 API，不挂载的那条路径（R-INT-5）用的是同一份。内核要而命名空间没有的东西 —— 节点身份、打开的文件的内容、挂载的生命周期 —— 都建立并保存在这一层。

## 二、挂载呈现层不缓存

内核的目录项超时、属性超时、负项超时都是 0。**每一次内核调用都落到 storage 上**，每一个答案描述的都是那一刻的命名空间。

由此：

- **跨机器的可见性不依赖任何机制。** 另一台机器上的写入一旦提交，这里的下一次 `stat` 就会看到它（R-CON-1、R-CON-2）。
- **没有需要失效的对象**，因此挂载呈现层不订阅变更推送流，也不向内核发送失效通知。
- **断线之后不需要重建任何本地状态**：重连即可继续。
- 代价：每一次 `ls`、每一次 `stat` 都是一个 RPC 往返。

只有一个数字例外，它不描述命名空间里的任何一个节点：命名空间最后一次报出的剩余空间，见第七节。

## 三、一个打开的文件就是一个缓冲区

storage 的读与写以整文件为单位，内核的读与写以 128 KiB 为单位。每个打开的描述符持有一份完整的文件内容，两侧在这里对接：

```
打开   ──▶ 先问大小，再取回整个文件，放进这个描述符的缓冲区
读     ──▶ 从缓冲区切片，不产生 RPC
写     ──▶ 打补丁或扩展缓冲区，标记为未提交；除了至多每秒一次去问剩余空间，不产生 RPC
关闭   ──▶ 未提交则整个写回
```

缓冲区属于描述符，不属于节点。两个程序同时打开同一个文件，各写各的副本；最后提交的那个赢，先提交的内容消失（R-CC-1 不在这一版内）。

三个边界：

- **`O_CREAT` 立刻在命名空间里建出文件**，不等到提交。同机另一个程序马上就能看到它。
- **`O_TRUNC` 从空缓冲区开始，不取回任何东西**，并立即算作未提交 —— 一次不写任何字节的截断仍然要被提交。
- **`truncate(2)` 在没有打开的描述符时直接写穿**；有描述符时落在它的缓冲区里，随其余内容一同提交。

### 单个文件的大小上限

一个打开的文件整份驻留在内存里，因此单个文件的大小就是一次调用能让进程分配的内存量。`Options.MaxFileSize` 给它设上限，缺省为 `fuse.DefaultMaxFileSize`（1 GiB）。调用方可以调高，但没有「不设上限」这个取值；负值在 `New` 处被拒绝。

超过上限的请求一律以 EFBIG 拒绝，且**拒绝发生在分配之前**：

| 上限之上的是 | 行为 |
|---|---|
| `truncate(2)`、`ftruncate(2)` 请求的长度 | EFBIG |
| `write(2)` 的终点（偏移 + 长度） | EFBIG。整次写入被拒，不截短为部分写入 |
| `open(2)` 时命名空间报告的文件大小 | EFBIG。内容不被取回 |
| 截到非零长度，而文件本身超限 | EFBIG。保留前缀需要取回整个文件，而 storage 没有按区间读 |
| 截到 0，而文件本身超限 | 成功。截到 0 不需要取回任何东西 |

因此打开一个文件是两次 storage 调用：先 `Stat` 问大小，再 `Read` 取内容。两次之间文件变大的话，取回的仍然是变大之后的整个文件。

## 四、提交发生在关闭时

`close(2)` 是失败还能被告知给发起者的最后时刻，提交因此挂在它上面，而不是挂在描述符的最后一个引用被释放时 —— 后者的返回值被内核丢弃。`fsync` 走同一条提交路径。

提交失败时错误返回给 `close`，缓冲区里的内容不保留、无处查询（R-ERR-3 不在这一版内）。不重试。

**写入方自己通过同一个描述符看得到自己写的内容**，包括大小与修改时间。同机的其它进程在提交之前看到的是命名空间里的旧内容。

## 五、够不到就报错

storage 的错误是 `syscall.Errno`，挂载呈现层原样交给内核。取不到 errno 的错误一律成为 EIO。

**绝不返回空目录、绝不报告文件不存在、绝不返回过期内容**（R-ERR-1、R-ERR-2）。这一条覆盖每一个操作，包括那些「回答不出来就随便给个值」看起来无害的：目录大小、扩展属性。

## 六、命名空间答不上来的，挂载呈现层不代答

storage 契约有模式与两个时间的写入口，也有整个命名空间的容量，但没有属主、没有扩展属性。凡是内核问到而契约答不上的，挂载呈现层报错：

| 被问到 | 回答 |
|---|---|
| `chown` 改成挂载者以外的属主 | EPERM |
| 契约之外的其它属性 | EPERM |
| 扩展属性 | EOPNOTSUPP |
| `renameat2` 的 `RENAME_EXCHANGE`、`RENAME_NOREPLACE` | EINVAL |
| 符号链接指向哪里 | EOPNOTSUPP |
| 硬链接 | 不提供（R-FS-4） |
| 类型无法命名的节点 | EIO |

`chmod` 与 `utimens` 落到 `SetAttr` 上；新建一个文件或目录之后，挂载呈现层随即把调用方要求的模式设上去。属主是唯一一个报错的属性：命名空间不带属主，挂载点把每个节点都报成挂载它的那个用户（R-SEC-1），因此把属主改成那个用户就是它已经是的样子，改成别人则无处存放。

目录的链接数一律为 1。

### 符号链接

命名空间不创建符号链接，也读不回一个链接指向哪里 —— R-FS-1 要求的符号链接不在这一版内。但服务端交出去的那个目录里可以已经有一个，是别的东西放进去的，于是挂载呈现层如实报告它：

| 对一个符号链接做 | 结果 |
|---|---|
| `lstat`、列目录 | 报告为符号链接，模式与长度都是链接自己的 |
| `readlink` | EOPNOTSUPP |
| `stat`、`open`、读、写 | EOPNOTSUPP —— 内核解析这些路径时先 `readlink` |
| `rm` | 删掉链接本身，它指向的文件不动 |
| 改名 | 搬动链接本身 |

于是**不存在「以链接的名字拿到它指向的那个文件」这条路径**。答不出指向哪里就报 EOPNOTSUPP，不报 EINVAL —— 后者的意思是「这不是一个链接」。

## 七、容量

命名空间报出自己的容量，挂载呈现层把它换算成内核要的块数：

| 内核要的 | 从哪来 |
|---|---|
| 块大小 | 固定 4096 字节。命名空间按字节计量，块只是报出去时的计价单位 |
| 总块数 | 命名空间的总量 |
| 空闲块数 | 总量减已用，不为负 |
| 可用块数 | 命名空间报的「还能写入的量」 |
| inode 数、空闲 inode 数 | 都是 0。这里不数 inode，0 是「没有 inode 表」的报法，`df` 把它显示成没有这一栏，而不是显示成已经用尽 |
| 名字长度上限 | 255 |

三个块数都向下取整：装不满的一块不计入。

自己没有容量可报的命名空间以 `ENOSYS` 拒绝，这个拒绝原样到达调用方 —— `df` 说「功能未实现」，那是实话。三个数不能同时为真时是 EIO。两者都不换成编造的数字（R-WS-5、R-ERR-2）：FUSE 库对不作答的文件系统的默认回答是一个全零结构，读起来是一块没有剩余空间的盘，而先查空间再决定写不写的程序会照着它行事。

**默认配置下，这一整节只对挂载它的那个用户成立。** 别的调用方问 `statfs` 时，内核自己回答，回的是一个清零的结构，请求根本到不了这一层。于是 `sudo df` 与同机的其它本地用户看到的都是一块 0 字节、0 可用的盘 —— 那正是上一段拒绝去编造的那个答案，而挂载这一侧没有任何东西能改变它。

改变它的开关在主机上，不在本系统里：fuse 模块参数 `allow_sys_admin_access`（`/sys/module/fuse/parameters/allow_sys_admin_access`，默认关）打开后，初始 user namespace 中带 `CAP_SYS_ADMIN` 的调用方绕过这项检查，`sudo df` 于是问到这一层，读到的是真数字。因此这条代价是有条件的：默认配置下 `df` 是一条只对挂载者有效的通道，要让 root 也看得见，需要运维在主机上打开那个参数。

问容量这一次调用带自己的 2 秒截止时间，不用挂载点通用的操作超时：`df` 会走遍机器上的每一个挂载点，一个够不到的服务端否则会让整台机器上的 `df` 卡满那个超时。

### 配额在造成它的那次调用处就拒

配额由命名空间那一侧执行，超出配额的提交以 EDQUOT 失败。但提交发生在 `close(2)`，而大量程序从不查看 `close(2)` 的返回值 —— 只在那里拒绝，等于让那些字节无声地消失。失败必须落在造成它的那次调用上（R-WS-5）。

因此挂载呈现层持有一个数字：命名空间最后一次报出的「还能写入的量」。每一次会让缓冲区变长的调用 —— `write(2)`，以及落在打开的描述符上的 `ftruncate(2)` —— 拿这次改动要多占的字节数与它相比，比不过就地 EDQUOT（不是 ENOSPC —— 没有哪块盘满了，是一份配额被用完了）。没有描述符的 `truncate(2)` 直接写穿到命名空间，由命名空间以同一个 errno 拒绝，于是同一件事不会因为手上有没有描述符而在两个地方给出两种答案。

**变短的改动不做这项比对，也从不因为配额被拒**，哪怕命名空间已经在配额之上：一个越了限的 workspace 必须有一条回到限下的路，而把文件截短正是那条路。

这个数字：

- **整个挂载点共用一个**，因为它描述的是命名空间，不是某一个文件。
- **至多每秒重新问一次。** `write(2)` 是文件系统最热的一条路，每次都问一遍，代价远超过它买到的那次拒绝。
- **过了期就由发现它过期的那次写入去换掉它**，其余在途的写入照旧用手上这个数，谁也不必排在别人后面等（R-CC-2）。
- **问失败不清空它**：上一次量到的仍然是最后有人量到的。一次都没问到之前没有数字，也就不做任何比对。
- 命名空间报了 `ENOSYS` 的话，这个问题不再问第二次，此后任何写入都不做这项比对。

**它按设计就是会过期的，因此它只提前拒绝、从不放行。** 数字偏大，放不下的写入会被放过，由提交去拒绝 —— 提交才是权威。数字偏小，一次本来放得下的写入被拒，下一次就通过了。它唯一的作用，是把那个终归要来的拒绝送到造成它的那次调用上。

以 `O_TRUNC` 打开的描述符不知道命名空间里原先那份内容有多长 —— 那条路径没有问过 —— 于是它写回去的内容按全额计费。这会拒掉一次本来放得下的写入，而不会放过一次放不下的。

## 八、节点身份由这一层给出

内核认一个节点靠一个编号，storage 契约里没有这个编号，挂载呈现层因此自己分配并保存它。

保存的形式是一棵名字树，每个被解析过的名字一条记录，记着编号与节点的类型。编号取自一个只增的计数器，用过不再发第二次：一个节点消失之后，它的编号不再指向任何东西。

| 发生的事 | 记录的变化 |
|---|---|
| 查到一个此前没见过的名字 | 发一个新编号 |
| 再查同一个名字，包括并发地查 | 拿到同一个编号 |
| 改名 | 记录随节点搬到新名字上；旧名字不再指向任何节点，之后建在那里的是另一个节点，拿另一个编号 |
| 改名一个目录 | 底下的记录随它一起搬，各自的编号不变 |
| 删除，或者查名字时发现它已经不在了 | 连同底下的整棵子树一起丢掉 |
| 列目录 | 目录里已经没有的名字，连同底下的子树一起丢掉；列的过程中冒出来的新名字不算在内 |
| 同一个名字换了类型 | 那是另一个节点，发一个新编号 |

由此：两个同时存在的节点绝不共用编号；被内核遗忘过的节点再查回来仍是原来的编号。

记录只在两处收缩：查一个名字发现它不在了，以及列它所在的目录。别的 client 删掉的名字因此要等到有人再问起它、或者列一次它的父目录，才被丢掉；在那之前它占着一条小记录。走遍一棵大目录树会给见过的每个名字留下一条记录，直到卸载或者那个名字从它的目录里消失。

跨卸载重挂不稳定：编号是这一次挂载的，不是命名空间的。

## 九、生命周期

挂载与卸载是频繁的日常操作（R-WS-2）。一次挂载把一份 storage 接到一个挂载点上，并在卸载或内核断开连接时结束。

## 十、client 不做什么

- **不缓存命名空间。** 挂载呈现层与 remote storage 都不把目录项、属性或内容留在本地；唯一被持有的数字是剩余空间，而它不决定任何事（第七节）。
- **不重试失败的写入。**
- **不在离线时接受写入。**
- **不代答命名空间答不出的问题。**

## 十一、部署形态

作为库嵌入集成方既有的 daemon service，或作为独立二进制运行（R-INT-1、R-INT-4）。作为库时不注册信号处理、不写标准输出、不调用进程退出、不修改进程级设置、包加载时不产生副作用（R-INT-2）；日志只写入调用方给定的目的地，未给定则丢弃。

只使用 remote storage 而不挂载是第三种用法（R-INT-5），这条路径不依赖 FUSE，因此不受 Linux 限制。
