# client 角色

命名空间的使用者。持有一份 remote storage，把命名空间呈现为本地目录，并维持这一呈现所需的全部本地状态。

本文只写 client 内部。角色边界、storage 与 RPC 两条契约的分工见 [`../architecture.md`](../architecture.md)。

## 一、内部构成

| 组件 | 职责 | 需求 |
|---|---|---|
| **remote storage** | storage 接口的远端实现：每次调用一次 RPC。持有连接与会话，负责重连、订阅变更推送流、报告连接状态。自身不缓存。 | R-INT-5、R-INT-9 |
| **挂载呈现层** | 把一份 storage 呈现为本地目录。持有命名空间视图、元数据缓存、写暂存，并负责令内核缓存失效。仅 Linux。 | R-FS-1、R-CON-1~4、R-CC-1、R-ERR-1~3、R-INT-8 |
| **生命周期与控制面** | 挂载的建立与拆除、配置、控制通道服务端、状态上报。 | R-ERR-4、R-WS-2、R-WS-3 |
| **CLI** | 控制通道的客户端。 | R-INT-4 |

```
   程序 ──▶ 内核 VFS
                │
                ▼
        ┌──────────────────────────────┐        ┌──────────────────┐
        │        挂载呈现层             │◀───────│  生命周期与控制面 │◀── CLI
        │  命名空间视图 / 缓存 / 暂存   │        └──────────────────┘
        └──────────────┬───────────────┘
                       │ storage 接口
                       ▼
        ┌──────────────────────────────┐
        │       remote storage         │
        │   会话 / 重连 / 变更流订阅    │
        └──────────────┬───────────────┘
                       │ RPC
                       ▼
```

挂载呈现层只认 storage 接口，因此把一份本地 storage 交给它即可得到一个不经网络的挂载点——这是验收判据 A5 的基础。

## 二、缓存放在挂载呈现层，remote storage 不缓存

remote storage 保持「一次调用一次 RPC」。这样只使用它、不挂载的调用方（R-INT-5）得到的是一个行为可预测的客户端，而不是一个行为取决于订阅是否健康的客户端。

缓存是挂载呈现层的事，因为只有它需要——文件系统调用的密度决定了不缓存就无法使用。

## 三、什么时候本地副本可信

这是整个 client 侧最要紧的一条。

> **本地副本可信，当且仅当自它被取回以来，变更推送流一直被连续观察。**

不是「未超过某个时长」。时长只是兜底：万一 server 漏发了它应该发的事件，时长限制了错误存活多久。**真正的依据是观察的连续性。**

由此推出三种状态：

| 状态 | 条件 | 行为 |
|---|---|---|
| **连续观察中** | 推送流在线，位置是当前的 | 正常使用本地副本 |
| **中断，但仍可续** | 推送流断开，尚在 server 保留窗口内 | 已取回的继续可用（取回时它是真的，且 server 会重放漏掉的）。新的问题等待连接，不猜测。写入立即失败。 |
| **已断裂** | 超出保留窗口，或续订时被告知无法重放 | 全部本地副本作废。每个操作都必须到达 server，到不了就失败（R-ERR-1）。 |

第二种与第三种的分界由 **server 的保留窗口**决定，不由 client 自行选择。停留在第二种状态超过那个点，就是在观察已经断裂之后仍然相信本地副本。

**连接状态因此是正确性输入，不是运维指标。** 推送流断了多久才被察觉，就是本地副本被错误使用了多久。

## 四、重同步的次序

推送流断裂后重建本地状态时：

```
先订阅（记下订阅的起始位置）──▶ 再重新取数据
```

反过来会静默丢失两个动作之间发生的变更——重取回来的数据早于一个永远不会提到它的订阅，窗口很小，损失是永久的，且事后无从察觉。

「重建」不等于遍历命名空间。文件系统按需取数，作废本地副本的代价是后续访问多几次 RPC，而不是一次全量遍历——这很幸运，因为全量遍历会把上面那个竞态拉长到整个遍历的时长。

## 五、变更事件的应用次序

```
收到事件 ──▶ 先更新本地命名空间视图 ──▶ 再令内核缓存失效
```

顺序不可颠倒。内核被要求失效后会在下次访问时重新询问，若此时本地视图尚未更新，它拿到的正是刚被要求丢弃的旧值。

**仅有次序还不够。** 一个在事件到达前就已发出的请求，可能在事件应用之后才返回，把旧值写回本地视图，而此时已经没有待处理的失效动作来纠正它。因此每个响应都携带它所反映的位置，本地视图只接受不比现有更旧的数据。次序与位置比较是同一件事的两半，缺一不可。

**失效动作必须能在别的一切都卡住时继续进行。** 令内核失效时可能与内核对我们的调用相互等待，因此失效不能在处理请求的路径上同步进行；投递失效动作也绝不能阻塞，否则死锁会从另一条路回来。

## 六、写入

```
打开写 ──▶ 在本地暂存文件中准备内容
写入   ──▶ 只写暂存文件，不产生 RPC
关闭   ──▶ 提交（携带所依据的版本）
           ├── 成功 ──▶ 其它 client 可见
           └── 失败 ──▶ 错误返回给 close，暂存内容保留并可查询
```

**提交发生在关闭时，因为那是失败还能被告知给发起者的最后时刻。** 而程序普遍忽略关闭的返回值，所以提交失败的暂存内容**保留而非删除**，并可通过控制通道查到（R-ERR-3、R-ERR-4）。不重试——重试意味着一个我们并未做出的持久化承诺。

**本机的读取立即看到本机的写入**，包括大小与修改时间（R-CON-4）。否则写完文件再检查大小的程序会认为写入失败。

**打开已有文件写入需要先取回内容。** 这与「单个操作不得阻塞整段传输」相互冲突，冲突在大文件上显现；两者如何调和见[写会话与稀疏暂存](../../../.agents/notes/proposed/architecture/2026-08-19-write-session-and-staging.md)。

## 七、生命周期与控制面

挂载与卸载是频繁的日常操作（R-WS-2），不是罕见的管理动作。一个进程可持有多个挂载点，它们共享连接与本地状态。

控制通道对外提供：挂载、卸载、状态、以及**未能保存的写入清单**。

状态里有两件事从挂载点内部看不出来，而文件系统本身没有地方表达它们：**连接是否已断裂**，以及**是否存在提交失败的写入**。不上报，它们就不存在。

## 八、client 不做什么

- **不判断自己是否落后。** 由 server 明确告知无法重放，client 才作废本地状态；自行猜测会在两个方向上都出错。
- **不重试失败的写入。**
- **不在离线时接受写入。**
- **remote storage 不缓存。**

## 九、部署形态

作为库嵌入集成方既有的 daemon service，或作为独立二进制运行（R-INT-1、R-INT-4）。作为库时不注册信号处理、不写标准输出、不调用进程退出、不修改进程级设置（R-INT-2）；缓存、暂存占用、并发请求数都有可配置上限（R-INT-3）。

只使用 remote storage 而不挂载是第三种用法（R-INT-5），这条路径不依赖 FUSE，因此不受 Linux 限制。
