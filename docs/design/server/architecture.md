# server 角色

命名空间的权威持有者。持有一份 storage，把它经 RPC 暴露给多个 client，并负责记录与分发变更。

本文只写 server 内部。角色边界、storage 与 RPC 两条契约的分工见 [`../architecture.md`](../architecture.md)。

## 一、内部构成

| 组件 | 职责 | 需求 |
|---|---|---|
| **请求处理** | 接收 RPC 请求，调用 storage，返回结果。不持有命名空间状态，不缓存。 | R-INT-1 |
| **变更日志** | 为每一次成功的修改分配一个单调递增的位置并记入日志；按位置重放；维护保留窗口。 | R-CON-1、R-CON-2 |
| **订阅分发** | 维护各 client 的推送流：从其给定位置重放，追平后转入实时分发。 | R-CON-1 |
| **storage** | 命名空间的实际存取。由集成方提供，或使用随附的本地文件实现。 | R-INT-6 |

```
        RPC 请求                      变更推送流
            │                              ▲
            ▼                              │
     ┌─────────────┐              ┌────────────────┐
     │  请求处理    │──── 修改 ───▶│    变更日志     │───▶│ 订阅分发 │
     └──────┬──────┘   成功后记录  └────────────────┘
            │                              保留窗口
            ▼
     ┌─────────────┐
     │   storage   │   localdir / 对象存储 / 集成方自有
     └─────────────┘
```

## 二、写入与记日志的次序

```
请求处理 ──▶ storage 提交（携带调用方所依据的版本）
              ├── 版本不符 ──▶ 拒绝，不记日志
              └── 成功 ──▶ 变更日志分配位置并记录 ──▶ 分发
```

**先落 storage，后记日志。** 顺序颠倒会记下一次并未发生的修改，而 client 无从分辨。

反过来的风险是：storage 已提交而日志未记（进程在两步之间死亡）。此时该次修改真实存在但没有事件，客户端只能靠自身的兜底机制发现。这是本设计接受的风险，代价换取的是「日志里的每一条都确实发生过」——反向的错误更难被察觉，也更难恢复。

## 三、变更日志

日志记录发生了什么，不记录内容本身：某个节点被创建、被删除、内容变了、属性变了、被改名到何处。每条带一个单调递增的位置。

**位置是全序的，且与提交顺序一致。** 这是 client 得以维持一份不偏离事实的命名空间视图的唯一依据。

**保留窗口。** 日志不无限保留。窗口长度是一个部署参数，它直接决定了一个 client 可以断开多久而仍能续上：

- 窗口内 → 从断点重放，client 的本地状态继续有效
- 窗口外 → 明确告知无法重放，client 丢弃全部本地状态重建

**空闲时也要推进位置。** 长时间无变更时，推送流仍周期性发出位置标记。否则一个只是安静的 client 会在重连时被误判为落后太多，白白丢掉一份并未过期的本地状态。

## 四、订阅分发

每个 client 的推送流有两个阶段：**重放**（从其给定位置追到当前）与**实时**（新变更直接送出）。两个阶段对 client 而言没有区别，事件序列是连续的。

**慢订阅者被断开。** 每个订阅者有一份有上限的待发缓冲；超出上限即断开该订阅者。

这是刻意的：一个停止读取的 client 若能拖住日志，就会把自己的问题变成所有人的内存问题。断开它，问题就收敛回它自己——重连时若还在窗口内则续上，否则重建。

## 五、storage 的位置

server 通过 storage 接口访问命名空间，不知道底下是什么。集成方注入自己的实现（R-INT-6），或使用随附的本地文件实现。

storage **不参与**变更历史（见顶层设计第四节）。它只需满足身份稳定、版本随内容变化、提交原子、提交时校验版本这四条。

**版本校验在 storage 侧完成，不在请求处理侧。** 「读出当前版本 → 比较 → 写入」若拆成两步，两次并发提交可以同时通过比较（R-CC-1 因此失效）。校验必须与写入是同一个不可分割的动作。

## 六、server 不做什么

- **不缓存。** 命名空间的事实就在 storage 里，缓存只会引入一份可能过期的副本。
- **不持有 client 的状态。** 除订阅位置外，server 不知道任何 client 的情况。client 消失即消失。
- **不做鉴权。** 且不做半套——不留形同虚设的校验分支、不留默认放行的开关、不打印会让人误以为受保护的日志。理由见[第一个可用版本的范围](../../../.agents/notes/proposed/process/2026-08-19-mvp-scope.md)。

## 七、部署形态

作为库嵌入集成方既有的 server，或作为独立二进制运行（R-INT-1、R-INT-4）。作为库时不注册信号处理、不写标准输出、不调用进程退出（R-INT-2）；待发缓冲与日志保留量都有可配置上限（R-INT-3）。
