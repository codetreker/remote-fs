# 设计（Design）

系统的架构，**已经定下来的样子**。

**这里不是思考记录，也不是设计讨论的场所。** 不写方案权衡、不写探索过程、不写结论是怎么得出来的。读者打开这些文档是为了知道系统是怎么建的，不是来围观它被想明白的过程。

证据与调研在 `docs/research/`。系统必须做到什么在 `docs/spec/`。

## 两个层次，以及它们之间的界线

架构自外向内分两层来写。

### 顶层设计

系统整体：由哪些模块构成、每个模块负责什么、彼此如何依赖、数据如何流动。它定义边界，以及跨越边界的契约。

它**停在每个模块的表面**。任何模块的内部结构都不出现在这里。

### 模块设计

一个模块一份：这个模块内部怎么组织、对外暴露什么、依赖什么、内部数据如何流动。

它**停在自己的边界**。不解释系统全貌，也不伸进别的模块内部；引用其它模块只能通过顶层设计定义的契约。

这条线是双向的，两个方向都要守。顶层文档一旦下沉进某个模块的内部，就不再是总览；模块文档一旦重讲一遍系统全貌，就出现了第二份总览——而它迟早会跟第一份漂移。

## 一份设计文档写什么

- 结构：由哪些部分构成、各自的职责、依赖关系
- 每条边界上的契约
- 数据流
- 这个结构带来的后果：它让什么变容易、让什么变不可能、代价是什么
- 每一部分对应 `docs/spec/requirements.md` 里的哪些需求编号

## 不写什么

- **推理与权衡。** 当一个决定很可能被不知情的人推翻时，允许**一句话**的理由。不允许一节，更不允许方案对比。
- **需求。** 需求属于 `docs/spec/`。设计只说需求如何被满足，绝不重述需求是什么。
- **调研。** 引用、实测数据、源码考据属于 `docs/research/`。设计可以陈述结论并指向调研，但不搬运证据。
- **状态、历史、计划。** 设计用现在时描述系统被设计成的样子，不写「当前进度」「后续打算」这类会过期的内容。

## 文件

```
docs/design/
  README.md               本目录的规则
  architecture.md         顶层设计：角色、边界、跨角色数据流
  server/
    README.md             server 目录的规则
    architecture.md       server 角色内部
  client/
    README.md             client 目录的规则
    architecture.md       client 角色内部
```

第二层按**角色**切分，不按包切分。一个角色一个目录；该角色内部若需要进一步展开，在自己的目录里增加文档，不影响另一个角色。

每个目录都有 `README.md`，写的是**该目录的规则**——什么该放进来、什么不该、有哪些文档。设计内容按其内容命名，不写进 `README.md`。
