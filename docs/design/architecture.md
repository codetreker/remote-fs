# 顶层设计

本文描述系统由哪些角色构成、各自持有什么、如何交互、数据如何跨角色流动。角色内部的设计不在这里，见 `server/` 与 `client/`。

## 一、两个角色

系统只有两个角色，它们运行在不同的机器上，通过 RPC 交互。

**server** —— 命名空间的权威持有者。它持有一份 **storage**（本地文件、对象存储、或集成方自有的任何东西），并把它经由 RPC 暴露出去。命名空间的事实以这里为准。

**client** —— 命名空间的使用者。它持有一份 **remote storage**：一个把每次调用变成一次 RPC 的 storage 实现。client 侧还负责把这份命名空间呈现为本地目录，以及维持这一呈现所需的全部本地状态。

一个 server 面对多个 client（R-CON-1）。client 之间不直接通信。

## 三、同一个接口，两个模块

client 侧的 remote storage 与 server 侧的 storage **实现同一个接口**。

它们**不是同一个模块**，也不在同一个角色里：server 侧的那个真正持有数据；client 侧的那个不持有任何数据，它把每次调用翻译成一次 RPC。

接口相同带来两个直接后果，都不需要额外设计：

- 挂载呈现层只认这个接口，因此**可以直接挂载一份本地 storage，完全不经过网络**。这是验收判据 A5「与真实目录对拍」的基础。
- RPC 服务端也只认这个接口，因此**把 remote storage 交给它就得到一个代理**。

## 四、两条契约的分工

跨角色边界上有两条契约，分工必须清楚，否则义务会重复或落空。

**storage 接口**：一份命名空间的存取。它**不负责变更历史**——所有写入都经由 server 落到 storage，因此 server 天然看得见每一次修改，历史由 server 记录（见 `server/architecture.md`）。这样 storage 的实现门槛才低到第三方愿意接入自有存储（R-INT-6），`localdir` 也不必自建一份历史。

代价：绕过 server 直接改动底层存储，server 察觉不到。这不在当前场景内，将来可作为 storage 的一项可选能力补上。

任何 storage 实现必须满足：

| 义务 | 违反的后果 |
|---|---|
| 节点身份跨改名保持稳定，删除后不再复用 | 一个文件的内容会以另一个文件的名字被读到 |
| 内容版本在内容变化时必定改变 | 使用方无从判断本地缓存是否仍然有效 |
| 内容提交是原子的 | 其它 client 读到撕裂的文件 |
| 提交时校验调用方所依据的版本，不符则拒绝 | 并发写会静默丢失（R-CC-1） |

**RPC 接口**：跨角色的实际边界。除了转发 storage 的各项操作，它额外承载变更推送流，并必须满足：

| 义务 | 违反的后果 |
|---|---|
| 变更事件全序，且与提交顺序一致 | client 的命名空间视图永久性地偏离事实 |
| 每次修改恰好产生一个变更事件 | 漏掉的那次修改不会被任何人察觉 |
| 可从保留窗口内的任意位置重放变更 | 每次断线都要付出重建全部本地状态的代价 |
| 无法重放时明确报告，而不是从「当前」悄悄开始 | client 以为自己一直在观察，实际漏掉了变更。**这是最坏的一种失败**，因为它无声且事后无从察觉 |

client 侧的 remote storage 实现 storage 接口，但它**不产生**上述任何性质——它如实传递 server 侧的性质。因此一旦 server 侧违反其中一条，client 无从补救。

## 五、跨角色的数据流

### 读

```
程序 read ──▶ 挂载层 ──┬── 本地已有可信副本 ──────────────▶ 返回
                       └── 没有 ──▶ remote storage ──RPC──▶ server ──▶ storage
```

「本地是否有可信副本」由挂载层判断，判断依据来自变更推送流。remote storage 自身不做缓存，每次调用都是一次真实的 RPC。

### 写

```
程序 open/write ──▶ 挂载层写入本地暂存，不产生 RPC
程序 close      ──▶ remote storage 提交（携带所依据的版本）──RPC──▶ server
                     ├── 成功 ──▶ 其它 client 可见
                     └── 版本不符或失败 ──▶ 错误返回给 close，暂存内容保留
```

提交前对其它 client 不可见（R-CON-3）；同机进程立即可见（R-CON-4）；提交失败不丢数据（R-ERR-3）。

### 变更传播

```
client A 提交 ──RPC──▶ server ──▶ 写入 storage
                          │
                          ▼
                    记录变更并分配位置
                          │
                          ▼
                变更推送流分发给所有 client
                          │
          ┌───────────────┴───────────────┐
          ▼                               ▼
     client B                        client C
          │                               │
remote storage 收到并推进位置              …
          ▼
挂载层先更新本地状态
          ▼
挂载层再令内核缓存失效
          ▼
内核下次访问时重新询问 ──▶ 得到新的事实
```

最后两步的顺序不可颠倒：先让内核失效，它会立刻重问一个尚未更新的本地状态。

client A 自己也会收到自己那次提交的事件；按变更位置判重即可，不需要识别事件来源。

### 挂载与卸载

```
CLI ──▶ 控制通道 ──▶ 生命周期管理 ──▶ 建立 remote storage 与 RPC 连接
                                   ──▶ 建立挂载呈现层，附着到本地目录
卸载：拆除挂载呈现层，断开连接
```

挂载与卸载是频繁的日常操作（R-WS-2）。冷挂载时本地无任何既有状态（R-WS-3）。

## 六、部署形态

两个角色各有两种存在方式（R-INT-1、R-INT-4）：

| 角色 | 作为库嵌入 | 作为独立进程 |
|---|---|---|
| server | 链接进集成方既有的 server | 独立服务端二进制 |
| client | 链接进集成方既有的 daemon service | CLI 二进制，带参数时以 daemon 方式运行 |

client 侧还有第三种用法：只使用 remote storage，不挂载（R-INT-5）。这条路径不依赖 FUSE，因此不受 Linux 限制。

## 七、第二层

各角色内部的设计各占一个目录，一个角色一份：

- `server/architecture.md` —— RPC 服务端、storage 实现、变更日志与订阅分发
- `client/architecture.md` —— remote storage、挂载呈现层、缓存与暂存、生命周期与控制面

第二层只写角色内部，不重讲系统全貌，跨角色只通过本文定义的接口与契约来引用。

## 八、代码组织

代码组织与角色划分不是一回事：一个包可能被两个角色共用（如接口定义与协议词汇），一个角色也可能由多个包构成。

整个仓库是**单个 Go module**，模块路径 `github.com/codetreker/remote-fs`。

```
go.mod

packages/                    可被外部与自身 import
  storage/                   接口定义与实现者义务（两个角色共用）
    localdir/                本地文件实现
  protocol/                  RPC 的操作与数据词汇（两个角色共用）
  transport/                 连接抽象（两个角色共用）
    grpc/
    websocket/
    httpsse/
  server/                    RPC 服务端
  client/                    remote storage
  mount/                     挂载呈现层；缓存与暂存；仅 Linux
  daemon/                    生命周期与控制面服务端
  control/                   控制通道协议（daemon 与 CLI 共用）

cmd/                         二进制，不被 import
  remote-fs/                 CLI；带参数时以 daemon 方式运行
  remote-fs-server/          独立服务端

docs/
```

包与角色的对应：

| 包 | 归属 |
|---|---|
| `storage`、`protocol`、`transport` | 两个角色共用 |
| `storage/localdir` | server 侧（也用于本地挂载的验证路径） |
| `server` | server 侧 |
| `client`、`mount`、`daemon`、`control` | client 侧 |

单 module 不与 R-INT-10 冲突：只 import 某一种 `transport` 的集成方不会链接其余两种的代码。若将来依赖面本身成为问题，任一子目录都可以就地变成独立 module 而不改变其 import 路径。

三处拆分有明确理由：三种 `transport` 实现各自成包，使得选用其一的集成方不承担其余的依赖（R-INT-10）；`storage` 与 `storage/localdir` 分开，使得第三方实现自有存储时只需引入接口（R-INT-6）；`mount` 与 `client` 分开，使得不挂载的使用者不被 FUSE 与平台限制绑住（R-INT-5、R-INT-8）。
