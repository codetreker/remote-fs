# 规格说明（Spec）

这个系统是给谁用的、要解决什么、对外承诺什么。**这里不写它怎么实现。**

## 这是哪一种 spec

「spec」在业界至少指五种东西：需求文档、产品简介、形式化模型、协议定义，以及——最容易搞混的——设计文档。本目录不完全是其中任何一种，所以先说清楚它是什么：

**一份带明确契约的 functional spec。** 也就是从外部可观察的行为，写到足以照着做验收测试的精度，并且对每一类依赖我们的人分别写清楚。

它刻意**不是** PRD——这是基础设施，没有市场定位要谈。**不是** IEEE 830 那种编号 shall 条款——文件系统的行为只有作为整体才有意义，拆成一条条独立句子后，恰恰丢掉了最要紧的那些相互作用。**也不是**形式化模型——一致性保证将来值得用形式化方法写，现在做是本末倒置。

## 什么该写进来

- **问题**，以及这是谁的问题。
- **用户**，以及每一类用户想达成什么。
- **场景与工作流**，端到端，从意图到结果。
- **系统对使用它的程序做出的保证**——什么成立、什么不成立、多快成立。这是全篇的重心，也是最该被逐条挑战的部分。
- **接入自有存储的一方必须履行的义务。** 他们是我们依赖的一方，所以他们必须保证什么，属于契约，不是实现细节。
- **规模**：上述保证必须在什么量级上成立。
- **什么情况算失败**——出现哪些结果会让这个系统不值得存在。
- **明确的非目标**，写下来，免得后来的人「顺手修好」其中一条。

## 什么不该写进来

机制。分层、组件、缓存、传输格式、数据结构、算法、库的选型、包布局、方法签名。

这些属于 `docs/design/`。支撑这些选择的调研和证据属于 `docs/research/`。

## 边界怎么判

判据是 **义务 vs 机制**，不是「接口 vs 内部实现」。**另一方必须满足的契约**属于这里；**任何一方用什么机器去满足它**不属于这里。

按顺序用两条测试：

1. **读者能不能在不提出另一种实现的前提下反对这句话？** 不能，它就是机制。
2. **这句话能不能熬过一次彻底重写？** 如果另一个实现拥有相同的外部行为、却会让这句话变假，它就是机制。

下面是例子，包含那些真的不好判的情况：

| 陈述 | 判定 | 理由 |
|---|---|---|
| 「一台机器上的改动，另一台机器在一秒内可见。」 | spec | 这是保证，可以就其本身争论。 |
| 「客户端订阅一条变更事件流。」 | design | 机制，而且是能实现上面那条保证的若干机制之一。 |
| 「服务端不可达时，读操作报错，而不是返回较旧的内容。」 | spec | 可观察行为，而且可测。 |
| 「缓存条目带一个代际计数器。」 | design | 机制。 |
| 「存储实现绝不能把两个不同的对象呈现为同一个对象。」 | spec | 对另一方的义务，且措辞中立到任何实现都能满足。 |
| 「存储分配的标识符在删除后不得复用。」 | **按此措辞属于 design** | 同一条义务，但措辞预设了「标识符」。改成行为化表述就该进来。 |
| 「程序必须能在挂载的目录树上跑 `git status`。」 | spec | 上述保证的一条具体验收标准。 |

最后一行才是写这一切的意义所在：**一条写得足够精确的保证，本身就已经是一个验收测试。** 措辞要做到别人不用追问就能照着写出测试。

## 语言

**spec 用中文写**，因为它是要被反复阅读和争论的那份文档，中文读起来更自然。可以夹用英文术语。

`docs/design/`、`docs/research/`、代码与注释仍然用英文。

## 本目录的结构

```
docs/spec/
  README.md          边界规则、约定、索引
  problem.md         问题、用户、场景、交付形态、开放假设
  requirements.md    完整目标需求，带编号
```

两份都是**活文档**：认知变了就地重写，永远只有一份、永远是当前有效的那份。给它们加日期会产生几份日期不同的需求文档，谁也说不清哪份算数。

**这里不记录「哪一轮做哪些」。** 范围切分是一个带备选方案的决定，它属于 `.agents/notes/`，用需求编号引用本目录的条目。spec 说系统最终要做到什么，不说什么时候做。
