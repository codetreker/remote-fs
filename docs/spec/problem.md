# 问题、用户与场景

## 问题

一个 agent 产出文件。另一台机器上的另一个 agent 需要看到这些文件——并且**两个 agent 都不应该为此被改写成去调某个存储 API**。

它的一般形态是一个远程文件系统：一份命名空间，权威地保存在服务端，在任意多台机器上呈现为一个普通目录。一个程序写入文件，另一处的程序读到它。两者都不知道对方存在，也都不知道这个文件系统是远程的。

这件事是从 agent workspace 产品里拆出来单独做的，因为这个需求本身跟 agent 无关。值得单独做的理由在于：真正难的那几处——可见延迟、并发访问、以及「像真文件系统到足以让未经修改的工具能跑」——不管写文件的是谁，都是同一批难点。

## 用户

五类。除了第一类，其余都是把我们集成进别的东西里的程序员。

| 用户 | 他们看到什么 | 他们需要我们做到什么 |
|---|---|---|
| **workspace 里运行的程序** | 一个普通目录。它们不知道我们存在。 | 普通的文件操作，行为得像普通的文件操作。 |
| **集成客户端的人** | 一个链接进自家 daemon service 的 package。 | 往一个他们已经拥有的进程里加一个挂载点，而不必因此继承一套进程模型、一个日志去向、或一组信号处理。 |
| **集成服务端的人** | 一个链接进自家 server 的 package。 | 把自家存储发布成可挂载的命名空间，而不必为此多起一个服务。 |
| **SDK 使用者** | 一套编程接口，不挂载。 | 从没有文件系统可挂、或挂载不可用的代码里，读写同一份命名空间。 |
| **运维** | 独立二进制。 | 单独部署它、挂载与卸载 workspace，出问题时能查出是什么问题。 |

## 场景

### S1 —— 跨机器交接

机器 A 上的 agent 往自己的 workspace 里写完一个文件，结束。机器 B 上的 agent 在同一个 workspace 里工作，读到它。

B 必须在 **A 写完后一秒内**观察到这个文件，不靠轮询，也不需要有人告诉它去看。**可见性不得取决于某个时间间隔是否已经走完。**

这是这个系统存在的理由。这条不成立，其余都无所谓。

### S2 —— 在已挂载的 workspace 里干活

一个 agent 在挂载的 workspace 里长时间工作：创建、读取、重写、删除文件，并且**极其频繁地列目录**。

workspace 的行为必须像本地目录到一定程度，使得为本地目录写的工具能不加修改地跑起来。**具体哪些工具必须能跑，目前是一条开放假设——见文末。**

### S3 —— 并发写

两个 agent 同时写。多数时候写的是不同文件，偶尔会写同一个。

写不同文件时**必须完全互不干扰**。写同一个文件时，结果必须是**显式的**：要么某个写者被拦住不让写，要么它被告知自己的写没有生效。

**绝不允许发生的是：两个写者都认为自己成功了，而其中一个的写不见了。**

### S4 —— 冷挂载一个休眠的 workspace

大部分 workspace 并没有被挂载。它们被用过、被卸载，之后就一直躺在服务端——有时躺很久。偶尔某一个会被重新挂载回来。

挂载一个休眠的 workspace，起点是**本地什么状态都没有**。它必须能迅速变得可用，而「可用」的意思是：第一次列目录和头几次读文件不能慢得离谱。一个要花几分钟才能开始干活的 workspace，不会有人愿意挂。

### S5 —— 热 workspace 长期挂着

有一部分 workspace 是持续挂载、被大量使用的。而在**不同** workspace 之间的挂载/卸载切换是频繁且日常的：**挂载不是一次罕见的管理操作。**

### S6 —— 出了问题

服务端连不上；或者一次写入没能保存下来；或者某个 agent 读到的是陈旧内容。

负责的人必须能查出来。并且**故障必须以故障的形式暴露，而不是以一个看起来合理的错误答案的形式**——一个在不知道答案时编一个出来的文件系统，比一个直接停下来的文件系统更糟糕。

### S7 —— 在一台机器上长期保存 workspace

运维只提供一块本地持久磁盘和一个独立 server。server 第一次启动时建立 workspace，之后可以停止、升级、异常退出并重新启动；已经确认成功的文件与目录在重新启动后仍是同一份命名空间，重新挂载和跨机器可见性继续遵守相同保证。

本地持久状态的必要结构若缺失、损坏，或者各部分无法证明属于同一份 workspace，server 必须拒绝启动。对象内容在读取时若无法验证也必须报错。把残存的一部分解释成新的空 workspace，或把无法验证的字节当成文件内容，都会把「数据无法证明」伪装成「数据不存在或仍然正确」。

## 交付什么

五份产物，因为这个系统会以五种方式被使用：

- **客户端 package**，可嵌入既有的 daemon service。
- **服务端 package**，可嵌入既有的 server。
- **SDK**，不挂载的编程式访问。
- **独立服务端二进制**。它随附一个只依赖本机持久存储的 workspace 形态，也能接入其它存储。
- **独立 daemon 与 CLI**，同一个二进制，用参数选择以 daemon 方式运行。它既是可部署形态，也是验证其余部分的手段。

**package 是主要交付物。** 二进制的作用是证明 package 可用，以及在没人想嵌入时把系统跑起来。

## 规模

workspace 在服务端长期存在，间歇性被挂载。存在的很多，同一时刻挂着的很少。

单个 workspace 的体量尚未实测。当前的工作假设是**一棵源码树**——大量小文件，访问以元数据为主——这里把它记为**一条待验证的假设，而不是一个用来设计的数字**。

## 开放假设

以下问题尚未解决。每一条都连同「它决定了什么」一起记下来，好让将来解决它是一个**有意识的动作**，而不是一次意外发现。

### workspace 里到底跑什么

已知：不跑数据库；不要求 SQLite；不要求共享内存映射的一致性。
未知：版本控制工具、包管理器、编译器会不会在里面跑。

这一条决定了系统必须把本地文件系统模仿到多像，而这又决定了后面绝大部分工程量。**它是本文档中最有后果的一个未决问题**，应当靠观察真实 agent 的行为来定，而不是靠猜。

### 同一文件的并发写是否罕见到可以直接失败

S3 只要求结果是显式的。至于「显式」应该是「拦住」还是「事后告知」，取决于它发生得多频繁，以及 agent 拿到这个信息之后能做什么有用的事。这两点目前都不清楚。
