# 问题、用户与场景

## 问题

一个 agent 产出文件。另一台机器上的另一个 agent 需要看到这些文件——并且**两个 agent 都不应该为此被改写成去调某个存储 API**。

**volume 是一份由服务端权威持有的逻辑文件树。** 这个远程文件系统把同一个 volume 在 Linux 上呈现为普通目录，在 Windows 上呈现为系统网络驱动器，也允许通过编程接口访问。一个程序写入文件，另一处的程序读到它。两者都不知道对方存在，也不需要知道这棵文件树的权威状态位于另一台机器。

这件事是从 面向 agent 工作环境的产品里拆出来单独做的，因为这个需求本身跟 agent 无关。值得单独做的理由在于：真正难的那几处——可见延迟、并发访问、以及「像真文件系统到足以让未经修改的工具能跑」——不管写文件的是谁，都是同一批难点。

## 用户

五类。除了第一类，其余都是把我们集成进别的东西里的程序员。

| 用户 | 他们看到什么 | 他们需要我们做到什么 |
|---|---|---|
| **volume 里运行的程序** | Linux 普通目录或 Windows 系统网络驱动器。它们不知道我们存在。 | 用所在平台的普通文件操作访问同一份权威数据。 |
| **集成客户端的人** | 可分别链接进既有 Linux 或 Windows 进程的 package。 | 在自己拥有的进程里提供平台原生的文件访问，由宿主管理生命周期、日志和身份，只承担所选平台的依赖。 |
| **集成服务端的人** | 一个链接进自家 server 的 package。 | 把自家存储发布成可挂载的 volume，为各入口提供同一份权威数据与访问保护，而不必实现客户端平台的文件系统规则或多起一个服务。 |
| **SDK 使用者** | 一套编程接口，不挂载。 | 从没有文件系统可挂、或挂载不可用的代码里，读写同一个 volume。 |
| **运维** | 独立二进制。 | 单独部署它、挂载与卸载 volume，出问题时能查出是什么问题。 |

## 场景

### S1 —— 跨机器交接

机器 A 上的 agent 往自己的 volume 里写完一个文件，结束。机器 B 上的 agent 在同一个 volume 里工作，读到它。

B 必须在 **A 写完后一秒内**观察到这个文件，不靠轮询，也不需要有人告诉它去看。**可见性不得取决于某个时间间隔是否已经走完。**

这是这个系统存在的理由。这条不成立，其余都无所谓。

### S2 —— 在已挂载的 volume 里干活

一个 agent 在挂载的 volume 里长时间工作：创建、读取、重写、删除文件，并且**极其频繁地列目录**。

volume 的行为必须像所在平台的普通文件系统到一定程度，使得为本地目录或网络驱动器写的工具能不加修改地跑起来。已经打开的文件句柄持续访问同一个文件对象：另一个调用方修改它后，后续读取看到新状态；改名、删除名字或替换路径后，原句柄仍指向原对象，不会读写替代物。写入和截断各自在调用中确认结果，程序不必关闭文件才能使修改可见。**具体哪些工具必须能跑，目前是一条开放假设——见文末。**

### S3 —— 并发写

两个 agent 同时工作，多数时候修改不同文件，偶尔会修改同一个。不同文件的写入必须完全互不干扰。普通文件句柄按范围修改文件，重叠部分按实际执行顺序生效，两个调用都可以成功；未触及的部分不能被某个句柄的旧整文件内容覆盖。需要比较原内容是否仍然有效的工作，显式选择独立的版本校验；只有这类提交承诺在依据过期时失败。

Linux 上配合加锁的程序显式使用 flock 或传统 POSIX fcntl 记录锁，按 Linux 的持有者、字节范围和关闭规则取得共享或排他保护。不参与的程序仍可以读写、改名或删除；建议锁本身不提供强制保护。Linux 普通打开不自动取得任何锁。

Windows 程序在打开时声明读、写、删除的共享方式，并能取得共享或排他的字节范围锁。已经生效的限制约束同一 volume 的所有入口；从 Linux 挂载或编程接口发起请求，不能绕过 Windows 已经取得的保护。各平台的锁仍保留自己的持有者、等待、取消和关闭语义，不能互相冒充。

需要阻止不参与者修改的工作，可以使用独立的强 S/X 扩展：先取得稳定占有，再检查同一文件，其内容、存在性与身份在保护期间不变。多个稳定持有者可以并存，稳定权限本身不允许修改；受保护修改需要排他权限。没有强占有冲突的普通修改仍然允许。

保护跟随同一个文件的身份，不能因同名替换转移给别的文件。它有明确的有限期限，长时间上传不能自动延长；修改在最终变更处取得许可时，占有权限仍须有效。占有保护生效后的访问，与识别基于旧内容的写入，分别承担各自的保证。

### S4 —— 冷挂载一个休眠的 volume

大部分 volume 并没有被挂载。它们被用过、被卸载，之后就一直躺在服务端——有时躺很久。偶尔某一个会被重新挂载回来。

挂载一个休眠的 volume，起点是**本地什么状态都没有**。它必须能迅速变得可用，而「可用」的意思是：第一次列目录和头几次读文件不能慢得离谱。一个要花几分钟才能开始干活的 volume，不会有人愿意挂。

### S5 —— 热 volume 长期挂着

有一部分 volume 是持续挂载、被大量使用的。而在**不同** volume 之间的挂载/卸载切换是频繁且日常的：**挂载不是一次罕见的管理操作。**

### S6 —— 出了问题

服务端可能连不上，一次写入可能没能保存，某个 agent 也可能读到陈旧内容。负责排障的人必须能够查明这些故障；系统无法确定答案时，必须报告失败，不能给出一个看起来合理的错误答案。

占有管理也有会丢失的结果。申请或解除的响应丢失时，调用方必须能区分已完成、明确未完成与结果未知。受理动作的授权方仍有效时，调用方能在其明确声明的历史保留期限内核对同一次动作；授权方重启或被隔离后，旧动作明确表现为授权方已退役或结果未知，不会重新执行。取消等待不能证明授权从未生效，失联不能证明此前确认的保护已经解除。

### S7 —— 在一台机器上长期保存 volume

运维提供一块本地持久磁盘和一个独立 server。首次启动建立 volume；之后的停止、升级、异常退出与重启都必须保留已经确认成功的名字、属性与内容，使重新挂载和跨机器访问继续满足相同保证。

已经确认且期限未满的强 S/X 占有也跨越重启。恢复后须维持剩余保护，或在该期间阻止相冲突的授权与修改，不能清空占有状态让另一个写者提前进入。旧远端文件引用失效时必须明确报错，不能用原路径重新打开另一个对象；建议锁失去连续性也不能被静默恢复后当作从未中断。

本地持久状态的必要结构缺失、损坏，或者各部分无法证明属于同一个 volume 时，server 必须拒绝启动；对象内容在读取时无法验证也必须报错。残存部分不能被解释成新的空 volume，无法验证的字节不能被当作合法内容返回。

### S8 —— 从 Windows 系统网络驱动器工作

Windows 11 24H2 及以上客户端中的普通程序和文件管理器，把同一 volume 连接成当前登录会话里的网络驱动器。使用者不安装第三方文件系统驱动、不取得管理员权限，也不改变整台机器的安全或缓存策略。集成方在自己的 Windows 进程中发布和停止访问，选择远端身份，并继续负责业务授权。

Windows 入口支持日常可读写文件树所需的打开、创建、读取、写入、刷新、列目录、目录变更通知、属性查询与修改、改名、替换、删除、共享模式和字节范围锁。Windows 名字无法无歧义地表示 volume 中的内容时，受影响的按名操作整体失败；它不能隐藏一个条目、猜测目标或修改其它入口的名字。已有文件句柄仍按对象身份工作。

同名替换必须保持两个对象的区别。替换前已打开的句柄继续读写旧对象，新打开的句柄取得替代对象，系统报告的文件身份也必须不同。一个句柄承诺的关闭时删除跟随它所打开的对象及目录项，不能在旧名字后来指向新对象时删除替代物。

系统网络驱动器的缓存不能削弱跨机器可见性或错误真实性。另一入口完成的内容、属性和名字变更必须在既定时限内可见；远端状态无法确认时，Windows 操作报告错误，不能用缓存中的旧内容、旧目录或旧的“不存在”回答成功。

默认情况下，只有创建该映射的本地用户与登录会话能够使用它。其它本地身份、匿名访问和完整性无法确认的连接均被拒绝。本机入口也不能绕过远端针对实际 volume、对象与操作作出的授权决定。

## 交付什么

五类产物，因为这个系统会以五种方式被使用：

- **平台客户端 packages**，可分别嵌入既有的 Linux daemon service 或 Windows 客户端进程。
- **服务端 package**，可嵌入既有的 server，为所有入口提供同一份平台中立的远端文件契约。
- **SDK**，不挂载的编程式访问。
- **独立服务端二进制**。它随附一个只依赖本机持久存储的 volume 形态，也能接入其它存储。
- **独立 daemon 与 CLI**，同一个二进制，用参数选择以 daemon 方式运行。它既是可部署形态，也是验证其余部分的手段。

**package 是主要交付物。** 二进制的作用是证明 package 可用，以及在没人想嵌入时把系统跑起来。

## 规模

volume 在服务端长期存在，间歇性被挂载。存在的很多，同一时刻挂着的很少。

单个 volume 的体量尚未实测。当前的工作假设是**一棵源码树**——大量小文件，访问以元数据为主——这里把它记为**一条待验证的假设，而不是一个用来设计的数字**。

## 开放假设

以下问题尚未解决。每一条都连同「它决定了什么」一起记下来，好让将来解决它是一个**有意识的动作**，而不是一次意外发现。

### volume 里到底跑什么

已知：不跑数据库；不要求 SQLite；不要求共享内存映射的一致性。
未知：版本控制工具、包管理器、编译器会不会在里面跑。

这一条决定了系统必须把本地文件系统模仿到多像，而这又决定了后面绝大部分工程量。**它是本文档中最有后果的一个未决问题**，应当靠观察真实 agent 的行为来定，而不是靠猜。

### 显式版本校验如何报告冲突

普通描述符的重叠写入按实际顺序生效，不默认检测调用方的内容依据。显式强占有只保护授予之后的访问，也不能证明取得权限之前读到的内容仍然新鲜。独立版本校验工作流须拒绝过期依据；其冲突由哪个调用报告、调用方如何处理，仍属于 R-CC-4 的未决范围。
