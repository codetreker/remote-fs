# MVP 范围

日期：2026-08-19
状态：**当前迭代**

先把整条链路跑通，再迭代。本文定义「跑通」的确切含义，以及哪些东西**明确不做**。

条目编号（R-…）引用 [`../requirements.md`](../requirements.md)。本文只切分范围，不新增需求——若发现需要一条 `requirements.md` 里没有的需求，先加到那边去。

## 判断什么能推迟的标准

文件系统里，推迟一个**功能**是省事，推迟一个**保证**往往是返工——因为保证通常要靠结构来兑现，而功能可以后加。本文的取舍全部按这条标准做，每一项都注明推迟的代价。

## 范围内

### 功能

单个 workspace 挂载到一个本地目录；读、写、创建、删除、列目录、建目录、删目录、改名、符号链接；卸载。（R-FS-1）

### 保证

这四条是 MVP 的实质内容，功能只是它们的载体。

**G1 —— 跨机器可见性。**（R-CON-1、R-CON-2、R-CON-3、R-CON-4）一台机器上的写入完成并关闭文件后，另一台机器上已挂载同一 workspace 的进程必须在**一秒内**能看到该文件并读到相同内容。可见性不得取决于任何轮询间隔是否走完。

**G2 —— 并发写不静默丢失。**（R-CC-1、R-CC-2）两个进程先后提交对同一文件的修改时，若后者所依据的内容已经不是当前内容，**后者必须失败**。绝不允许两者都认为自己成功而其中一份修改消失。写不同文件必须完全互不干扰。

**G3 —— 故障暴露为故障。**（R-ERR-1、R-ERR-2、R-ERR-5）服务端不可达时，操作以 I/O 错误失败。**不得**返回空目录、不得报告文件不存在、不得返回过期内容而不加说明。无法判定的情况一律按错误处理。

**G4 —— 提交失败不丢数据。**（R-ERR-3、R-ERR-4）一次写入若最终未能保存到服务端，本地已写的内容不得被静默丢弃，且必须有办法查出发生了这件事。

### 交付形态

从第一行代码起就按 package 组织，二进制只是薄壳。（R-INT-1、R-INT-2、R-INT-3、R-INT-4）

- 客户端 package、服务端 package
- 独立 daemon/CLI 二进制（同一个，参数选择 daemon 方式运行）
- 独立服务端二进制

服务端的存储是**可替换的**（R-INT-6）——这是交付要求，因为「集成方接入自有存储」是既定场景。MVP 提供**本地目录**这一种实现，它同时充当验收基准：挂载点的行为可以直接和它底下那个真实目录对拍。

平台仅 Linux（R-INT-8）。

## 范围外

| 不做 | 推迟的代价 | 底线是否已被覆盖 |
|---|---|---|
| **接口鉴权与权限校验** | 低（实现），**但改变部署前提** | 见下 |
| 写锁 / 租约 | 低 | 是。G2 用「提交时校验所依据的版本」即可成立，不需要锁的归属与超时回收 |
| 离线读写与重放 | 低 | 是。G3 要求断线直接失败，语义诚实 |
| 冷挂载性能优化（S4） | 低，纯性能 | 冷挂载**可用**是 MVP 要求，**快**不是 |
| SDK（不挂载的编程接口） | 低 | 形态已在交付要求里，实现推迟 |
| 完整工具链兼容（git / 构建 / 包管理） | **中，取决于写模型** | 见下 |
| 跨平台（macOS / Windows） | 中 | 仅 Linux |
| 缓存跨重启存活 | 低 | — |

### 接口鉴权明确不做

MVP 的服务端接口**不做身份认证，也不做权限校验**。任何能连上服务端的客户端都能读写任何 workspace。（对应 R-INT-7、R-SEC-1、R-SEC-2 暂不覆盖）

这带来两个必须写下来的后果：

**部署前提改变。** MVP **只能跑在可信网络上**——本机、或者受控的内网。它不是一个「安全性稍弱」的版本，而是一个**没有安全边界**的版本。任何把它暴露到不可信网络的部署都是错误使用，文档与启动输出都应当说明这一点，而不是让人从「没配置鉴权」推测出「大概有默认鉴权」。

**多租户问题一并推迟。** 没有身份，就没有「这个 workspace 属于谁」。MVP 里 workspace 之间没有归属关系，也没有隔离。

推迟的实现成本低——鉴权发生在连接建立处，是一个可以后加的环节。但**不得为了省事而假装做了**：不做就一处校验都不写，不留形同虚设的开关，不打印会让人误以为受保护的日志。半个鉴权比没有鉴权更危险，因为它会让部署的人放心。

### 工具链兼容为什么单独说

「workspace 里跑什么」目前是开放假设（见 `problem.md`）。MVP 不承诺 `git`、编译器、包管理器能正常工作。

但这一项和其它推迟项不同：**它对写入模型有约束。** 如果将来需要支持这些工具，改名必须是原子的、文件大小和修改时间必须精确。因此 MVP 虽然不承诺它们能跑，也不得选择一种事后无法兑现这些性质的写入方式。这是本文唯一一条「不做，但不许把路堵死」的条目。

## 验收

MVP 完成的判据。每条都应当能直接写成测试。

| # | 判据 |
|---|---|
| A1 | 机器 A 写入并关闭一个文件后，机器 B 在 1 秒内列目录可见该文件，且读到的内容与 A 写入的一致 |
| A2 | A 与 B 基于同一份内容并发修改同一文件，先提交者成功，后提交者收到失败；文件最终内容是先提交者的，完整无损 |
| A3 | 断开与服务端的连接后，读取一个此前未访问过的文件返回 I/O 错误；列目录返回 I/O 错误而非空列表；访问不存在的路径不得因此变成「存在」或反之 |
| A4 | 令一次提交失败，该次写入的内容仍可被找回，且系统能报告这次失败发生过 |
| A5 | 对挂载点与一个本地目录执行同一串文件操作，产生的目录树、文件内容、以及错误码一致；任何差异必须是本文或 `problem.md` 中明确列出的非目标 |
| A6 | 客户端与服务端 package 可被第三方程序链接：不注册信号处理、不写 stdout/stderr、不调用进程退出、不设置进程级参数 |
| A7 | 一个休眠已久的 workspace 可以被重新挂载并正常读写（不要求快） |
| A8 | 代码中不存在任何形同虚设的鉴权：没有被绕过的校验分支、没有默认放行的开关、没有暗示「已受保护」的日志或输出 |

A5 是其中最有价值的一条：它不需要预先枚举「应该怎样」，而是拿一个真实目录当作标准答案。

A8 是一条反向判据——它要求的是**某种东西不存在**。之所以写成验收条款，是因为「鉴权不做」在实现时最容易退化成「鉴权做了一半」，而后者更危险。

## 迭代顺序（暂定）

MVP 之后按此顺序推进，顺序可随观察到的真实使用情况调整：

1. **鉴权与权限校验**——它决定这东西能不能离开可信网络，因而决定它能不能被真正部署
2. 确定 workspace 里实际运行的工具，据此定下语义等级
3. 工具链兼容所需的语义补齐
4. 冷挂载与元数据密集访问的性能
5. 写锁
6. SDK
7. 跨平台
