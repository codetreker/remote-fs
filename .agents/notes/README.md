# Agent Notes

这里放一种设计文档。一份 **Agent Note** 记录一个影响本仓库的决定或提案 —— **为什么这么定，以及放弃了什么**。这是代码和其它文档承载不了的部分。

## 与 `docs/` 的分工

| 位置 | 承载什么 |
|---|---|
| `docs/spec/` | 系统要做到什么、给谁、为什么。不写怎么实现。 |
| `docs/design/` | 已经定下来的架构。**不写思考过程、不写方案权衡。** |
| `.agents/notes/` | **决定本身**：为什么这么定、比过哪些方案、放弃了什么、什么条件下该重新考虑。 |
| `docs/research/` | 调研证据与引用链。写完即冻结。 |

`docs/design/` 刻意不写权衡，正是因为权衡有这里可放。一个决定进了 design，它的理由和被否的备选留在这里 —— 于是 design 保持可读，而理由不至于丢失到只剩 git 历史。

## 目录与命名

每份 Agent Note 有两个轴，都编码在**路径**里：`{lifecycle}/{class}/yyyy-mm-dd-topic-title.md`

**生命周期**（顶层目录）是这份 note 的状态，note 随状态在目录之间移动：

- **`proposed/`** —— 提案。**用于「暂时不做的将来工作」**；正在做的事不经过这里。
- **`implemented/`** —— 决定已落地。文件记录定了什么、否了什么，并**与实际发生的现实保持同步**：后续代码改了文件位置、包名、默认值，同一次改动里更新这份 note（只更新描述当前系统的事实，不改决定本身，也不改那次决定当时的情形 —— 见「什么时候写」）。
- **`rejected/`** —— 考虑过并否决。只在「它的理由能挡住一个诱人且有意义的错误」时保留，否则整份删掉。
- **`archived/`** —— 已落地且其理由不太可能再指导将来工作的记录，冻结存放（见下）。

**分类**（第二层目录）是决定的**种类**，见下节。

文件名里的日期是这个话题**首次被提出**的日期，不是最后修改日期。note 在生命周期目录之间移动时，日期不变。

Note 之间互相引用**一律用相对 markdown 链接**（形如 `[话题]` 后接圆括号包住 `../architecture/2026-08-19-topic.md` 这样的相对路径），不用散文描述、不用编号 —— 这样引用可被机械检查，且能在文件移动后被修复。

**不建集中索引文件。** 目录树本身就是清单，索引只会与现实漂移。

## 分类

| 分类 | 覆盖什么 |
|---|---|
| `feature` | 一项新的、面向使用者或面向模型的能力 |
| `bug-fix` | 修正一个缺陷，或补上一次事后复盘暴露的缺口 |
| `simplification` | 删掉代码、行为或暴露面，不增加能力 |
| `architecture` | 关于**已交付源码**的结构性决定 —— 包之间如何关联、运行时词汇是什么 |
| `process` | 代码**周边**的工具、政策或工作流 —— 门禁、包管理、依赖引入 —— 不是运行时行为 |
| `testing` | 测试基础设施与策略 |

`architecture` 与 `process` 的分界：**architecture 关于我们交付的源码；process 关于围绕它的工具与工作流。**

`refactor` 刻意缺席 —— 它与 `simplification` 重叠，而后者的判据「可观察行为是否改变」已经覆盖了它。

## 归档与删除

**归档**一份 implemented note，条件是：已落地的决定已经完成，且它的理由不太可能再指导将来的工作。

**保持活跃**的条件是：它的备选方案、归属边界、否定性保证、持久或线上语义、安全规则、或者「什么条件下该重新引入」仍然有用。

**永远不归档一份 proposed note** —— 一个过时的提案应当被否决，而不是被归档。

**rejected note** 只在它还能挡住一个可能被再次提出的错误时保留，否则删掉。

归档后的 note **永久冻结**：不编辑、不重排、不更新、不移动、不删除，也不得把它当作当前行为的依据。活跃的文档仍可有意引用一份归档 note 来指向历史。

## 什么时候写

**任何非平凡改动都必须在同一个 PR 里新增或更新至少一份 Agent Note。** 非平凡的判据：改变了行为、架构、跨文件或跨包共享的契约、流程或工具、测试策略、磁盘/线上/配置格式，或任何一个维护者将来可能合理地想重新考虑的决定。

**为将来的实质性工作写的提案放进 `proposed/`；已经做出的决定直接放进 `implemented/`。** 正在做的事不必先经过 `proposed/`。

更新已经拥有该决定的那份 note 就够了，不要新建重复的。只有纯机械或纯局部、不改变行为/契约/结构/流程/理由的修改可以豁免。

**一份 Agent Note 永远不会被改写成另一个决定。** 决定变了就新写一份，并让两份互相链接。把旧 note 就地改成它的反面，会让「我们当时为什么那样想」永久消失。

**「保持同步」只针对描述当前系统的那些句子。** 一份 implemented note 里有两种句子：一种说系统现在是什么样 —— 文件在哪、包叫什么、默认值多少、行为如何 —— 代码搬动了就在同一次改动里跟着改；另一种说那次决定当时的情形 —— 当时有多少条需求、权衡过哪些方案、交付了什么、代价是什么 —— 它属于那个时刻，不因今天的现实而变。分辨只需问一句：**它说的是系统，还是那次决定？**

后一种与今天矛盾时，**加交叉链接，不动原句**。把「当时拒绝了 X」改写成「现在做了 X」，看上去是在同步事实，抹掉的却是当时拒绝的理由 —— 而那个理由往往仍然成立，新方案照样得绕开它。

## 文件格式

### 头部

前三行固定：

```markdown
# Agent Note: <标题>

Status: <状态>
```

`Status:` 的取值必须与所在的生命周期目录一致：

- `Status: proposed`
- `Status: implemented`
- `Status: rejected —— <一句话说明为什么>`

状态行不带日期、不带括注 —— 日期在文件名里，其余在 git 里。否决理由是唯一带内容的状态，因为那是读者来看这份 note 的原因。

### 正文骨架

每份 note 都以 `## 问题` 开篇 —— 动机，且**要写到脱离解法也能独立成立**。之后按生命周期不同。固定小节用下列名字，除此之外确实需要的技术小节可以自由插在它们之间。

**`proposed/`**
```markdown
## 问题
## 提案
…按需的技术小节…
## 备选方案
## 验收标准
## 风险
```

`## 提案` 是打算做的改动，可以用将来时。`## 验收标准` 说清什么可观察的状态算做完。`## 风险` 同时覆盖「可能出什么问题」和「这个改动明知要放弃什么」。

**`implemented/`**
```markdown
## 问题
## 决定
…按需的技术小节…
## 备选方案
## 后果
```

`## 决定` 用**现在时**描述已发生的现实。`## 后果` 记录这个取舍**付出了什么、也买到了什么**。提案期的小节（`## 提案`、`## 计划`、`## 验收标准`）不得出现在 implemented note 里。

**`rejected/`** —— 就是被冻结的提案原样，保留它当时有的小节，判决写在 `Status:` 行上。

### 「备选方案」是强制的

每份 Agent Note 都必须有 `## 备选方案`：**每一个真实考虑过的备选，以及它为什么输了。**

一个只记录了结论、没记录它打败了什么的决定，就是在邀请别人重新争论一遍 —— 而这正是 Agent Note 存在的理由。

**备选方案是记录，不是编造。** 如果当时确实没有比较过别的方案，就写「没有考虑过其它方案」，不要为了填满这一节而虚构。

### 在生命周期之间移动

移动文件的同时必须改 `Status:` 行并满足目标目录的骨架。

`proposed/` → `implemented/`：把 `## 提案` 改写成现在时的 `## 决定`，把 `## 验收标准` 与 `## 风险` 收进 `## 后果`，删掉计划、只留实际发生的事。

`proposed/` → `rejected/`：只在 `Status:` 行补上理由，然后冻结文件。

## 语言

中文，与 `docs/spec/`、`docs/design/` 一致 —— 这些是要被反复阅读和争论的文档。可夹用英文术语。
