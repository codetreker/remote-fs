# Agent Note: 暂存预算与失败写入的销账

Status: proposed

## 问题

R-ERR-3 要求：系统若持有已经由本地接口接受、尚未得到服务端确认的内容，不得静默丢弃，且必须能查出该状态。R-INT-3 又要求累积资源有可配置上限。这两项义务必须一起成立。

[实时文件句柄](../../implemented/architecture/2026-09-08-live-file-handles.md)逐次同步确认普通 WriteAt 与 Truncate，不在 handle 或节点里保存 dirty 内容。一次同步调用失败或结果未知就在该调用中报告；它不自动生成本地持久暂存清单。本文保留未来确实接受而未确认内容时的预算、查询与销账机制，不能将它描述成当前普通写入的隐藏重试路径。

原提案面对的是关闭时提交、失败后保留的路径。如果只提供保留与列出、没有清偿操作，就会出现：

- 禁止丢弃；
- 不重试，所以没有任何东西会自动排空它；
- 控制通道**只列出**失败的写入，**没有任何操作能销账**。

于是保留的暂存内容是单调增长、不可删除、躺在别人进程里的磁盘数据。到达上限时三种行为全错：

| 到达上限时 | 后果 |
|---|---|
| 丢弃最旧的保留内容 | 直接违反 R-ERR-3，而且是静默的 —— 正是 R-ERR-3 存在的理由 |
| 拒绝新写入 | 设计里没写。且一次没人注意到的失败提交最终会把挂载点堵死 |
| 让保留内容不计入上限 | 违反 R-INT-3 |

**清单的名字也不能断言客户端不知道的事。** 一次因网络错误而失败的提交可能已在服务端成功，必须报告结果未知。若系统确实保留了已接受的内容，清单不能一律叫「未保存的写入」；其中部分条目可能已经提交。

## 提案

### 预算拆成两份，因为这是两种性质相反的东西

以下机制只适用于明确提供本地暂存或接受后异步确认的形态；引入它须同时说明哪些内容可以从服务端重建、哪些内容只能从本地保留。

| | 在途暂存 | 保留的失败内容 |
|---|---|---|
| 性质 | **缓存** —— 可以从服务端重新取回 | **数据** —— 不可重建 |
| 可驱逐 | 是 | **否** |
| 上限 | 软上限，超出即驱逐 | **硬预算** |
| 耗尽时 | 驱逐最久未用 | **以「设备空间不足」拒绝新写入** |

两份预算**分开计量**。把它们放进同一个池子，就必然要在「丢数据」和「堵死」之间二选一。

耗尽硬预算时拒绝**新写入**，而不是驱逐**已保留的** —— 这是唯一同时满足两条需求的行为。它也是诚实的：磁盘满了本来就会产生同样的错误，是每个程序都已经处理的情况。

### 控制通道提供销账操作

清单必须有出口。三个操作：

- **取出** —— 把保留的内容取到指定路径，不改变保留状态
- **销账** —— 确认放弃，删除保留内容
- **重新提交** —— 由调用方明确选择版本化工作流，以核对后的远端版本为前置条件重新提交，不匹配则拒绝

第三个必须带版本校验。否则一个好意的运维人员重放一条旧条目，就覆盖掉了之后所有更新的版本。

### 清单叫「未确认的写入」

因为「未保存」是一个客户端无法证实的断言。

条目里必须写明它是哪一类：

- **确定失败** —— 服务端明确拒绝（版本不符、权限、空间）
- **结果未知** —— 网络错误、超时；服务端可能已经提交

两类的处置不同。「结果未知」的条目在重新提交前应当先查当前版本，而这正是版本校验重提交所做的事。

### 保留内容的位置、权限与寿命

- 位置：仅所有者可进入的目录，**绝不放在他人可预先占位的公共路径下**（R-SEC-3）
- 权限：仅所有者可读 —— 它是远端文件的明文内容
- 寿命：**跨卸载与进程重启存活**，直到显式销账。R-WS-3 允许没有本地状态时冷挂载，不授权清除另行接受的未确认内容；引入暂存的形态必须明确这项持久责任。

## 备选方案

**单一预算，到达上限时驱逐最旧的保留内容。** 最简单，永远不会堵死。输在它就是 R-ERR-3 禁止的那件事，且是静默地做。

**单一预算，到达上限时拒绝一切写入。** 不丢数据。输在它让在途暂存（可重建的缓存）与保留内容（不可重建的数据）争抢同一份配额 —— 一次大文件写入会因为几条陈年失败条目而被拒。两种性质相反的东西不该共用配额。

**自动重试失败的提交，让池子自己排空。** 消掉了「没有出路」这个问题。输在它隐含了一个我们并未做出的持久化承诺：应用会开始依赖「写了就会到」，而这正是设计明确拒绝的（那属于离线能力，且半成品比没有更危险）。

**不保留，提交失败即丢弃，只把错误返回给 `close()`。** 这是原来考虑过的形态。它先接受本地写入，再把失败推迟到常被忽略的 close，因而会静默丢失已接受内容。当前同步写穿在原 WriteAt / Truncate 中报告失败，未采用这个先成功后丢弃的方案；若未来重新引入未确认本地状态，这条反对理由仍成立。

**保留内容不落磁盘，只在内存里。** 不涉及磁盘权限与位置问题。输在进程重启即丢失，而失败提交常常与进程异常同时发生。

## 验收标准

- 两份预算在文档里分别命名、分别配置、分别计量。
- 硬预算耗尽时拒绝新写入，且返回的是「设备空间不足」这一类错误。
- 控制通道有取出、销账、重新提交三个操作，且重新提交带版本校验。
- 清单叫「未确认的写入」，条目区分「确定失败」与「结果未知」。
- 保留内容的位置与权限满足 R-SEC-3，且跨卸载与重启的责任被明确记录，不以冷挂载能力作为自动清除的依据。
- R-ERR-4（运行中的系统必须能被查询）由**库**满足，而不是只由控制通道满足 —— 嵌入我们的集成方不会运行我们的控制通道。

## 风险

**「拒绝新写入」意味着一次未被注意的失败最终会让挂载点不可写。** 这是刻意的：它把静默的数据丢失换成了响亮的、不可忽视的故障。但它要求运维确实会看到告警 —— 若无人查看清单，用户体验是「某天开始写不进去了」。这条依赖 R-ERR-4 的可观测性真正可用。

**版本校验的重新提交在「结果未知」条目上仍可能出错。** 若服务端其实已提交成功，当前版本就是那次提交的结果，重新提交会因版本不符而被拒 —— 这是正确的，但运维看到的是「重提失败」，而真相是「本来就成功了」。区分这两者需要比较内容，本 note 不提供。

**跨重启存活意味着有一份需要被管理的磁盘状态。** 对嵌入式集成方（R-INT-1）而言，这是我们在他们进程里留下的持久痕迹。位置必须可配置，且必须能被他们的备份与清理策略看见。
