# Agent Note: 对象存储后端已知没做的事

Status: proposed

## 问题

[把命名空间放进对象存储](../../implemented/architecture/2026-08-21-namespace-in-an-object-store.md)通过了完整的契约套件，也就是说它在契约测得到的地方都是对的。契约测不到的地方有一批已知的缺口，它们都不是「还没想到」，而是「想到了，这一版不做」。

写下来的理由只有一个：一个没有记录的缺口和一个不存在的缺口，在下一个人读代码时长得一模一样。而这些缺口里有几条，看起来像是已经处理过了。

## 提案

以下每一条都还没做。列在这里是为了让它们各自可以被单独排期，也为了让任何一条被当作「已经有了」时能被立刻否掉。

**没有任何长度上限。** `ENAMETOOLONG` 在 errno 词汇表里，而这个后端从不产生它。一个名字可以有一兆字节，一条路径可以有任意深——而路径解析是每一层一次查询，所以深度直接变成一次调用里的查询次数。`localdir` 靠内核替它拒绝，这里没有内核。

**用量计数一旦出错就没有回头路。** 计数由每一次改变大小的事务维护，构造上是精确的。但 `Space` 在数字不自洽时报 `EIO` 而不是把它夹回合理范围——这是对的，编造一个数字比报错更糟——代价是任何让计数出错的东西（缺陷、部分恢复、手改过的行）会让 `Space` 永久失败，而且没有任何带内的修复手段。`limited` 有 `Recount`，这里没有对应物。

**一次超时之后落地的写入没有重试的说法。** `Put` 超时但对象其实存下了，重试会撞上 `EEXIST`，而代码里那句注释说这意味着「上游出了问题」。它不意味着。

**`ResourceNotFound` 归类未定。** 它现在落进默认的 `EIO`，理由是它既可能是对象真的不在，也可能是账户不在——按「判定不了」处理是安全的方向。代价是：如果它其实表示一次确定的缺席，清扫器会对着它永远重试。

**从未对着真的 Azure 跑过。** 所有验证都在 Azurite 上。摘要那件事就是一个例子：Azurite 只在写入响应里给 `Content-MD5`，而真的 Azure 从 2019-02-02 起还会给 `x-ms-content-crc64`——这个差异是从文档读来的，不是测出来的。

**SDK 的版本被 Azurite 钉住。** azblob 停在一个较旧的版本，唯一原因是当前最新的 Azurite 拒绝更新的 SDK 送出的 `x-ms-version`。升 SDK 要先等 Azurite，而不是改一个请求头。

**跨进程加锁没有被测过。** `busy_timeout` 配了但没有任何用例走到它——并发用例是一个进程里的两个连接池，不是两个进程。

**只有 schema v1。** 拒绝不认识的版本这条路径测过了；升级那条路径不存在，也没有任何东西证明它写得出来。

**`Garbage` 的排序跨了两个状态的 OR**，所以 SQLite 会把整个匹配集排一遍而不是走 `objects_by_state` 索引。在一个清扫批次的量级上无所谓，在一个攒了大量垃圾的命名空间上不是。

**`Sweep` 里那条「只删掉了一部分就收手」的分支到不了。** `discard` 只在 `break` 处提前退出循环，而那一处必定同时置上 `failure`，于是 `len(gone) < len(keys)` 蕴含 `err != nil`，`Sweep` 在检查 `gone < len(keys)` 之前就已经带着那个错误返回了。它要么该删掉，要么 `discard` 的契约该改成「可以不带错误地只完成一部分」，并配一个真的走到那条路的用例。

## 备选方案

**逐条各开一份 note。** 更合仓库的习惯——一份 note 一个决定。输在这九条共享同一个决定（原型阶段先不做），拆开会让那个共同的理由重复九遍，也会让「它们是一起被权衡的」这件事消失。

**不写，等它们变成问题时再说。** 输在其中几条会先以别的面目出现：一个永远失败的 `Space` 看起来像损坏的数据库，一次 `EEXIST` 看起来像并发缺陷。

## 验收标准

每一条被单独处理掉，或者被显式地判为不需要处理。这份 note 在最后一条被处理之后否决或删除，而不是留着慢慢腐烂。

## 风险

**这份清单会被当成完整的。** 它不是——它是已知的那些。契约套件覆盖不到的地方还有多少未知，这份 note 答不了。
