# Agent Note: 打开之后没有任何东西把文件钉住

Status: proposed

## 问题

本地 `open(2)` 交出的描述符钉在一个 inode 上。此后这个程序做的每一件事都落在它打开的那个对象上，名字发生什么都不影响：名字被删掉，读写照常；另一个文件被改名盖到这个名字上，读写仍然落在原来那个对象上。

这个挂载点没有对应的东西。`storage.Storage` 的每个操作都以路径寻址，各自独立解析。一次打开因此是对同一个字符串的两次互不相干的解析：

```
Open   →  storage.Read(P)      整个文件进入这个描述符的缓冲区
   …      另一个客户端把别的东西改名到 P …
Flush  →  storage.Write(P)     缓冲区落到此刻位于 P 的那个对象上
```

两次调用之间没有任何东西把它们绑在同一个对象上。写落到另一个文件上，静默地，原本在那里的内容没有了。

这在已交付的系统里，不是假设，也不是新出现的。它一直没有被单独写下来，是因为每次被提到时都被当成别的问题的症状。

### 挂载层确实钉了一下，钉的强度正好是它脚下那棵树

[挂载层](../../implemented/process/2026-08-19-mvp-scope.md)提交时用的不是打开时记住的路径，而是当场从 inode 树上读回来的路径（`node.path()` 即 `Inode.Path(Root())`）。改名走这个挂载点时，go-fuse 在我们的 `Rename` 返回 0 之后把子 inode 挂到新名字下（[`rawBridge.Rename` 里的 `MvChild`](https://github.com/hanwen/go-fuse/blob/423b377e1452ab7b3522229185a3047f72e3f966/fs/bridge.go#L610-L627)），于是提交时读到的是新路径，写跟着文件走 —— `TestAnOpenHandleFollowsItsFileThroughARename` 守着这一条。

所以钉子是有的，而它盖住的范围正好是**本进程自己做过的改名**。别的客户端做的改名、直接对后端命名空间做的改名，都不移动这棵树里的任何东西；提交于是去解析一个已经属于别人的名字。这个系统存在的理由就是不止一台机器用同一份命名空间，所以这个盖住的范围等于没盖。

### 挂载层的身份与读写范围

[名字不是身份](../../implemented/bug-fix/2026-09-01-a-name-is-not-an-identity.md)为路径查询引入节点身份，并在 handle 的路径身份改变时保留缓冲区长度；提交仍按路径寻址。

这个挂载点有一份真正的身份记录，它不是路径的函数：`packages/fuse/identity.go` 是一棵名字树，号取自一个只增、永不复用的计数器，改名时号跟着节点走，在腾出来的名字上新建的节点拿一个新号。这套东西是**专门为了把节点分开**才建的——用路径哈希当号会让 `git init` 死在 SIGBUS 上。

这份 note 当时的论点是：这棵树只记**这个挂载点看到过的**名字，别的客户端做的改名它没看见，于是 `children["P"]` 还在、种类也对得上，下一次 `Lookup` 交回同一份身份、同一个 `st_ino`；`keepOnly` 只发现**已经消失的**名字，发现不了一个还在、却已经指着另一个东西的名字。当时由此推出的最强结论是「分辨节点的机器已经造好了，而且是为分辨节点专门造的，它照样看不见这件事——缺的不是编号机制，是那个事件根本不到达」。

命名空间通过每次 `Stat` 报告这个名字后面的节点身份。`identity.child` 比对名字、种类与 `storage.Attr.ID`，发现身份变化时分配另一个 inode 号，不依赖事件到达。身份可能被宿主复用的 `localdir` 仍有漏判边界；同身份覆写也不会触发干净 handle 的长度覆盖，见[缓冲内容与长度绑定](../bug-fix/2026-09-07-bind-buffered-reads-to-their-size.md)。默认内核页缓存还可能把旧 handle 的内容交给新 open，见[跨句柄页缓存陈旧](../bug-fix/2026-09-07-prevent-cross-handle-page-cache-staleness.md)。身份比较不能证明完整的读侧保证已经成立。

**本 note 拥有写侧的问题**：提交仍然落在**名字**上而不是落在描述符打开的那个节点上，所以下一节说的毁数据一条不少。读侧的身份比较、长度与页缓存修复，都不会让一次提交知道自己该写去哪里。

### 写侧毁数据，读侧骗人

**写侧。** 缓冲区落到此刻位于 P 的对象上，那里原有的内容被替换，没有人被告知。而且 `storage.Write` 的契约是「文件不在则创建」：别的客户端把 P 删掉了，提交不会失败，它把 P 重新造出来，内容是某个程序在很早之前读到的那份字节。本地 `open` 之后 `unlink`，写进去的数据随最后一个引用消失；这里它在那个名字上复活。

**读侧持有打开时的内容。** 到达 `handle.Read` 的调用从缓冲区切片，内核也能直接从文件页缓存作答。读取完整旧版本与写入错对象是不同的问题；长度混用与跨句柄页缓存由上述两份缺陷提案处理，本提案继续约束提交的目标与依据。

### 同一个名字被解析几次，就有几次落错的机会

open 到 close 只是最长的那一段。已交付的挂载层里，一次系统调用经常是好几次独立解析：

| 触发 | 解析序列 | 中途换了对象会怎样 |
|---|---|---|
| `open(2)` 到 `close(2)` | `Read` … `Write` | 写落在另一个对象上 |
| `open(2)` 本身 | `Stat` → `Read` | 按 A 的大小判定装不装得下，取回 B |
| `truncate(2)` 到非零长度 | `Stat` → `Read` → `Write` | 一次读-改-写，B 被写成 A 的前缀 |
| `creat(2)` | `Create` → `SetAttr` → `Stat` | 权限位落在另一个对象上 |
| `utimensat(2)`，且有未提交内容 | `Write` → `SetAttr` | 时间戳落在另一个对象上 |

`truncate(2)` 那一行值得单独看：**一次系统调用触发一次完整的读-改-写，中间什么都没有被持有。** 它不需要任何人打开过文件，也不需要两个写者。

## 边界：这不是相邻三份提案里的任何一个

**不是「一次写会话产生 N 次提交」。** [写会话的定义与稀疏暂存](2026-08-19-write-session-and-staging.md)处理的是描述符被复制之后关闭事件发生 N 次，于是第 2 到第 N 次提交带着已作废的版本报出假错误。那里的问题是**提交发生几次**；这里的问题是**一次提交落在哪个对象上**。把提交收敛到恰好一次，那一次仍然是不钉的。

**不是定序。** [变更定序与版本语义](2026-08-19-ordering-and-versions.md)问的是「一个响应携带的位置从哪来」，要保证本地视图不被旧数据推回去。那是关于**视图的时间**的问题。即使位置永远正确，`storage.Write(P)` 寻址的仍然是 P。

**不是不透明节点身份解决的。** [storage 契约的操作词汇](2026-08-19-storage-operation-vocabulary.md)里有一句「改名与查询交错时键不会指向错误的对象」，读起来正像本 note 的问题，所以这一条要分得最清楚。

身份**命名**一个对象，它不**持有**一个对象。换成身份寻址之后，提交发向的是打开时拿到的那个 id：要么落在打开的那个对象上，要么因为那个 id 已经不在而失败。**从静默写错变成报错，这是很大的改善，但它是寻址方式的副产品，不是一个钉子。** 身份之外仍然缺两件事：

- 打开期间那个对象**自己**被改掉了，身份一无所知 —— A 读 id X、B 提交到 id X、A 提交到 id X，A 赢，B 的修改静默消失。这是 R-CC-1 说的那件事，与名字无关。
- 读侧完全不受影响：缓冲区是用打开那一刻的字节填的，身份不会让它跟上。

所以身份是必要的，不是充分的。本提案在它落地之前与之后都成立，两者相加才是终局形态（见下面对内容派生版本的那条风险）。

## 提案

### 提交携带所依据的版本

`storage` 的提交操作多一个参数：调用方所依据的版本。目标当前的版本与它不符时，提交被拒绝，不写入任何东西。

**版本不持有任何对象，它只保证「没被持有」这件事一定会被发现。** 一次提交要么落在它打开的那个东西上，要么失败；这份 note 里全部静默的破坏因此变成一个错误。

一个检查同时覆盖四种情形，而这四种一直被分开谈：

| 打开期间发生了什么 | 当前版本 | 提交 |
|---|---|---|
| 另一个对象被改名到这个名字上 | 不是所依据的那个 | 拒绝 |
| 这个名字上的对象被删掉 | 不存在 | 拒绝，而不是把它重新造出来 |
| 这个对象自己被别的客户端改了 | 不是所依据的那个 | 拒绝（R-CC-1） |
| 什么都没发生 | 相同 | 落在它打开的那个对象上 |

新建的文件没有「之前的版本」可以依据，所以版本参数需要一个专门取值表示「打开时这里什么都没有」；带着它提交，等价于 `Create` 的前置条件，目标已存在则 `EEXIST`。没有这个取值的话，「创建」就只能退回成一次无条件覆盖，而那正是要消掉的东西。

### 版本在挂载层有地方放

[范围决定](../../implemented/process/2026-08-19-mvp-scope.md)当时否掉这条，理由之一是「版本一旦进了 `Write` 的参数，它上面的每一层都要记住并传递它」。挂载层现在已经交付，那句话的实际大小可以直接从代码上读出来：`packages/fuse` 的 `handle` 已经持有打开时刻取回的内容，版本与它同源、同生命周期，多一个字段而已。有描述符的路径就只有这一处。

没有描述符的路径要自己制造依据，它们是真正多出来的工作：

- `truncate(2)` 到非零长度的那次读-改-写，在它自己的 `Stat`／`Read` 上取版本，提交时带上；
- `Setattr` 里「先把未提交内容写出去、再改属性」的那一步，两次调用之间同样没有钉子。

这两处都没有一个打开的 handle 可以直接保存依据，必须各自携带版本。三个元数据超时为 0 不关闭文件页缓存，也不能用来证明全部内核调用都会进入挂载层。

属性变更本身要不要带版本，本 note 不定：它毁不掉内容，而且内核把模式与时间分成两次请求发过来，两次之间本来就没有原子性可言。

### 什么变了，值得反转一条记录在案的决定

范围决定明确把乐观并发校验切了出去，本提案是把它请回来的一半，所以要说清楚新出现的是什么。

**当时的第二条理由是「它挡的是并发写同一个文件这个小概率事件，属于边界情况」。** 这份 note 的全部内容就是同一个检查还挡另一件事，而那件事不是并发写同一个文件：触发它的是**别人对一个不相干的名字做的改名或删除**，受害者是一个从头到尾只碰自己那个文件的程序。而「把一个对象改名盖到一个名字上」正是原子保存的标准写法 —— 写临时文件、改名盖过去 —— 编辑器、构建工具、`sed -i`、`rsync` 每天都在做。那条「小概率的边界情况」的判断只对它当时看着的那一半成立。

**当时的第一条理由是传递成本，那是在挂载层存在之前估的。** 现在能看到实际形状：一个字段，加上两处没有描述符的读-改-写。

### 第三方实现者要付什么（R-INT-6）

沿用[定序与版本](2026-08-19-ordering-and-versions.md)的取值：版本不透明、仅可比等。本 note 再加两条义务：

- **内容改变时版本必须改变。** 否则这个检查什么都挡不住。
- **比较与写入不可分割。** 一个用「读版本 → 比较 → 写」实现的存储满足契约的字面意思，却静默作废整份提案。我们验证不了这一点，只能把它写成实现者的担保 —— 定序那份 note 已经记下同一条风险，这里让它落到一个具体操作上。

令牌本身几乎不要钱：ETag、代数、内容哈希、`mtime`+size 都可以，只要满足上面第一条。要钱的是那个不可分割。对象存储普遍有条件写（S3 的 `If-Match`）；一个普通目录没有，`localdir` 只能用进程内的每路径互斥，那覆盖的正好是 `localdir` 承诺的范围（一个进程看着一个目录），同一个目录被两个进程各挂一次时它不成立。

与句柄比，这个门槛低一个量级：句柄要实现者维护打开状态、它的生命周期、以及一个客户端死了之后谁来收尸。R-INT-6 在此前每一次契约决定里都是决定性的（版本不可比序、区间写推迟，都是被它挡下来的），这一次也是它做的决定。

### 句柄不是被否掉，是被排在后面

R-CC-3 要一种「写之前排他占有文件」的手段，那件事非句柄形状不可 —— 占有检测不出来，只能持有。所以句柄迟早要来，两者不冲突，分工是清楚的：

- 占有是**可用性**机制，它让冲突尽量不发生；
- 版本校验是**正确性**机制，它保证冲突发生了一定被发现。

占有是会丢的：客户端死了、租约到期、实现者的收尸策略与我们设想的不同。丢掉之后剩下的只有版本校验。所以版本校验是地板，句柄是地板之上减少踩空次数的东西 —— 先做地板。

### 读侧本提案不解决

提交带版本让**写**发现对象换了，不让**读**发现。一个打开着文件不写、只反复读的程序，仍然读的是打开那一刻的字节。读侧的答案是缓存加变更流（[观察源独立成契约](2026-08-19-observation-source-and-channels.md)），它与本提案在不同的位置，且它要先有一条变更流才成立。写侧不能等它 —— 写侧毁数据。

## 备选方案

**句柄：`Open` 交出一个东西，操作都拿着它，`Close` 释放它。** POSIX 的文件描述符、9P 的 FID、NFSv4 的 open 都是这个东西，而且它是两个候选里**唯一真正的钉子** —— 别的都只是让落错被发现。它还顺带能回答另外两件事：服务端有了一个可以挂东西的位置，于是 R-CC-3 的排他占有有地方放，读侧的失效通知也有地方投递。输在它要服务端持有打开状态，以及持有状态附带的一整套东西：生命周期、客户端死掉之后的泄漏与收尸、以及一个会话概念 —— 而「一次请求就是一次完整的操作。没有会话、没有句柄，两次请求之间不留任何东西」是[服务端架构](../../../../docs/design/server/architecture.md)刻意选的形状。压垮它的是 R-INT-6：把打开状态的生命周期与崩溃恢复写进契约，等于要求每一个接入自有存储的第三方都实现一遍租约。它没有死，见上面「句柄不是被否掉，是被排在后面」。

**只上不透明节点身份，不加版本校验。** [storage 契约的操作词汇](2026-08-19-storage-operation-vocabulary.md)已经提了身份，而且身份让提交寻址一个对象而不是一个名字，静默写错因此变成报错。输在它只覆盖「名字下面换了对象」，覆盖不了「对象自己被改了」（R-CC-1 原样成立），也覆盖不了读侧。它不是本提案的竞争者，是它的另一半。

**提交前再 `Stat` 一次，比较大小与修改时间。** 一行契约都不用改，挂载层自己就能做。输在它是一个自带窗口的检查：`Stat` 与 `Write` 之间正是本 note 说的那种缝，而且 `mtime` 的粒度让同一个时间戳刻度内的两次改动无法区分。它买到的是一个更小的窗口，代价是让人以为窗口关上了 —— 比知道它开着更糟。

**接受它，把它作为已知语义写进文档。** 范围决定已经接受了「后写者赢，先写者的内容消失」，本 note 只是把这句话的范围扩大。输在两句话不是同一件事：「后写者赢」讲的是同一个对象上的取舍，使用者理解得了、也规避得了（不并发写同一个文件）；「写到另一个对象上」没有任何可规避的前提，触发条件在受害者看不见的地方。

**挂载层维护一份「名字 → 对象」的本地视图，靠变更流失效它。** 将来做缓存与变更推送时这份视图无论如何都要有，改名事件到达时挂载层就知道 P 换了对象，可以拒绝或者改投。输在它把正确性押在一条通知按时到达上：客户端落后、断线、或者根本没有事件源（挂一份 `localdir` 时就没有）时，它什么都不保护。变更流能减少版本校验被触发的次数，替代不了它。

## 验收标准

- `storage` 的提交操作带上「所依据的版本」，并有一个专门取值表示「打开时这里什么都没有」。
- 契约文档写明版本不符时提交被拒绝，且这个拒绝与「不存在」「无法判定」三者相互可分（R-ERR-1、R-ERR-2）。
- 契约文档写明实现者的两条义务：内容改变时版本必须改变；比较与写入不可分割，且这一条我们验证不了、只能由实现者担保。
- `packages/fuse` 的 `handle` 记住打开时取到的版本，提交时带上；被拒绝时向发起者报错，不重试、不静默覆盖。
- 没有描述符的两条读-改-写路径（`truncate(2)` 到非零长度、`Setattr` 里先提交再改属性）在自己那次读所取到的版本上提交。
- `storagetest` 有用例覆盖：所依据的版本已不是当前版本时提交被拒绝；两个并发提交只有一个成功（R-CC-1）；带「什么都没有」提交而目标已存在时 `EEXIST`。
- 有一个用例覆盖本 note 的问题本身：打开 P、把另一个对象改名到 P、提交被拒绝，且 P 上的内容没有被动过。
- 范围决定里「`Write` 携带调用方所依据的版本」那条备选方案指得到本 note —— 那条决定在此被反转，两份必须互相指得到。

## 风险

**这里定的是拒绝，不是拒绝以什么面目出现在系统调用上。** R-CC-4 就是这一条，它是【未决】。`ESTALE`（NFS 对一个失效的 file handle 报的正是它）是显然的候选，但选它要有依据，本 note 不替 R-CC-4 做决定。在它定下来之前，挂载层报什么错都是临时的。

**内容派生的版本认不出两个内容相同的对象。** 版本是内容哈希时，检查退化成「这个名字上的字节还是我读到的字节」，而不是「这还是我打开的那个对象」。一个内容相同的对象被改名盖过来时提交会通过 —— 那一刀毁掉的字节与我们本来就要覆盖的字节相同，所以损失是有界的，但「落在打开的那个对象上」这句话在这种实现下不严格成立。要它严格成立，需要不透明节点身份，两者相加才是终局形态。

**`localdir` 上「比较与写入不可分割」没有系统调用可以直接依靠。** 进程内的每路径互斥覆盖它承诺的范围；同一个目录被两个进程各挂一次时不成立。这与[定序与版本](2026-08-19-ordering-and-versions.md)记下的是同一个风险，本提案把它从「第三方可能做不到」变成「我们自己的实现在一种部署下也做不到」，因此它必须被写进 `localdir` 的文档，而不是只写进契约。

**拒绝会变多，其中一部分是无害的拒绝。** 另一个客户端提交了完全相同的内容，版本仍然变了，我们仍然拒绝。这是刻意的：版本仅可比等，判断不了一次变化是否实质。

**检测挡不住需要预先占有的场景。** 一个程序想确保自己的提交不会被拒绝，本提案给不了它任何东西；那是 R-CC-3，要句柄。

**本提案不改变读侧版本的选择**（见「读侧本提案不解决」）。一个只读的长打开仍持有打开时的字节；路径上的身份变化可在之后的查询中被识别，但不能刷新已持有的内容，也不能补足上述长度与页缓存缺口。
