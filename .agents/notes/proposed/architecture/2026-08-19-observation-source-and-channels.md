# Agent Note: 观察源独立成契约，事件与数据分通道

Status: proposed

## 问题

[元数据复制](../../implemented/architecture/2026-08-27-metadata-replication.md)接续了观察依据与事件、数据隔离的职责：服务端 metastore 提供日志，`replicated.Storage` 组合数据操作、快照与订阅。当前实现使用 HTTP/SSE；其他传输及共享观察契约仍待接续。[移除宿主目录后端](../../implemented/simplification/2026-09-08-remove-the-host-directory-backend.md)取消了原提案针对 `localdir` 的本地观察源分支。

本提案提出时，两个缺陷出现在同一条概念边界的两个高度。

**高层：变更流不属于挂载层被声明依赖的任何一条契约。** `docs/design/architecture.md` 把变更流放在 RPC 契约上；`client/architecture.md` 说挂载层只认 `storage` 接口，因此可以把一份本地 storage 交给它、得到一个不经网络的挂载点。

两者不能同时为真 —— 挂载层的有效性判据**完全**用变更流表述。`localdir` 只提供 storage，于是本地挂载要么永久处于「已断裂」状态、什么都不缓存，要么挂载层去做类型断言、`storage` 因此长出一个隐藏的下半身。

前一种后果尤其坏：验收判据 A5（挂载点与真实目录对拍）**对拍的就成了一个生产中永不出现、且完全绕过缓存与失效机器的配置** —— 而风险恰恰全在那台机器里。

**底层：变更流与批量数据共用一条连接，而传输契约对队头阻塞没有任何约束。** 这不只是延迟风险，它闭合成一个自维持的循环：

```
客户端发起一次整文件取回，占住连接
  → 传输期间它停止排空事件流
  → 服务端的有界订阅缓冲填满
  → 服务端按「慢订阅者」策略把它踢掉
  → 客户端进入断裂，作废全部本地状态
  → 重建是惰性的，因而正比于引发这一切的那个批量负载
  → 更多批量传输 → 回到第一步
```

触发条件只是「一个繁忙挂载点上的一个大文件」。**客户端自己的一次读，把自己变成了一次全量缓存作废。**

此外，R-INT-9 要求的三种传输里，**SSE+REST 的请求/响应与推送流本就分居两条独立 HTTP 连接** —— 把传输抽象定义成「一条双向连接」，会让三种强制传输里有一种根本无法实现。

## 提案

### 数据访问与连续观察对应同一个卷

数据访问与连续观察是两项独立能力，但必须对应同一个卷。当前复制层组合这两项能力，再把 `storage.Storage` 交给挂载层。

新增传输时，仍须提供相同的快照、连续观察、续订与故障语义；共享抽象不能把两份卷的数据与观察拼接起来。直接挂载的差分对拍验证挂载语义，带副本的路径另行验证观察中断与失效。

### 传输是 session，不是连接

`transport` 抽象定义为一个**可跨多条连接的 session**，承载两个逻辑通道：

- **事件通道** —— 服务端到客户端的变更流
- **数据通道** —— 请求/响应，含批量传输

session 拥有重连与续订，两个通道各自可能独立地断开与恢复。

### 义务规定性质，不规定拓扑

写进 RPC 契约：

> **从一次变更被记入日志，到它的事件抵达一个健康订阅者，其耗时与同一 session 上并发的批量传输无关。**

三种传输用三种不同机制满足它，所以契约不能规定机制。

同时写下一个必须预先堵住的推论：**HTTP/2 的流多路复用并不免除这条义务。** 一个丢包会拖住该 TCP 连接上的所有流，一条大的未分块消息无论如何都会独占它。「用 gRPC 所以没问题」是一个舒服且错误的结论。

**批量传输必须分块**，无论拓扑如何。

### 状态机扩成两个存活性事实

这是通道分离**诚实的代价**，必须同时改，否则比现状更糟。

分离之后，「事件通道通、数据通道断」与「事件通道断、数据通道通」都可达且都合法：

| 事件通道 | 数据通道 | 本地副本 | 新的取数 | 写入 |
|---|---|---|---|---|
| 连续观察中 | 通 | 可用 | 正常 | 正常 |
| 连续观察中 | 断 | **仍可用** —— 观察未中断，缓存仍有依据 | 等待重连 | 失败 |
| 中断，仍可续 | 通 | 已取回的仍可用 | **可直达服务端** | 失败 |
| 中断，仍可续 | 断 | 已取回的仍可用 | 等待重连 | 失败 |
| 已断裂 | 任意 | 全部作废 | 必须直达服务端，到不了则失败 | 失败 |

第二行与第三行是新出现的：前者说明**缓存的可信度只取决于事件通道**，后者说明**取不到新数据不等于缓存不可信**。

## 备选方案

**把变更流并入 `storage` 接口，让 `localdir` 也实现它。** 只有一条契约，挂载层的表述不用改。输在它抬高了 R-INT-6 的门槛：接入自有存储的第三方本来只需要实现「一个卷的存取」，现在还要实现一个可续订、有保留窗口、能诚实报告缺口的事件流。而变更历史归 server 正是为了避免这个负担。

**只规定「事件送达时延与批量传输无关」这条性质，不规定两个通道。** 改动最小，且契约仍然是传输中立的。输在两点：SSE+REST 本就是两条连接，不承认这一点会让抽象被最容易的那种传输（gRPC）塑形，而在最难的那种上变形；以及那个自维持循环是结构性的，靠「记得去测」来防守迟早会漏。

**只记录这个循环的存在与触发条件，不改结构。** 最省事。输在它把一个已知会自我放大的故障留在系统里，而修法的代价（一条契约义务 + 状态机多两行）远小于事后从 RPC 契约里挖出来重做。

**保持一条连接，但给事件通道优先级。** 在 gRPC 上可行，在 WebSocket 上要自己实现帧级调度，在 SSE+REST 上无意义。规定拓扑而非性质的典型后果。

**不做本地观察源，接受本地挂载永久处于「已断裂」。** 承认 A5 只验证「不带缓存时行为正确」。输在它把 A5 从「最有价值的一条验收」降级为「验证了最不容易错的那部分」。

## 验收标准

- 复制层明确组合数据访问与连续观察，拒绝把不同卷的两项能力配对，再向挂载层提供 storage。
- 新增传输与 HTTP/SSE 经过相同的快照、连续观察、续订与故障验收；直接挂载的差分对拍不能代替带副本路径的验收。
- RPC 契约里有「事件送达时延与并发批量传输无关」这条义务，以及「HTTP/2 多路复用不免除它」这条注记。
- 传输契约里写明批量传输必须分块。
- `client/architecture.md` 的状态表覆盖两个存活性事实的全部组合。
- 三种传输各自能说明它用什么机制满足那条义务。

## 风险

**状态机变大。** 从三个状态变成两个维度的组合。这是真实成本，不是记账花招 —— 更多状态意味着更多可能被漏测的转换。缓解手段是那两个维度各自独立、且第二维（数据通道）只影响「能不能取新数据」，不影响「已有的能不能信」。

**直接挂载的对拍不覆盖复制失效。** 与普通目录对拍能验证挂载层语义；观察中断、重同步及并发批量传输仍须在带副本的路径上验证。换用对象存储后端作为夹具不会自行补足这些覆盖。

**分块的块大小是一个未定的参数。** 太大则义务失效，太小则吞吐受损。本 note 只规定必须分块，不定块大小 —— 它需要实测，而实测要等有实现。
