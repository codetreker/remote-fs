# Agent Note: 变更定序与版本语义

Status: proposed

## 问题

本提案提出时，`docs/design/` 声明了两条定序规则，却没有机制产出它们要求的值。[元数据复制](../../implemented/architecture/2026-08-27-metadata-replication.md)已经实现日志位置与树改动同事务、响应下界及一致性快照；以下反例说明这些约束为什么存在。显式内容版本工作流的前置条件与通用并发后端的临界区规则仍保留为提案。

**第一条：「每个响应携带它所反映的位置，本地视图只接受不比现有更旧的数据」。** 但变更日志在 server 侧、且写在 storage 提交**之后**，storage 本身被明确排除在历史之外。那么处理一次读请求时，位置从哪来？

用回复时刻的日志尾盖章，会让盖章比数据新：

```
本地视图 F = X @ 100
client 发 READ(F)
server 读 storage 得到 X（旧值）
另一写者提交 F → Y，取得位置 101
server 用当前日志尾盖章 → 101
client 接受 X @ 101
事件(101, F 变了) 到达 → 不比 101 新 → 判重丢弃
```

F 被永久钉死在旧值上，且此后没有任何事件能纠正它。**一条为防止永久陈旧而设的规则，制造了永久陈旧。**

**第二条：「变更事件全序，且与提交顺序一致」。** 位置在 storage 提交返回之后分配，两者之间没有临界区。两个并发提交可以按 (A,B) 落盘、按 (B,A) 取号。对内容变更尚可（客户端重取一次即可），对创建/改名/删除则不行 —— 客户端靠**应用事件**重建命名空间视图，「创建 /a/x」在「/a/x 改名为 /a/y」之后被应用，会留下永不清理的幽灵条目。

而显然的补法 —— 一把锁横跨提交与取号 —— 会把所有写入串行化，正是 R-CC-2（写不同文件必须完全互不干扰）禁止的。

## 提案

[显式文件锁](../../implemented/architecture/2026-09-07-file-locks.md)补上权限状态的顺序：暂存后的原生最终转换，与受影响资源的授权变化和新的权威视图捕获原子排序。[实时文件句柄](../../implemented/architecture/2026-09-08-live-file-handles.md)用内部内容 revision CAS 让范围修改保留未覆盖区域，竞争后重新捕获当前字节并有界重试。普通重叠写可以按实际执行顺序成功；R-CC-1 的显式内容版本前置条件没有因此完成。已经捕获的旧视图可以完成单次读取，不能据此把普通响应标成 live-grant 检查或整个打开期间的快照。

### 位置是存取前采样的下界

响应携带的位置，**在存取 storage 之前采样**。它的含义是「这个答案不包含晚于 P 的任何变更」—— 一个下界。

盖低是安全的：代价只是将来多一次重取。盖高是不安全的：它会让正确的值被当作陈旧丢弃。

### 事件与响应用两条不同的规则

| 输入 | 规则 |
|---|---|
| **事件** | 位置**严格大于**该节点已应用位置才应用 |
| **响应** | 携带的下界**大于等于**该节点已应用位置才接受 |

严格大于用于事件，是因为位置相等意味着同一个事件；重连或重放时相等位置可以直接跳过，不需要识别事件来源。

大于等于用于响应，是因为下界为 P 的响应其数据必然不早于 P，与已应用到 P 的视图一致，接受它不会回退。

这两条规则合起来，正是「次序与位置比较是同一件事的两半」那句话缺失的另一半。

### 临界区是每节点的

本提案要求显式版本比较、storage 写入、日志追加三者在**同一个每节点临界区**内完成。SQLite 的内部内容 revision 比较与发布在写事务内完成，树与日志共同提交，仍保留原生 writer 串行化。它没有提供调用方指定旧内容依据的提交接口，也没有采用这里全部的每节点并发结构。

不同节点从不互相阻塞，R-CC-2 成立。而每节点内部，取号必然发生在该节点上一次提交之后，所以每节点顺序与提交顺序必然一致。

### 全序义务弱化

契约改为：

- **每节点**的事件顺序与该节点的提交顺序一致；
- 跨节点存在一个**任意但全序**的位置序列。

跨节点的相对顺序不再被承诺。客户端重建视图时只依赖每节点顺序，而幽灵条目问题恰好是每节点问题（同一个名字的创建与改名）。

改名跨越两个节点（两个父目录），需要在两个父目录上按固定顺序取临界区以避免死锁。

### 版本仅可比等

沿用 [storage 操作词汇](2026-08-19-storage-operation-vocabulary.md) 的决定：版本是不透明的、只能比相等的令牌。定序完全由位置承担。

文件逻辑身份、内容修订、强 Grant generation、续期 revision 与 change-log position 分别标识目标、一次内容状态、一次强授予、授予的续期状态与命名空间顺序。advisory 锁只协调参加同一协议的持有者，强 X 只证明修改权限，都不证明调用方先前读取的内容仍然有效。FileSession 的期限与动作历史另有归属，不能与日志化身混用。管理动作的不可变结果与当前状态分别核对，旧授权方退役不让旧动作在新序列下重新执行；强占有的重启保护仍由持久时长证据与恢复屏障承担，不要求逐条恢复动作历史。

## 备选方案

**在回复时刻采样位置。** 最自然的实现 —— 处理完请求，取当前日志尾。它就是上面那个缺陷的来源。之所以要专门记下它，是因为它比正确做法更容易写出来，而错误是静默的。

**以内容版本作为接受依据，位置只用于流的定序。** 版本是唯一由数据产出方直接附着在数据上的令牌，直觉上更可靠。输在版本被刻意定成仅可比等：客户端无法判断两个版本谁新。要让它可比序，就等于要求每个 storage 实现者维护一个单调计数器 —— 而 ETag、内容哈希都不满足，这直接抬高 R-INT-6 的门槛。定序交给位置是更便宜的分工。

**全局临界区横跨提交与取号。** 保证真正的全序且与提交顺序一致，语义最强。输在它把所有写入串行到一次网络/磁盘往返之后，违反 R-CC-2 —— 而 R-CC-2 在 MVP 范围内。

**预留-回填：先取号，再提交 storage，再回填日志条目。** 保证取号顺序等于开始顺序，且不需要临界区跨越 I/O。输在崩溃：进程死在提交与回填之间会留下一个**永久空洞**，而重放必须按序，于是空洞卡死所有订阅者。定义空洞策略（超时后标记为「未知变更」）是可能的，但那等于承认日志里有内容不可知的条目，客户端只能对它整体重同步 —— 用一个更复杂的机制换来一个更差的降级行为。

**不承诺任何跨节点顺序，连位置都不给全序。** 更诚实也更简单。输在客户端无法判断自己是否落后：续订需要一个可比较的位置。

## 验收标准

- 契约文档写明：位置是存取前采样的下界；事件用严格大于、响应用大于等于；临界区是每节点的；全序义务是「每节点顺序一致 + 跨节点任意全序」。
- 上述那段交错时序被作为反例写进契约文档 —— 它是这条规则存在的理由，且比规则本身更容易记住。
- 改名在两个父目录上取临界区的顺序被明确规定。
- `docs/design/architecture.md` 与 `client/architecture.md` 对定序的表述一致，不再出现「不比现有更旧」这种在两种规则之间含糊的措辞。

## 风险

**每节点临界区的粒度取决于 storage 实现者。** 契约要求版本校验与写入不可分割，而 server 无法验证实现者是否真的做到了。一个用「读版本 → 比较 → 写」实现的第三方 storage 满足契约的字面意思，却静默作废 R-CC-1。这条与[写会话与暂存](../../rejected/architecture/2026-08-19-write-session-and-staging.md)里的同一问题同源，需要在契约里声明它不可由我们验证、必须由实现者担保。

**位置下界会造成多余的重取。** 采样与存取之间发生的提交会让响应被盖低，客户端将来收到事件时再取一次。这是刻意接受的代价 —— 反向的错误是永久陈旧。

**跨节点顺序不再被承诺，可能有我们尚未想到的依赖。** 目前只识别出改名跨两个父目录这一处。若将来出现需要跨节点原子性的操作（例如目录树移动的可见性），这条弱化的契约不够用，届时需要新的 note 而不是就地加强。
