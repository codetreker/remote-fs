# Agent Note: 按内容哈希合并重复对象

Status: proposed

## 问题

对象按不透明键存放，每次写入产生一个新对象。两个内容完全相同的文件因此占两份空间，同一个文件被写入两次相同的内容也占两份——后者在源码树里并不罕见，一次构建、一次 `git checkout` 回到原状，都会产生这样的重复。

命名空间的容量上限是按内容的字节数算的（`Commit` 记的是文件的大小），所以重复**不会**吃掉使用者的额度。被吃掉的是部署方在对象存储上真正付钱的那部分。这是一个成本问题，不是一个正确性问题，也正因如此它可以等。

它可以等，但有两件事不能跟着它一起等。

**没有人知道重复有多少。** 每个对象在提交时记下的摘要落在 `objects.digest` 里，而系统里没有任何东西读它：`metastore.Store` 没有返回它的方法，`metastore.Node` 没有这个字段，契约用例把一个摘要传进 `Commit` 之后只断言 content、size、mtime 和 mode。这一列写得进去、出不来——既回答不了「值不值得做」，也没有任何用例能证明它真的在那里。把写入路径里取摘要那一步换成 `nil`，整个 module 照样全绿。

**「一个对象最多被一个名字指着」今天是一条真的不变量，而合并的全部目的就是拆掉它。** 依赖这条不变量的代码不在合并动作里，在写入路径里，见下。

## 提案

三步，按这个顺序。前两步各自独立成立，不等第三步落地。

**一、让 metastore 容得下「一个对象被多个名字指着」。** 加一个把一批名字改指到另一个对象的操作，并把两处退休对象的语句换成条件判断。这一步不做任何去重决策，它只是把一条隐式的不变量换成一次显式的检查，外加一个能拆掉那条不变量的操作。见下一节。

**二、清点。** 一个只读动作，按 `(namespace, digest, size)` 分组，报告重复占了多少个对象、多少字节。它让「值不值得做」变成一个可以回答的问题，也是 `objects.digest` 的第一条读回路径——那一列因此第一次有办法被断言。

**三、合并。** 一个可以单独运行的动作，扫描候选组，把组内其余对象的引用改指到其中一个，剩下的置为垃圾，由既有的清扫器删除。

第三步不需要引用计数：可删的判据是「有没有行指向它」，而合并只改变哪些行指向哪个对象。但那个判据今天并没有被真的问出来，所以第一步是第三步的前提，不是它的一部分。

## 「一个对象最多一个引用者」是一条今天成立的不变量

键每次写入现发，且 `Commit` 只接受处在保留状态的键并把它置为已引用，所以同一个键不可能被指第二次。任何时刻最多一个 node 指向一个对象。

在这条不变量下，「这个 node 之前指向它」和「没有行指向它」是同一件事，于是两处退休对象的语句都不带条件——`packages/metastore/sqlite/objects.go` 里，一次覆盖写把被挤掉的对象置为垃圾；`packages/metastore/sqlite/tree.go` 里，删除或替换一个 node 把它的内容置为垃圾。两条都是 `UPDATE objects SET state = ? WHERE key = ?`，都不问还有没有别的行指着它。

合并让一个对象被 n 个 node 指着。此后覆盖其中任何一个，都会把那个对象置为垃圾，而另外 n−1 个还指着它。清扫器随后删掉它的字节，再调 `Forget`；`Forget` 会拒绝，因为它检查到对象仍被名字引用。**字节已经没了，行还在**，那 n−1 个文件从此永远读 EIO。这正是 R-ERR-2 禁止的「记着名字却读不到字节」，而 `Forget` 那道守卫在删除之后才生效，晚了一步。

第一步因此是三件事：

- 两处退休都加上条件：`AND NOT EXISTS (SELECT 1 FROM nodes WHERE content = ?)`。`nodes_by_content` 索引已经在，这是一次索引查询。
- 清扫器把「仍被引用」的检查挪到删字节之前，而不是留在 `Forget` 里。今天那道守卫不可能触发，所以它今天证明不了自己；挪到前面它才是一道真的防线。动这一处的人会同时碰上[对象存储后端已知没做的事](./2026-08-22-gaps-in-the-object-store-backend.md)里记的那条到不了的分支，两者住在同一段代码里。
- 加上改指操作，否则「一个对象被两个名字指着」这个状态从 `metastore.Store` 的接口外面根本构造不出来——`Commit` 会拒绝第二次提交同一个键——于是前两条也就无从测起。

改完之后，「有没有行指向它」第一次真的是被问出来的问题，而不是从一条不变量推出来的结论。

## 摘要能证明什么，不能证明什么

摘要是对象存储对它所存字节的报告，不是本地对同一个缓冲区算的校验和（实测证据见[对象存储后端](../../../../docs/research/object-store-backends.md)）。写入路径已经按这个要求取值，见[把命名空间放进对象存储](../../implemented/architecture/2026-08-21-namespace-in-an-object-store.md)。

这个来源决定的是**这个摘要说的是不是「存下来的那些字节」**——本地算的只能说明发出去的缓冲区是什么样。它不决定两份不同的字节能不能撞上同一个摘要，那是另一个条件，见「风险」。两个条件都满足，摘要才是同一性的判据；提案里用它当判据，靠的是第二个条件由信任边界而不是由摘要本身兑现。

**它不是损坏传输的检测手段。** 写入时连同字节一起送出一份校验和，服务端不匹配就拒绝，所以一次损坏的传输表现为一次失败的写入，而不是一个对不上的摘要。任何「把返回的摘要和本地算的哈希比一比」的步骤都永远不会触发，不要写。

**它不得同时被当作节点的版本。** [没有东西钉住一个打开的文件](./2026-08-20-nothing-pins-an-open-file.md)记下了原因：内容派生的版本认不出两个内容相同的对象，于是「这还是我打开的那个对象吗」被悄悄换成了「这个名字上的字节还是我读到的字节吗」。合并会让内容相同的对象真的变成同一个对象，那正是这条退化最容易被触发的场景。

## 候选组

分组的键是 `(namespace, digest, size)`，不是摘要一项。长度不同而摘要相同在原理上存在，而 `objects.size` 就在那里。

两条过滤不能少，少了就是静默的数据损坏：

- **`digest IS NOT NULL`。** 摘要是可空的，`Objects.Put` 的契约允许一份实现什么都不报。而 SQLite 的 `GROUP BY` 认为 NULL 彼此相等——`=` 不这么认为——所以不过滤的话，所有没有摘要而恰好等长的对象会被当成同一组重复品。实测：三个摘要为 NULL、长度相同的对象在 `GROUP BY digest, size` 下合成一组三个。
- **`state` 是已引用。** 保留中的键还没有字节，垃圾状态的对象正排队等删。

合并不得复用 `Commit`：`Commit` 会调整 `namespaces.used`，而合并必须让用量纹丝不动——用量按文件的大小累加，与对象数无关。

## 跨 workspace 是键格式的问题，不是排期问题

一个 workspace 的对象放在它自己的键前缀下，而 `objects.key` 里不含前缀。namespace B 的 node 指向 namespace A 的键，B 的客户端会去 `prefixB + key` 找它——那里什么都没有。跨 workspace 合并因此不是「首次实现先不做」，是今天的键格式做不了。

由此得到一条对形式的禁令，它约束的是将来：

> 一个对象的键必须能独立解析出它所在的前缀，否则跨 workspace 合并需要一次键格式迁移。

这条今天不成立。写下它，是为了让「跨 workspace 合并要花多少钱」不再被当成一个排期问题。

即使键格式解决了，还有第二层：一个被两个 workspace 引用的对象不再属于任何一个前缀，删除一个 workspace 也就不能简单地删掉它的前缀。

## 备选方案

**写入时就去重：先算哈希，查有没有一样的，有就直接指过去。** 省掉一次上传，重复从来不存在。输在它把一次网络往返（查询）放在每一次写入的关键路径上，而收益只在重复真的发生时才兑现；并且它需要写入者信任一个它没有亲自验证过的摘要——那个摘要来自上一次写入，不是这一次。

**内容寻址：键直接就是哈希。** 去重变成写入的自然结果，不需要任何合并动作。输在删除需要引用计数才安全，而引用计数是一份要维护、要在崩溃后修复的账。[把命名空间放进对象存储](../../implemented/architecture/2026-08-21-namespace-in-an-object-store.md)记了这次取舍。

**逐字节比对，不信摘要。** 把摘要降级成候选筛子，合并前把两个对象都读回来比一遍。它与摘要的强度完全无关，因此是跨越信任边界唯一站得住的做法，而合并是后台动作，两次读的代价付得起。它输在一个 workspace 之内是白花钱——那里没有信任边界可越，见「风险」——所以它是跨 workspace 合并的前提，不是首次实现的做法。

**只做第一步，不做去重。** 把退休变成条件判断、把守卫挪到删除之前，这两件事本身就是把一条隐式不变量换成显式检查，即使去重永远不做也是笔划算的买卖。输在它没有任何可观察的收益，而这份提案要的正是那个收益；它作为独立的一步保留在上面，不作为终点。

**不做。** 重复只花钱，不出错。这正是它被推迟的理由；这份提案记录的是它在什么条件下值得做——当重复的占比可以被测出来时。第二步就是让这个条件变得可以回答。

## 验收标准

**第一步。** 一个对象被两个名字指着时，覆盖其中一个不把它置为垃圾；两个都覆盖之后它才是垃圾。这个状态用新加的改指操作构造，所以它测在 metastore 的契约用例上，两份实现各跑一遍。清扫器那一侧：一个仍被引用的对象送进清扫，字节必须还在——用改指构造出那个状态，把守卫拆掉一次看它变红。

**第二步。** 一个含有已知重复的命名空间上，清点报出的重复对象数与字节数，与构造出来的重复量相等；没有重复时报零；摘要为 NULL 的对象一个都不出现在结果里。

**第三步。** 一个含有已知重复的命名空间上跑完合并之后：重复的对象只剩一份；所有指向被合并对象的行都指向留下的那一份；读回每个文件得到的字节与合并前完全一致；命名空间报告的用量不变；而**容器里的对象数确实下降了**。最后一条是这个动作唯一买到的东西，前面四条都只是「没有变坏」。

## 风险

**合并与并发写入之间的竞争，危险的是赢家那一侧。** 选出候选组与改指之间，被选作赢家的对象可能因为一次覆盖而变成垃圾。把一批行指向它，等于把它们指向一个正排队等删的对象。SQLite 只有一个写者，所以改指的那个事务重新读一次赢家的状态、不是已引用就放弃这一组，是充分的。输家那一侧安全：对象不可变，读取者手里的键被删掉时会重来，而重来拿到的是赢家的键，字节按构造完全相同——代价与去掉这条代价的办法见[在途的读者与清扫器](./2026-08-21-readers-in-flight-and-the-sweeper.md)。

**摘要相同而字节不同。** Azure Blob 在写入的响应里给的是 `Content-MD5`，而 MD5 的选择前缀碰撞在今天是可做的。一个能往命名空间里写东西的人因此可以构造出两个摘要相同、内容不同的对象。

在一个 workspace 之内这不构成攻击：workspace 就是访问边界，能往里写的人已经拥有里面的文件，把自己的文件换成自己的另一个文件没有收益。跨 workspace 才成立，而那里它是致命的——一个租户可以把另一个租户的文件换掉。

所以这不是一条实现时要小心的风险，是一条对判据的禁令：

> 合并的判定依据不得跨越 workspace 的信任边界。

跨越它需要的是逐字节比对，不是一个更强的服务端摘要：摘要由服务端计算，换不掉；自己算就回到了本地校验和，那正是上面否掉的东西。Azure 的 `x-ms-content-crc64` 同样不行，它是校验和而不是抗碰撞的哈希。
