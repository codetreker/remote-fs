# Agent Note: 按内容哈希合并重复对象

Status: proposed

## 问题

对象按不透明键存放，每次写入产生一个新对象。两个内容完全相同的文件因此占两份空间，同一个文件被写入两次相同的内容也占两份——后者在源码树里并不罕见，一次构建、一次 `git checkout` 回到原状，都会产生这样的重复。

命名空间的容量上限是按内容的字节数算的（`Commit` 记的是文件的大小），所以重复**不会**吃掉使用者的额度。被吃掉的是部署方在对象存储上真正付钱的那部分。这是一个成本问题，不是一个正确性问题，也正因如此它可以等。

## 提案

每个对象在写入时记下对象存储报告的内容摘要。一个可以单独运行的合并动作扫描摘要相同的对象组，把组内其余对象的引用改指到其中一个，剩下的进入待删队列，由既有的清扫器删除。

这不需要引用计数：判定一个对象是否可删的依据一直是「有没有行指向它」，而合并只改变哪些行指向哪个对象，那个判定不受影响。

**摘要必须是对象存储对它所存字节的报告，不能是本地对同一个缓冲区算的校验和。** 后者认不出一次损坏的传输，而合并动作恰恰是在拿它当「这两份字节相同」的证据。写入路径已经按这个要求取值，见[把命名空间放进对象存储](../../implemented/architecture/2026-08-21-namespace-in-an-object-store.md)。

**摘要不得同时被当作节点的版本。** [没有东西钉住一个打开的文件](./2026-08-20-nothing-pins-an-open-file.md)记下了原因：内容派生的版本认不出两个内容相同的对象，于是「这还是我打开的那个对象吗」这个问题被悄悄换成了「这个名字上的字节还是我读到的字节吗」。合并会让内容相同的对象真的变成同一个对象，那正是这条退化最容易被触发的场景。

跨 workspace 合并另有一层要考虑的东西：一个对象若被两个 workspace 的行引用，它就不再属于任何一个前缀，删除一个 workspace 也就不能简单地删掉它的前缀。首次实现应当只在一个 workspace 内合并。

## 备选方案

**写入时就去重：先算哈希，查有没有一样的，有就直接指过去。** 省掉一次上传，也省掉重复对象从来不存在。输在它把一次网络往返（查询）放在每一次写入的关键路径上，而收益只在重复真的发生时才兑现；并且它需要写入者信任一个它没有亲自验证过的摘要——那个摘要来自上一次写入，不是这一次。

**内容寻址：键直接就是哈希。** 去重变成写入的自然结果，不需要任何合并动作。输在删除需要引用计数才安全，而引用计数是一份要维护、要在崩溃后修复的账。上面那份 note 记了这次取舍。

**不做。** 重复只花钱，不出错。这正是它被推迟的理由；这份提案记录的是它在什么条件下值得做——当对象存储的账单里重复的占比可以被测出来时。

## 验收标准

一个可以单独运行的动作，在一个含有已知重复的命名空间上跑完之后：重复的对象只剩一份，所有指向被合并对象的行都指向留下的那一份，读回每个文件得到的字节与合并前完全一致，且命名空间报告的用量不变。

## 风险

**合并动作与并发写入之间的竞争。** 被合并掉的对象可能正在被某个读取者使用。对象不可变，所以那个读取者读到的字节是对的；但它的键会被删除。清扫器已有的那条规则——只删除没有行指向的对象——覆盖了这一点，前提是合并与清扫不能在同一个事务里把「改指」和「入队」拆开。

**摘要相同而字节不同。** 取决于对象存储报告的是什么摘要。若它是 MD5，构造碰撞是可行的；一个能写入 workspace 的人因此可以让另一个文件的内容被换掉。这决定了这个动作能不能在多租户的部署里开启，必须在实现前定下来。
