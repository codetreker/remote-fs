# Agent Note: storage 契约的操作词汇

Status: proposed

## 问题

`docs/design/architecture.md` 把 `storage` 定为系统的中心契约：client 与 server 两侧都实现它，第三方接入自有存储也实现它（R-INT-6）。但这份契约目前**只有四条义务，零个操作**。

没有操作清单、没有说标识是路径还是不透明的节点身份、没有说版本能不能比大小、没有说读是整文件还是按区间、没有错误词汇、**没有说提交是不是整文件**。

三个后果：

**往返次数是这个系统的货币，而设计没有决定它。** 一次 `stat` 花几个往返、`ls -l` 一千条目花几个往返，全部取决于操作的粒度。评审给出的算术里每一行都有两个答案，原因就在这。

**两个称职的工程师会造出互不兼容的东西。** 路径寻址 vs 节点身份寻址、`读(id, 偏移, 长度)` vs `打开(id) → 流`、整文件提交 vs 区间提交 —— 每一对都是合理的选择，而它们无法互换。

**四行散文交不出去。** R-INT-6 要把这份契约交给第三方，让他们写出合规实现。义务不是词汇，而实现者首先需要的是词汇。

## 提案

### 操作

| 操作 | 形状 | 备注 |
|---|---|---|
| 解析 | (父节点, 名字) → 节点身份 + 属性 | 一次一层。路径解析天然串行，见下 |
| 取属性 | 节点身份 → 属性 | |
| **列目录** | 目录身份, 游标 → **条目及其属性** + 下一页游标 | **每个条目内联携带属性**。见「为什么内联」 |
| 读链接 | 节点身份 → 目标 | |
| **读内容** | 节点身份, 版本, 字节区间 → 字节 | **按区间**，且携带调用方所依据的版本 |
| 创建 / 建目录 / 建符号链接 | (父节点, 名字, …) → 节点身份 + 属性 | |
| 删除 | (父节点, 名字) → — | |
| 改名 | (旧父, 旧名, 新父, 新名) → — | |
| 改属性 | 节点身份, 变更集 → 属性 | |
| **提交内容** | 节点身份, **所依据的版本**, 内容 → 新属性 | 整文件。区间提交见「风险」 |

### 标识

**不透明的节点身份，不是路径。** 跨改名稳定，删除后不复用。

路径寻址会让改名作废整棵子树的键、让变更事件无法寻址（服务端得知道每个 client 的命名空间视图）、并在改名与查询交错时让键指向错误的对象。

代价：客户端需要一份「(父节点, 名字) → 子节点」的反向索引，因为内核的目录项失效是按名字寻址的。

### 版本

**不透明，仅可比等，不可比序。**

这样第三方可以用 ETag、内容哈希、代数 —— 任何他们手头已有的东西。定序完全由变更日志的位置承担，不压在版本上。

### 每次修改必须返回受影响节点的身份与新版本

否则 server 的请求处理方写不出正确的日志条目（日志要记「哪个节点被创建/删除/改名到哪」），客户端也学不到自己新依赖的版本。

### 错误词汇

至少必须区分三类，且**「无法判定」不得被压平成「不存在」**：

- 不存在
- 存在但不满足前置条件（版本不符）
- **无法判定**（后端不可达、超时、内部错误）

这条是 R-ERR-1 / R-ERR-2 在契约层的落点。三种传输有三套原生错误模型，不强制规定的话，第一个边界就会把它压平。

## 为什么列目录要内联属性

这是往返复杂度性质，不是签名细节，所以它属于架构层。

只带名字的列目录让 N 条目的目录花 1+N 个往返；内联让它花 1 个。按 20 ms RTT、1000 条目算：

| | 往返 | 耗时 |
|---|---|---|
| 内联属性 | 1（约 140 KB） | **31 ms** |
| 只带名字，逐条解析 | 1001 | **20 s** |

多传的约 115 KB 换掉 1000 个往返 —— 11 ms 的传输换 20 秒。`git status` 遍历 1 万文件从 220 秒降到 20 秒。

而 `docs/spec/problem.md` 的 S2 明说列目录「极其频繁」，R-WS-4（冷挂载要迅速可用）与 R-SCALE-1（假设是源码树、以元数据访问为主）也都依赖它。

**这条曾经在架构初稿里，重写时丢失。** 记在这里以免再丢。

## 路径解析仍然是串行的

逐层解析意味着深度 4 的路径冷态要 4 个往返，且**任何客户端并发都压不掉** —— 第 n+1 层需要第 n 层的结果。

这是内核路径解析语义决定的，不是接口选择造成的。缓解手段是缓存（热态 0 往返），不是接口。

「一次调用解析整条路径」是一个真实的备选，见下。

## 备选方案

**路径寻址而非节点身份。** 更简单，且能一次解析整条路径（深度 4 从 4 个往返降到 1 个），对不挂载的编程式访问（R-INT-5）尤其有价值。输在三点：改名作废子树、变更事件无法寻址、改名与查询交错时键指向错误对象。第三点是决定性的 —— 它是静默的错误。

**保留节点身份，但额外提供一个「按路径解析」操作。** 没有被否决，只是不在本提案范围内：它是纯增量，随时可加，且对 SDK 路径的收益（10 万次 stat 从 40000 个往返降到 10000 个）在真有 SDK 使用者之前无法评估。

**版本可比序。** 允许客户端直接比较新旧，不必依赖日志位置。输在实现者负担：要求单调版本等于要求实现者维护一个计数器，而 ETag 与内容哈希都不满足 —— 这直接抬高 R-INT-6 的门槛。定序交给日志位置是更便宜的分工。

**只带名字的列目录 + 逐条解析。** 传输量最小（25 KB vs 140 KB），且对「只想列文件名」的场景没有浪费。输在往返：见上表，650 倍。传输量在这个系统里不是瓶颈，往返才是。

**整文件读而非区间读。** 更简单，且提交本来就是整文件的，读写对称。输在一处会致命：读 10 MB 文件的头 4 KB 会传 10 MB。而 S2 的负载里随机小读很常见。

**批量操作（多解析、多取属性、多读）。** 没有被否决，不在本提案范围内。它对不挂载的编程式访问收益巨大（10 万次 stat 从 40000 个往返降到 20 个），但挂载路径靠内核的目录项缓存已经摊掉了大部分粒度成本。等 SDK 有真实使用者再定形状 —— 提前定形状很可能定错。

## 验收标准

- 契约文档列出上述每个操作及其形状，第三方可据以写出实现而不必追问。
- 契约文档明确写出：标识是不透明节点身份、版本仅可比等、每次修改返回身份与新版本、列目录内联携带属性、读按区间。
- 错误词汇被明确列出，且写明「无法判定不得被压平成不存在」。
- `docs/design/architecture.md` 的 storage 契约小节与本 note 一致。

## 风险

**整文件提交在大文件上的代价没有解决。** 1 字节的修改要上传整个文件。区间提交是可能的（携带基准版本提交一段区间），但它与版本校验的原子性相互作用，且需要 storage 实现者支持区间写 —— 会抬高 R-INT-6 的门槛。本提案接受这个代价，条件是它不改变契约形状：区间提交将来可以作为额外操作加上，不必改动已有的。

**分页游标的语义未定。** 大目录必须分页（1 万条目内联属性约 1.4 MB，单条消息过大），但「分页期间目录发生变化」的语义没有在本 note 里定。这与变更定序是同一个问题，留给[定序与版本](2026-08-19-ordering-and-versions.md)。

**内联属性让单条消息变大。** 1.4 MB 的列目录响应与小的元数据操作共用一条管道时会造成队头阻塞。这不是本 note 的问题，但本 note 的决定会加重它 —— 见[观察源与通道分离](2026-08-19-observation-source-and-channels.md)。
