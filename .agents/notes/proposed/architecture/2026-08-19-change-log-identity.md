# Agent Note: 变更日志的身份、作用域与持久性

Status: proposed

## 问题

`docs/design/server/architecture.md` 把变更日志描述成「服务端级的、单数的日志」，并规定了保留窗口与「无法重放时明确报告」。三件决定它是否可信的事，一件都没写。

**身份。** 客户端续订时只带一个位置。位置属于谁、是否还是同一条历史，无人过问。于是：server 重启后日志为空，一个客户端拿着位置 12345 来续订，**一个看起来完全正确的实现会回答「在窗口内，你已追平」** —— 整段停机期间的所有变更静默丢失。

这正是设计自己命名的最坏失败：客户端以为自己一直在观察，实际上漏掉了变更，且事后无从察觉。而触发它只需要一次普通重启。

**作用域。** 日志是每服务端一份还是每卷一份，没有说。若是全局，每个客户端会收到所有卷的事件 —— 而 R-SCALE-2 明说「存在的卷很多，同时挂载的很少」，扇出因此是 O(客户端数 × 全部卷的变更率)。一个安静的卷会因为别人的流量而烧掉自己的保留窗口。

**持久性。** 从未说明。这不只是实现细节：它决定了「重启 server」是一次例行操作，还是一次全舰队事件。

## 提案

### 续订标识是（化身, 位置）

日志有一个**化身标识**。客户端续订时同时提交化身与位置。

化身不匹配 → server 明确回答「无法重放」，客户端丢弃全部本地状态重建。位置对不上但化身相同 → 按保留窗口判断。

**化身在日志不是上一次的逐字延续时改变。** 具体地：日志为空而客户端声称有位置、日志从非持久存储重启、或服务同一卷的进程换了一个不共享该日志的实例。

这是这个系统缺失的 fencing。它把「静默的错误答案」换成「昂贵但诚实的重建」。

### 日志按卷分

每个卷一条日志、一个独立的位置序列、一个独立的保留窗口。

事件扇出因此不跨卷：只挂载了 A 的客户端不会收到 B 的事件，也不会因为 B 的流量而被挤出自己的窗口。

这与 [卷进入契约](2026-08-19-volume-in-the-contract.md)里「一个 storage 实例 = 一个卷」的决定一致 —— 日志跟着 storage 实例走。

### 保留窗口同时有时间维度与容量维度

只有时间维度不是内存界：窗口内发生 100 万次变更，日志就增长 100 万条。

两个维度都要有，且**客户端被告知它是从哪一个维度掉出去的** —— 因为运维处置不同：时间维度掉出去说明客户端离线太久，容量维度掉出去说明变更率超出配置。

### 日志在内存中，且写清后果

日志在内存中。**后果必须写进文档，不能靠读者推断：**

> 每次 server 重启都是全舰队事件 —— 所有客户端同时断裂、同时丢弃全部本地状态、同时惰性重取。

而 server 被禁止缓存、被禁止持有客户端状态，于是 C 个客户端会在同一秒对同一个目录产生 C 次独立的 storage 读，没有去重、没有准入控制、没有抖动。

化身规则让这个后果**诚实**（客户端明确被告知要重建），但不让它**便宜**。持久化日志是消除它的办法，不在本提案范围内。

## 备选方案

**只带位置，不带化身。** 现状。输在上面那个重启即静默丢失的场景。它的代价是一个标识符，收益是消掉一整类无声故障 —— 没有理由不做。

**用「server 启动时间」或随机数当化身。** 比没有强，但把「日志是否连续」与「进程是否重启」混为一谈。持久化日志的进程重启不应该让所有人重建；而两个共享同一份持久日志的进程实例应该有相同的化身。化身应当属于**日志**，不属于进程。

**日志持久化。** 消掉全舰队事件，重启变成例行操作。（这一条后来被 [元数据复制](../../implemented/architecture/2026-08-27-metadata-replication.md) 采纳：日志与树同库同事务，于是这里担心的「storage 之外的持久状态」不再成立，而它换来一个新的义务——提交与追加之间的崩溃不再自愈，必须靠启动对账去发现。下面这段权衡属于当时，不改。）输在它让 server 拥有 storage 接口**之外**的持久状态 —— 嵌入式集成方（R-INT-1，首要交付目标）必须回答它存在哪里、持久性契约是什么、由谁备份，而 R-INT-3 对它的体积也适用。不在本提案范围内，但化身规则让将来加上它不需要改客户端。

**把日志存进 storage 自身。** 不引入新的持久状态，且天然与数据同生命周期。输在它把变更历史推回给第三方实现者 —— 而变更历史归 server 正是为了避免这个负担。

**日志全局，事件按卷过滤后再发。** 实现简单，一条日志一个序列。输在保留窗口仍然是共享的：一个高频卷会把安静卷的历史挤出去，而后者的客户端因此被迫重建。过滤解决了扇出，没解决窗口。

**不设容量维度，只靠时间。** 配置更简单。输在它不是内存界，而 server 也要能嵌入别人的进程。

## 验收标准

- 续订携带（化身, 位置），且契约写明化身在什么情况下改变。
- 化身不匹配时 server 明确回答「无法重放」，与位置超窗走同一条诚实路径。
- 日志按卷分，文档写明一个客户端只收到它所挂载卷的事件。
- 保留窗口有时间与容量两个维度，且客户端被告知从哪一维掉出。
- 「内存日志 ⇒ 每次重启是全舰队事件」这个后果出现在 `server/architecture.md` 里，不是靠读者推断。

## 风险

**全舰队重建没有缓解手段。** 化身让它诚实，不让它便宜。C 个客户端同时重建会对 storage 产生 C 倍的重复读，而 server 被禁止缓存。评审提出的「服务端对完全相同的在途请求做合并」不是缓存、不违反那条禁令，但本 note 不提出它 —— 它属于性能，需要先有实测。这条风险记在这里，以免将来把它当成新发现。

**化身的传播依赖实现者自觉。** 若集成方把日志换成持久实现却忘了让化身跨重启保持不变，所有客户端会在每次重启时白白重建；反过来，若换实现时忘了改化身，则会静默丢失变更。后者是危险的那一侧，契约必须把「什么时候必须改化身」写成实现者义务而不是建议。

**容量维度的单位未定。** 条目数还是字节数，本 note 不定 —— 它取决于事件的实际大小分布，需要实测。
