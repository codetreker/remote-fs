# Agent Note: 元数据复制 —— 一致性快照与有序日志

Status: proposed

## 问题

挂载点今天一个字节的元数据都不留。`packages/fuse/fuse.go` 把 `EntryTimeout`、`AttrTimeout`、`NegativeTimeout` 三个内核超时全设成 0，于是每一次内核调用都落成一次 RPC——每一次 `ls`、每一次 `stat`、路径搜索里每一次「文件不存在」都是一个往返。`client/architecture.md` 第二节把这个选择写得很清楚，也写明了代价。

代价在一个跑工具链的 workspace 上是压倒性的。可执行文件查找、模块导入、链接器搜索路径产生的「不存在」远多于「存在」，在 20 ms 链路上一次这样的探测风暴要花掉约十秒。

但把元数据留在本地，难的不是把它取下来，而是**取下来之后它什么时候会变成谎话，以及怎么知道**。而 R-CON-2 把这个问题的答案锁死了：

> **R-CON-2** 可见性不得取决于任何轮询间隔是否走完。挂载期间该保证持续成立，而不是在某个周期边界上成立。

这一条单独否掉了所有基于 TTL 的方案。哪怕 200 ms 的 TTL 也是「在某个周期边界上成立」。注意 R-CON-1 只要求一秒内可见——**一个一秒 TTL 的缓存字面上满足 R-CON-1**，是 R-CON-2 不让。

因此**「同步元数据」与「订阅变更流」不是两件事**：本地副本的可信度只取决于事件通道是否连续观察中。没有流，本地副本只有两种诚实的用法——每次操作都回源校验（等于没缓存），或者违反 R-CON-1 与 R-CON-2。

这份 note 定的是这条流与它的起点。它吸收并接续三份更早的提案：[观察源与通道](2026-08-19-observation-source-and-channels.md)、[定序与版本](2026-08-19-ordering-and-versions.md)、[变更日志的身份与作用域](2026-08-19-change-log-identity.md)；其中日志持久性一条与最后那份的结论相反，理由见「落盘与崩溃缺口」。[内核缓存与不可达](2026-08-19-kernel-cache-and-unreachable.md)所处理的那一层不在本 note 范围内，但它随本 note 的落地一并到期，见「风险」。

## 提案

本地副本只装元数据。文件字节仍然按需整份取回，内容不同步。

### 时序：订阅在前，快照在后

```
1. 客户端订阅 → 服务端从当前尾位置起向它推送；客户端缓冲
2. 客户端要快照 → 服务端取一次一致性切割，返回（快照句柄, 位置 P）
3. 分页流完 → Close，放掉底层资源
4. 重放缓冲：位置 > P 的应用，≤ P 的丢弃
5. 原子切换到本地副本，转入正常推送
```

顺序不能反，而反过来是更自然的写法。先抽快照再拿着它的位置去订阅时：

```
t0      采样位置 P
t0..t1  扫描产出快照            ← 这段时间里别人在写
t1      拿着 P 去续订
        若 (t0,t1] 之间的变更条数 > 保留窗口，P 已经掉出去了
        → 服务端诚实回答「无法重放」→ 全量重建 → 回到 t0
```

**扫描耗时 × 变更速率 > 窗口，就永远追不上。** 而重建代价正比于树的大小，于是**树越大越不收敛**——最坏的那种耦合方向。一次动两千个文件的分支切换就足以触发。

订阅在前之后，**保留窗口不在首次同步的关键路径上**，它只伺候断线重连。

### 快照是一次一致性切割

客户端不指定位置，要的就是「现在」；服务端也不需要能在历史位置上重建快照。

契约只要求一件事：**在 `Close` 之前，快照看到的是同一个瞬间。** 怎么取得由实现决定，而三种实现取得它的代价完全不同，不能写成一句话：

| 实现 | 怎么取得 | 代价 |
|---|---|---|
| SQLite（WAL） | 一个读事务 | 读事务钉住 WAL，checkpoint 过不去；事务开多久 WAL 涨多久 |
| PostgreSQL | `REPEATABLE READ` | 长事务挡住 vacuum，表膨胀 |
| 内存 | 加锁**只到取得引用为止**（写时复制或指针浅拷贝），拿到即放锁再流 | 锁若持有到流完，等于在一次网络传输的时长里冻住整个 workspace 的写入 |
| 合成日志的后端（`localdir`） | 遍历期间扣住位置分配器，写入排队 | 遍历一棵真实目录树期间写入停顿 |

前两行有一个必须正面处理的共同性质：**事务的生存期被网络速度决定。** 最坏情况是 server 重启后所有客户端同时重建，读事务同时开着，谁最慢 WAL 就涨到多大。

因此快照是一个**有生存期、有并发上限**的对象：每份快照有截止时间，超时即中止并放掉资源；同时打开的快照数有上限（R-INT-3）。中止之后客户端从头再来，而**从头再来之所以可以接受，正是因为订阅在前**——重试不影响日志窗口。反复拿不到就落到「挂载时序与降级」里那条已经设计好的降级。

代价写明：**快照流断了不能续传。** 一致性切割没了就是没了。

一份位置 P 的快照可以给任何**订阅开始 ≤ P** 的客户端共用；服务端做单飞合并时按这条分组。它让「所有客户端同时重建」这件事从「N 次全树扫描」变成「一次全树扫描」，而位置正是使共用安全的那个东西。

### 位置与接受规则

沿用[定序与版本](2026-08-19-ordering-and-versions.md)：位置在**存取之前**采样，含义是「这个答案不包含晚于 P 的任何变更」——一个下界。**盖低是安全的**，代价只是将来多一次重取；**盖高不安全**，它会让正确的值被当作陈旧丢弃，而且此后没有任何事件能纠正它。

| 输入 | 规则 |
|---|---|
| 事件 | 位置**严格大于**该节点已应用位置才应用。相等即同一事件——自己提交的回显靠这条免费判重 |
| 响应 | 携带的下界**大于等于**该节点已应用位置才接受 |
| 快照 | 它是精确的切割而非下界，所有节点的已应用位置一律种成 P |

客户端仍然维护每节点的已应用位置，但它只服务稳态：回显判重，以及事件通道中断而数据通道仍通时直达服务端拿到的响应要并回副本。

契约承诺的全序义务是弱的：**每节点的事件顺序与该节点的提交顺序一致，跨节点存在一个任意但全序的位置序列。** SQLite 的全局写串行化白送了真全序且必然与提交顺序一致，但不写进契约——否则将来的 PostgreSQL 后端会被一个它不需要的保证捆住。改名跨两个父目录，两个临界区按固定顺序取以避免死锁。

### 保留窗口是三个数

| | 取值 | 职责 |
|---|---|---|
| 下界 | 至少 100 条 | 安静的 workspace 的一次短暂抖动永远可续 |
| 上界 | 至多一万条／workspace，可配 | R-INT-3 的资源上限 |
| 时间界 | 丢弃早于十分钟的 | 伺候 R-SCALE-2 |

时间界的职责值得单独写下来，因为落盘之后它看起来像是多余的：它真正在做的是让「存在的 workspace 很多、同时挂载的很少」（R-SCALE-2）不变成「很多份一万条的日志躺在盘上」——没人挂载的 workspace 十分钟后缩到下界。这个理由与内存无关，不写下来，将来会有人看着「反正在盘上」把它调没。

**尾位置独立于条目保留。** 否则「已追平」与「掉出窗口」区分不开：一个安静了十一分钟、日志被时间界清空的 workspace，客户端拿着位置 P 来，答不出它是追平了还是漏了。

客户端必须被告知自己**从哪一个维度掉出去**——时间维度说明它离线太久，容量维度说明变更率超出配置，运维处置不同。

### 续订标识是（化身, 位置）

化身属于**日志**，不属于进程：持久化日志的进程重启不该让所有人重建，两个共享同一份日志的实例应当有同一个化身。

```
连上 → 送（化身, 位置）
    化身不匹配       → 重建
    位置 == 尾位置    → 已追平，直接转推送
    位置 < 最老保留   → 重建，并告知从哪个维度掉出
    否则             → 从 位置+1 重放
```

没有化身的后果是这个系统里最坏的那种失败：server 重启后日志为空，客户端拿着位置 12345 来续订，**一个看起来完全正确的实现会回答「在窗口内，你已追平」**——停机期间的全部变更静默丢失，事后无从察觉，而触发它只需要一次普通重启。

### 落盘与崩溃缺口

[变更日志的身份与作用域](2026-08-19-change-log-identity.md)把日志放在内存里，并把「持久化」列为范围之外的备选。这份 note 反过来：**日志落盘。** 理由是内存日志让每一次 server 重启都是全舰队事件，而加上快照之后这件事比当初贵得多——所有客户端同时重建，就是同一时刻的多次全树扫描砸在 metastore 上。

但落盘改变了一个性质，它不是「加个持久化」那么轻：**「metastore 提交」与「日志追加」之间的崩溃不再自愈。**

日志在内存里的时候这个缺口是无害的——进程一死日志就空了，化身跟着变，所有人重建，丢掉的那条事件根本没机会被人相信。落盘之后化身活了下来：

```
metastore 提交 /a/b → 成功
                        ← 崩溃
日志追加（P, /a/b 变了）→ 没发生
重启：日志尾还是 P-1，化身不变
客户端续订 P-1 → 「你已追平」
```

`/a/b` 在每一个客户端的副本里**永久停在旧值**，而且没有任何东西会纠正它。

因此写路径是：

```
每节点临界区 {
    版本校验
    metastore 事务 {
        应用树／属性改动
        分配位置 P
        追加 Change{P, …} 到日志
        记下 CommittedPosition = P
    }
}
向订阅者发布 Change
```

启动时对账：`CommittedPosition > 日志尾` ⇒ 有事件丢了 ⇒ **化身 +1** ⇒ 一次昂贵但诚实的重建。

由此得到一条要写进契约的规则：**一个后端要么能把位置纳入自己的原子提交，要么它的日志不得持久化。** 合成日志的后端（`localdir`）没有任何东西可以对账——它的「提交 + 追加」之间崩溃是**不可检测**的——所以它的日志只能在内存里，重启即换化身。持久化不是一个全局开关，是能参与原子提交的后端才有的特权。

日志与树同库同事务，还顺带消掉了那份 note 记下的另一条反对意见：**server 不会因此拥有 storage 契约之外的持久状态**。那份状态属于某个存储实现，而 R-INT-12 已经说明存储实现可以依赖它自己的外部服务，并且必须说明它需要什么。

### 日志归 metastore，观察源归服务端

**日志是每个 metastore 必须提供的能力**，怎么实现由各自决定。

但 `localdir` 没有 metastore，而端到端测试与挂载测试全部走 `localdir`。若日志只有 metastore 有，那么 `localdir` 后端的 workspace 永远没有事件流、挂载点永远回退到无缓存模式，于是**整套元数据复制机制在测试里一次都不会被走到**，而差分对拍对的会是一个生产中永不出现、完全绕过缓存与失效机器的配置——风险恰恰全在那台机器里。[观察源与通道](2026-08-19-observation-source-and-channels.md)已经为这件事论证过一轮。

因此：

> **观察源是服务端的构件，不是存储的能力。** 两种拿法：
> - metastore 提供日志 → 可落盘、跨重启可续订、位置与树同事务；
> - storage 没有日志 → **服务端自己记**，内存，随进程生灭，重启换化身。

第二条成立的依据在需求里现成：「绕开本系统直接改动被服务出去的命名空间」不是被支持的用法，所有写入都经过服务端。它的崩溃缺口与上面同源，但日志是内存的、进程一死就没了、化身跟着变——**自愈，因此无害**。

这样 `storage.Storage`（R-INT-6 那条契约）一个字不用改，第三方接自有存储照旧只需实现「一份命名空间的存取」，而 `mount(localdir)` 走的是与生产完全相同的缓存与失效路径。

快照同理：**通用慢路径是递归 `List`，metastore 后端提供快路径。**

### 事件装 delta

```go
type Change struct {
    Position Position
    Kind     Created | Removed | Modified | Renamed
    Parent   ID
    Name     []byte
    From     *Location // 仅 Renamed：来源的（parent, name）
    Node     *Node     // 仅 Created / Modified / Renamed
}
```

决定性的理由是**目录改名**。metastore 存的是 `parent_id + name`，一次目录改名在服务端是**一行**；delta 让客户端也是一行——底下整棵子树自动跟着走，编号不变。若事件只是「`/a` 变了，自己去取」，客户端只能丢掉 `/a` 底下的整棵子树再重走一遍。而目录改名恰恰是工具链最常做的事：切分支、把暂存目录换到位、解压后改名。

代价必须写成实现者义务：**客户端副本的正确性从此完全等于事件生成的正确性。** 落盘之后一次漏发或错发是永久的，没有任何超时救得回来。

一致性切割额外买到的：重放时 `≤ P` 的一律丢弃，于是 **rename 永远看得到自己的源**，不需要「源不存在的 rename 当作空操作」这一类容忍规则——那条规则不写，就永远不会有人依赖它。

### 挂载时序与降级

```
挂载      ── 立刻可用；此刻行为与今天相同（每 op 一次 RPC，正确但慢）
   │        订阅已开，事件在客户端排队
   ▼
快照拉完 ── 应用排队的 > P 事件 ── 原子切换到本地副本
```

挂载是瞬间的，**R-WS-4 按构造成立**；切换之前跑的是今天已经在跑、已经被测过的那一套。

**全量或不做，没有部分副本。** 要么整棵树在本地——于是「这个目录我列全了」永远为真——要么完全没有本地副本。这一刀砍掉的是整个缓存里最容易错、错了最难发现的那一类：**哪些目录是完整的**。readdir 需要完整性，lookup 不需要，两者共用一份记录时极易出错。

条目数预算可配；超预算就放弃快照、停在直通模式。而**这件事必须可见**——R-ERR-4 说降级若不可见等同于不存在——所以状态查询里要答得出「这个挂载点为什么没有本地副本」。

部分同步将来还能加：快照分页已经允许「只要一棵子树」，这一版只是不做。

### 两条连接

事件与批量数据分开。**对 gRPC 意味着两条 HTTP/2 连接，而不是一个连接上的两个 stream**——一个丢包会拖住那条 TCP 上的所有 stream，一条大的未分块消息无论如何都会独占它。「用 gRPC 所以没问题」是一个舒服且错误的结论。SSE+REST 天然是两条。

义务写成**性质而不是拓扑**：从一次变更被记入日志，到它的事件抵达一个健康订阅者，其耗时与同一 session 上并发的批量传输无关。三种传输（R-INT-9）各自说明用什么机制满足它。

**快照与文件传输都必须分块。** 快照现在是系统里最大的一次批量传输，它挤掉自己的事件通道，后果是重新拉一份快照——一个自我放大的循环，而触发它只需要一次正常的冷挂载。

客户端的状态是**两个存活性事实**的组合：

| 事件通道 | 数据通道 | 本地副本 | 取新数据 | 写入 |
|---|---|---|---|---|
| 连续观察中 | 通 | 可用 | 正常 | 正常 |
| 连续观察中 | 断 | **仍可用** | 等重连 | 失败 |
| 中断，仍可续 | 通 | 已有的仍可用 | 直达服务端 | 失败 |
| 已断裂 | 任意 | **全部作废** | 必须直达，到不了则失败 | 失败 |

第二行与第三行是这张表的全部意义：**副本的可信度只取决于事件通道**；取不到新数据不等于已有的不可信。

### 接口草图

```go
// 一致性切割。实现方用读事务、MVCC 或短暂加锁取得。
Snapshot(ctx context.Context) (Snap, Position, error)

type Snap interface {
    Next(ctx context.Context, limit int) (rows []Row, done bool, err error)
    Close() error
}

// 日志。落盘与否由实现决定；要落盘就必须与树的改动同事务。
Since(ctx context.Context, after Position, limit int) ([]Change, Retention, error)
Trim(ctx context.Context, keep Retention) error

// 续订标识与对账。
Incarnation(ctx context.Context) (Incarnation, error)
CommittedPosition(ctx context.Context) (Position, error)
```

`Since` 一并返回窗口状态，是为了让「已追平／时间维度掉出／容量维度掉出」三者能被分开回答。写路径上，今天的 `Create`、`Mkdir`、`Remove`、`RemoveDir`、`Rename`、`SetAttr`、`Commit` 各自返回它分配到的位置。

## 尚未决定的

- **客户端本地副本用什么装。** 复用 `metastore.Store` 做一个内存实现（形状天然吻合：`parent_id + name`，一次目录改名就是一行），还是另起一个只读结构？前者诱人，但 `metastore` 还管配额与垃圾回收，一份只读副本不该有那些。这一条挡着接口定稿。
- 保留窗口三个数的默认值。一万条这个量级挡不住一次动两千文件的分支切换，而掉出窗口的代价是一次全树重建；一把可用的标尺是「日志窗口大到超过树本身的规模就不如重建」，但真正的取值要实测。
- 快照的条目数预算、截止时间、并发上限的默认值。
- 分块大小。太大则那条延迟义务失效，太小则吞吐受损，需要实测。
- 本地副本要不要跨挂载落盘。需求里明说这不是需求、是可能的优化，因此这一版不做，但快照与位置的形状不得把它堵死。
- R-SCALE-1 仍然是【未决】，但**不再是阻塞项**——「全量或不做」加上一个预算，让规模决定行为而不是决定设计。

## 备选方案

**TTL 缓存。** 最省事，且一秒的 TTL 字面上满足 R-CON-1。输在 R-CON-2：可见性不得在周期边界上成立。这一条单独决定了这整份 note 的存在。

**先抽快照，再拿它的位置去订阅。** 更自然的写法，少一次往返。输在不收敛：扫描耗时 × 变更速率超过窗口就永远追不上，而重建代价正比于树的大小，于是树越大越容易踩中。

**快照扫完之后拿当前尾位置盖章。** 「拉最新的」最自然的实现。输在盖章比数据新：扫描早期读到的节点若在扫描期间被改，那条事件会因为「不比章新」被丢弃，该节点**永久陈旧**且没有任何东西能纠正它。之所以要专门记下来，是因为它比正确做法更容易写出来，而错误是静默的——同一个缺陷[定序与版本](2026-08-19-ordering-and-versions.md)已经在读响应上记过一次。

**快照的每一行带上「该节点最后一次变更的位置」，扫描因此不必原子。** 真正的好处不小：分页是无状态的，服务端在页与页之间不持有任何东西，快照流断了能从游标接着爬，也不会把一个数据库资源绑在链路速度上。输在**合成日志的后端填不出这一列**——`localdir` 不记每个节点上次变更于何时，服务端要么另维护一张无界且重启即空的表，要么就没法诚实地填。原子切割两边都做得到，统一的那个赢。代价是接受「快照不能续传」。

**用 Pebble 单独存日志。** 直觉上日志就该是一个 LSM。输在它买不到落盘的入场券：日志与树不同库就无法同事务，那个崩溃缺口仍然在，还要靠启动对账去补。而 Pebble 的强项在这个量级上全都用不上——一万条约两兆，追加频率等于写文件的频率而那本来就要走一次 metastore 事务，裁剪窗口是一条 `DELETE`。代价则是服务端二进制同时背上两套存储引擎，而 server 的首要形态是嵌进别人的 daemon（R-INT-1）。

**日志留在内存里**（[变更日志的身份与作用域](2026-08-19-change-log-identity.md)当时的结论）。省掉持久状态与崩溃对账。输在加上快照之后，「每次重启都是全舰队事件」的价码变了：所有客户端同时重建就是同一时刻的多次全树扫描。化身规则让这件事诚实，不让它便宜。

**把变更流并进 `storage` 接口。** 只有一条契约。输在抬高 R-INT-6 的门槛：接入自有存储的第三方本来只需实现「一份命名空间的存取」，现在还要实现一个可续订、有保留窗口、能诚实报告缺口的事件流。

**事件只发失效通知，客户端自己回源。** 自愈——错一次顶多多一次取回，而且不要求事件生成完全正确。输在目录改名：服务端一行的改动，客户端要丢掉整棵子树重走一遍，而目录改名正是工具链最常做的操作。它还买不到多少东西——每次操作仍然要回源，只省掉一次 `List`。

**允许部分副本，按子树同步。** 冷挂载最快，也不需要 R-SCALE-1 有答案。输在它引入「哪些目录是完整的」这一整类判断，而这是整个缓存里最容易错、错了最难发现的一块。全量或不做把这一整类消掉了，代价是一个悬崖式的降级——而那个降级已经被要求可见。

## 验收标准

- 挂载立刻可用，切换到本地副本之前的行为与今天逐字相同；切换是原子的，没有「一半在副本、一半直通」的中间态。
- 冷挂载一棵树之后，`ls -R` 与路径搜索类负载不产生 RPC；这条要量出来，不是推断出来的。
- 断开事件通道并越过保留窗口，客户端明确重建，且**被告知从哪一个维度掉出**。
- 重启 server：日志持久的后端上客户端续订成功且不重建；把日志尾人为落后于 `CommittedPosition`，启动后化身改变、所有客户端重建。
- 化身不匹配时服务端回答「无法重放」，与位置超窗走同一条诚实路径。
- 快照期间持续写入，切换之后副本与服务端逐节点一致——这条是「扫描不必原子」那个论证的验收，必须有一个把写入压在扫描窗口里的用例。
- 快照截止时间到期后资源被放掉，客户端从头再来且不掉出日志窗口。
- 超出条目预算时停在直通模式，且状态查询答得出为什么。
- `mount(localdir)` 与 `mount(client)` 走同一套缓存与失效路径，差分对拍在有本地副本的配置下进行。
- 事件通道断而数据通道通时，已有副本仍然可用；转入已断裂时全部作废。

## 风险

**客户端副本的正确性完全等于事件生成的正确性，而且是永久的。** 这是 delta 换来性能要付的账。落盘之后一次漏发或错发不会被任何超时纠正，而系统里没有任何东西能在事后察觉它。唯一的防守是正确性论证与故障注入，不是自愈。

**快照期间一个数据库资源被网络速度牵着。** 截止时间与并发上限把损害框住，但框不住它存在这件事。SQLite 上表现为 WAL 涨，PostgreSQL 上表现为表膨胀，而两者都在「所有客户端同时重建」那一刻最严重。共用快照能把它从 N 份降到 1 份，但那要求服务端做单飞合并，本 note 只规定它是安全的，不规定必须做。

**内核那一层随之到期。** 三个超时从 0 变成非 0 的那一刻，内核就成了第三层我们不控制的缓存，而且它不发请求给我们就直接作答。[内核缓存与不可达](2026-08-19-kernel-cache-and-unreachable.md)已经论证过整批后果——缓存时长必须 ≤ 失活探测窗口、负项时长是挂载级常量且要更短、客户端必须自己记住答过哪些名字不存在、转入断裂时要主动令内核失效且负项优先、关掉内核自动失效之后不再自愈、失效队列溢出要升级为粗粒度而不是丢弃。那份 note 不在本 note 范围内，但**它不能晚于本 note 落地**：本地副本一旦存在而内核那一层没跟上，R-ERR-1 的违反窗口就是无界的。

**「全量或不做」是一个悬崖。** 树一旦超过预算，挂载点从「全本地」直接掉回「每 op 一次 RPC」，中间没有过渡。这是刻意的——过渡态的代价是「哪些目录是完整的」那一整类缺陷——但它意味着预算的取值会直接决定用户体验的好坏，而 R-SCALE-1 还没有答案。

**合成日志的后端永远不能持久化。** `localdir` 及任何不把位置纳入自身原子提交的后端，每次 server 重启都让它的客户端重建。这一条不是暂时的实现限制，是那条规则的直接后果，将来也不会因为「加个持久化」而消失。

**保留窗口的默认值是猜的。** 一万条挡不住一次大的分支切换，而掉出窗口的代价随树的规模增长。在有实测之前，运维踩到的第一件事很可能是这个数。
