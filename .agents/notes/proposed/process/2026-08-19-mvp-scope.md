# Agent Note: 第一个可用版本的范围

Status: proposed

## 问题

`docs/spec/requirements.md` 有 37 条需求。一次全做既不可能也不明智，必须切一刀。

难在**切错的代价不对称**：

- 少做一个**功能**，将来加上就是了。
- 少做一个**保证**，往往要返工 —— 保证通常要靠结构兑现，而结构一旦成型，加保证意味着重做。
- 还有第三类最容易被忽略：**做了一个事后无法演进的形状**。它不表现为「少做了什么」，而表现为「将来做那件事时要推倒重来」。

第三类在「简化」的名义下最容易被牺牲，因为它当下看起来什么都没少。

## 提案

目标：**证明整条链路成立** —— 一台机器写入，另一台机器在一秒内看到。范围按这个目标收窄。

### 判断标准

对每一条需求问：**推迟它，代价是「以后加」还是「以后重做」？**

- 「以后加」→ 推迟
- 「以后重做」→ 现在做
- 「以后加，但前提是现在别选错形状」→ 现在不做，但把那个形状约束写下来

### 覆盖的需求

| 需求 | 覆盖到什么程度 |
|---|---|
| R-FS-1 | 读、写、创建、删除、列目录、建目录、删目录、改名。**不含符号链接** |
| R-CON-1 ~ R-CON-4 | 完整 |
| R-CC-1、R-CC-2 | 完整 |
| R-ERR-1 ~ R-ERR-5 | R-ERR-3 只做保留与列出，不提供取出/销账/重提 |
| R-INT-1 ~ R-INT-4 | 客户端与服务端 package；daemon 与 CLI 合一的二进制；独立服务端二进制 |
| R-INT-6 | 存储可替换；提供本地目录一种实现 |
| R-INT-8 | 仅 Linux |
| R-INT-9、R-INT-10 | 抽象按三种传输都要满足的形状定义；**只实现 SSE + REST 一种** |
| R-WS-1 ~ R-WS-3 | 一个 daemon 管**一个**挂载点 |

本地目录实现同时充当验收基准：挂载点的行为可以直接与它底下那个真实目录对拍。

### 不覆盖的需求

| 需求 | 不做 | 推迟的代价 |
|---|---|---|
| R-INT-7、R-SEC-1、R-SEC-2 | 鉴权与权限校验 | 实现代价低，**但改变部署前提** |
| R-CC-3 | 写锁 / 租约 | 低。R-CC-1 用提交时的版本校验即成立 |
| R-CC-4 | 并发失败以何种形式出现 | 低。当前为提交时拒绝 |
| R-FS-2、R-FS-3 | 工具链兼容 | **中，取决于写模型** |
| R-WS-4 | 冷挂载要快 | 低。冷挂载**可用**是要求，**快**不是 |
| R-INT-5 | 不挂载的编程接口 | 低 |
| R-SEC-3、R-SEC-4 | 暂存内容的权限与位置约束 | 中。与鉴权同批 |
| R-SCALE-1、R-SCALE-2 | 规模验证 | 低。不追求性能 |

此外不做：另外两种传输、多挂载点、符号链接、离线读写、按区间惰性暂存、缓存跨重启存活。

**R-ERR-3 的取出/销账/重提不做，其后果是：失败写入的清单只增不减。**

### 保留的四条保证，以及为什么它们不能推迟

| | 为什么 |
|---|---|
| 跨机器一秒可见 | 这是系统存在的理由。它决定服务端要不要推送、客户端要不要主动失效 —— 那是结构，不是功能 |
| 并发写不静默丢失 | 用提交时的版本校验即可成立，成本很低；事后加要改写入路径 |
| 故障暴露为故障 | 这是一种纪律不是一个功能。一旦代码里到处是「出错就返回空」，事后改回来等于重写 |
| 提交失败不丢数据 | 同上。默认行为是丢，改成不丢要改的是整条写入路径的形状 |

### 只实现一种传输，且选最难塑形的那一种

选 **SSE + REST**，而不是更省事的 gRPC 或 WebSocket。

传输抽象必须是**可跨多条连接的 session**（事件流与请求响应要能独立于彼此），而 SSE+REST **天然就是两条独立连接**。gRPC 是一条连接上的多路复用，WebSocket 是一条连接加自建帧 —— 先实现其中任何一种，抽象都会被塑成「一条双向连接」，而那种形状在 SSE+REST 上根本无法实现。

**先实现最难塑形的那一种，抽象就不会被最容易的那种带偏。**

代价：HTTP/1.1 的连接池限制并发，取消语义也弱。接受 —— 不追求性能。

### 鉴权不做，且不做半套

不做身份认证，不做权限校验。任何能连上的客户端都能读写任何 workspace。

**这不是一个「安全性稍弱」的版本，而是一个没有安全边界的版本。** 它只能跑在可信网络上，任何暴露到不可信网络的部署都是错误使用。

关键的一条是**不许假装做了**：不留形同虚设的校验分支、不留默认放行的开关、不打印会让人误以为受保护的日志。

理由：半个鉴权比没有鉴权更危险 —— **没有鉴权时部署的人知道自己在裸奔，半个鉴权时他不知道。**

### 测到什么程度

分层与规则见 [`docs/testing.md`](../../../../docs/testing.md)。这里定的是**哪几层在范围内**。

必须有：

- **单元** —— 核心逻辑：命名空间视图、缓存有效性、暂存、事件应用、定序。不需要挂载点。
- **对拍** —— 挂载点与真实目录逐操作比较。这是覆盖面最广的一层，且不需要网络。
- **跨机器** —— 两个客户端 + 一个服务端。
- **故障注入** —— 只做两类：**断线**与**提交失败**。

不做：

- **其余的故障注入**（响应与事件乱序、丢事件、续订被告知无法重放）。它们对应的设计决定本身还在提案状态 —— 测一个尚未议定的行为，测出来的是当前实现而不是意图。
- **文件系统一致性套件**（pjdfstest 一类）。它验证的是完整 POSIX 语义，而我们明确不提供其中相当一部分（R-FS-4），跳过清单会比通过清单还长。对拍在同等成本下更贴合我们实际承诺的东西。
- **性能与规模**。不追求性能就不设性能门禁 —— 一个没人打算达标的指标只会被静音。

## 形状约束

以下三项不做，但**实现不得选择一种事后无法兑现它们的形状**。它们与上面的推迟项不同 —— 推迟项的代价是「以后加」，这三项若选错形状，代价是「以后重做」。

| 约束 | 细节归属 |
|---|---|
| 改名必须留得住原子性；文件大小与修改时间必须留得住精确性 | [写会话与稀疏暂存](../architecture/2026-08-19-write-session-and-staging.md) |
| `O_TRUNC` 与新建文件不得取回任何内容；将来改为按区间取，不得变成对提交形状的改动 | 同上 |
| 凭据是协议词汇里可刷新的一项，不是连接握手的属性 | 本 note |

## 备选方案

**只读挂载。** 砍掉整条写入路径，链路更快跑通。输在它证明不了这个系统存在的理由 —— 核心场景是「A 写，B 看到」，只读版本连场景都覆盖不了。而且写入路径的形状（暂存、提交、版本校验）是最容易选错、事后最贵的部分，越晚碰风险越大。

**把鉴权放进来。** 部署形态立刻可用，不必背「只能跑可信网络」这个限制。输在它不为「证明链路成立」服务，且会把凭据管理、轮换、作用域一并拖进来。推迟它的代价是「以后加」而不是「以后重做」—— 前提是位置别放错，那条已写成形状约束。

**三种传输都实现。** 直接满足 R-INT-9，也能验证抽象确实中立。输在三倍工作量，而抽象是否中立可以靠「按最难的那种塑形」在很大程度上保证。将来加另外两种若发现抽象不够，那本身就是有价值的发现，代价是加实现而不是重做。

**先做 gRPC，因为它最省事。** 工具链成熟、多路复用现成、取消语义完整。输在塑形：它会让抽象长成「一条双向连接」，而 SSE+REST 无法实现那种形状 —— 于是加第三种传输时要返工抽象。**省下的时间会连本带利还回去。**

**用写锁而不是乐观版本校验。** 语义更干净，也不会让调用方收到写失败。输在服务端要维护锁的归属与超时回收、客户端崩溃还要处理锁泄漏 —— 而版本校验只需要服务端每个文件存一个版本号。两者都能满足「不静默丢失」这条底线，选便宜的那个。

**不设「形状约束」这一类，只分做与不做。** 更简单。输在第三类恰恰是最容易被牺牲的 —— 它当下看起来什么都没少，而代价要到很久以后才显形。单列一节正是为了让它不被「简化」顺手删掉。

## 验收标准

| # | 判据 | 由哪一层覆盖 |
|---|---|---|
| A1 | 机器 A 写入并关闭一个文件后，机器 B 在 1 秒内列目录可见该文件，且读到的内容与 A 写入的一致 | 跨机器 |
| A2 | A 与 B 基于同一份内容并发修改同一文件，先提交者成功，后提交者收到失败；文件最终内容是先提交者的，完整无损 | 跨机器 |
| A3 | 断开与服务端的连接后，读取一个此前未访问过的文件返回 I/O 错误；列目录返回 I/O 错误而非空列表 | 故障注入（断线）+ 跨机器 |
| A4 | 令一次提交失败，该次写入的内容仍可被找回，且系统能报告这次失败发生过 | 故障注入（提交失败） |
| A5 | 对挂载点与一个本地目录执行同一串文件操作，产生的目录树、文件内容、以及错误码一致；任何差异必须是 `docs/spec/problem.md` 中明确列出的非目标 | 对拍 |
| A6 | 客户端与服务端 package 可被第三方程序链接：不注册信号处理、不写 stdout/stderr、不调用进程退出、不设置进程级参数 | 单元 + 真实入口 |
| A7 | 代码中不存在任何形同虚设的鉴权：没有被绕过的校验分支、没有默认放行的开关、没有暗示「已受保护」的日志或输出 | 反向判据 |

**A5 最有价值**：它不需要预先枚举「应该怎样」，而是拿一个真实目录当作标准答案。

**A7 是一条反向判据** —— 它要求某种东西*不存在*。写成验收条款，是因为「鉴权不做」在实现时最容易退化成「鉴权做了一半」。而反向判据比普通测试更容易变成摆设：**A7 必须被「引入一处形同虚设的鉴权 → 看它变红 → 撤销」验证过**，否则它证明不了任何事。

**A3 与 A4 各自对应一类故障注入，而那两类正是范围内的两类** —— 这不是巧合：范围就是照着必须验收的东西划的。

## 风险

**「只能跑在可信网络上」很容易被忽略。** 一个能跑通的东西会被人拿去部署。除了文档，启动时的输出也应当说明这一点 —— 但不做的东西不该悄悄长出功能，所以这条只是提醒，不是交付项。

**「先按最难的传输塑形」是一个赌注。** 它赌的是 SSE+REST 的形状是三者的上界。若将来发现 gRPC 或 WebSocket 有它无法表达的需求（例如真正的双向流），抽象仍然要返工 —— 只是方向反了。目前没有证据表明存在这样的需求，但这个赌注应当被记下来。

**四条保证里没有一条是可测量的性能。** 一秒可见是延迟上界，但没有吞吐、没有并发规模、没有冷挂载时限。这是刻意的，代价是「跑通了」与「能用」之间还有一段没有验收覆盖的距离。
