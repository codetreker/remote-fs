# Agent Note: 补足 SQLite 各包自己的测试覆盖

Status: proposed

## 问题

[现行覆盖率规则](../../../../docs/testing.md#覆盖率是必要的从来不是充分的)只由一个包自己的测试二进制为该包计入覆盖率。`internal/integration` 验证公开入口的组合行为，但它执行的 SQLite 调用不增加其它包的覆盖率。已有用例通过，不能证明每个内部组件都有足够的包内测试。

对 [`packages/metastore/sqlite/...`](../../../../packages/metastore/sqlite) 使用 Go 默认包内统计，以 `GOMAXPROCS=2`、`-count=1`、`-timeout=10m`、`-p=1` 测量，263 个顶层测试和包含子测试的 831 个判定均通过，没有失败或跳过；覆盖结果仍未达到现行门槛：

| 包，相对于 `packages/metastore/sqlite` | 包覆盖率 | 低于 50% 的函数数 |
|---|---:|---:|
| 根 package | 80.50% | 12 |
| `internal/changes` | 6.65% | 21 |
| `internal/dbstate` | 0.00% | 12 |
| `internal/nativelease` | 70.15% | 11 |
| `internal/schema` | 0.00% | 26 |
| `internal/sqlerr` | 68.00% | 10 |
| `internal/sqlvalue` | 0.00% | 8 |

这七个生产包的语句合计覆盖率为 57.37%，共 100 个函数低于 50%；它是 SQLite 子树的测量，不是全仓库的覆盖率。全仓库结果尚未测得，不能从这些数字推断全仓库 85% 门禁是否通过。根包与 nativelease 达到包级 70%，也仍有未达标函数。

## 提案

按[SQLite 模块边界](../../implemented/architecture/2026-09-09-sqlite-internal-modules.md)，在生产代码所属 package 的测试二进制中补足局部断言，保留现有 integration 用例的组合验证职责。测试文件继续按 `xxx.go` 对应的 `xxx_test.go` 归组。

局部用例须验证结果和失败语义，不只调用函数以经过语句。重点包括持久状态与身份边界、schema 迁移和完整性、日志裁剪与 page 预算、原生证据失败、错误分类，以及根包的构造、checkpoint 和 replica 分支。已有原子顺序、资源限制、取消与错误链不能为达到数字而被改写；不为测试开放额外生产入口。

## 备选方案

尚未比较具体的补测分配方案。实施时可复用既有场景或建立组件自己的局部 fixture，但只运行其它包的用例不能满足本包的覆盖门槛。现有 integration 用例继续提供独立的组合行为证据。

## 验收标准

- SQLite 子树递归运行全部用例，失败、跳过、缺少判定与缺少测试继续按现行规则处理。
- 仅使用各包自己的测试二进制统计，七个生产包各达到 70%，每个函数达到 50%；有实际执行块的 profile 与函数报告能对应到同一份源码。
- 测试对成功结果、边界拒绝、取消和真实故障分别作出可观察断言；原有集成用例、公开 API、schema 字节与生产行为保持不变。
- 全仓库 85% 合计门槛继续由全仓库测量独立裁定，不用 SQLite 子树百分比替代，也不通过降低阈值、改变排除规则或跨包合并覆盖数据取得通过。

## 风险

延后期间，SQLite 的测试可以全部通过而包内覆盖门禁仍失败。缺少局部用例的组件难以独立验证其分支和失败结果，组合用例不能代替这个缺口。

补测可能增加重复 fixture 与执行成本；应复用准备数据和明确的职责，避免复制整套集成环境或只追逐百分比。全仓库还可能存在其它包的覆盖缺口，本提案只处理已测得的 SQLite 范围，不代表那些工作已被评估或完成。
