# Agent Note: 新句柄不得读到旧句柄填入的页缓存

Status: proposed

## 问题

严重级别：P1。[R-CON-1、R-CON-3](../../../../docs/spec/requirements.md) 要求已提交内容在一秒内可见，读取不得混合不同提交的内容。FUSE 的每个句柄保存自己的整文件缓冲区，但 [Open 返回的 flags 为 0](https://github.com/codetreker/remote-fs/blob/252259f1b89682a5b2acf54004f0fe8b8677528d/packages/fuse/node.go#L318-L339)，内核仍可在同一 inode 的句柄之间共享内容页。

在该提交上，以 SQLite metastore 与 memory object store 挂载文件系统：先写入 1 MiB 的 `A`，打开旧句柄；通过 storage 将同一节点覆写成等长的 `B`，等待 1200 毫秒，再打开新句柄。旧句柄先读取首个 4096 字节，新句柄随后读取同一范围，得到的仍是 `A`；当前已提交内容与新句柄取回的内容都是 `B`。旧句柄重新填入页缓存，因此单在新句柄打开时失效不能证明后续读取正确。

## 提案

让 FUSE 内容缓存策略与句柄持有的版本一致，保证旧句柄之后的读取不能污染新句柄。保留[节点身份与 inode 分层](../../implemented/bug-fix/2026-09-01-a-name-is-not-an-identity.md)；身份相同不意味着内容版本相同。具体缓存机制待实现前比较。

此项拥有跨句柄页缓存隔离；[缓冲区与长度的一致性](2026-09-07-bind-buffered-reads-to-their-size.md)单独验收。[打开文件的身份钉住](../architecture/2026-08-20-nothing-pins-an-open-file.md)继续拥有按旧路径提交可能写到另一节点的写入问题。

## 备选方案

未比较具体实现方案。[元数据复制](../../implemented/architecture/2026-08-27-metadata-replication.md)中的三个属性及目录项超时不控制内容页；[内核缓存与不可达](../architecture/2026-08-19-kernel-cache-and-unreachable.md)拥有完整的缓存失效与故障行为设计，本项修复不得将那些尚未实现的保证视为已有能力。

## 验收标准

- 在真实 FUSE 挂载上重现上述顺序，新句柄每次读取均得到 `B`；旧句柄在新句柄打开后继续读取也不能改变该结果。
- 覆盖多页与交错读取，任何成功读取不得拼接不同版本；在已提交覆写一秒后新打开的句柄能读到新内容。
- 节点身份、内容大小限制与现有读写错误语义继续成立。

## 风险

延后的是内容可见性保证，代价是普通读取继续可能成功返回旧字节。缓存策略改变可能增加 FUSE 调用或改变映射行为，需实测其影响；不能以缩短超时或延迟重试作为正确性的依据。文件写入的身份钉住与并发提交控制仍由各自提案拥有。
