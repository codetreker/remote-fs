# Agent Note: 持续读取不得饿死副本更新

Status: implemented

## 问题

[R-CON-1](../../../../docs/spec/requirements.md) 要求跨客户端变更在一秒内可见，频繁列目录是正常使用场景。[`Replica.lockExclusive` 通过 `TryLock` 与一毫秒定时器争抢写锁](https://github.com/codetreker/remote-fs/blob/252259f1b89682a5b2acf54004f0fe8b8677528d/packages/metastore/sqlite/replica.go#L361-L381)，等待中的写者不能阻止新读者进入。持续 `List` 可以使变更无法应用，而读取仍成功提供旧副本。

在该提交上，4096 文件的副本由 128 个 goroutine 持续列目录。修改根目录 mode 的 `Apply` 在两秒 deadline 前一直未能取得独占锁，期间完成了 1257 次列目录；停止读者后，同一变更立即成功。轮询争锁把更新能否推进交给了读者是否碰巧全部空闲。

读者在 SQLite reader pool 中排队时尚不能执行查询，却可能已经取得 replica 共享访问。写者因此要等待整条队列逐批扫描完成，而不仅是同时能执行的查询。目录越大，这批尚未执行的读取对变更可见性的影响越大。

## 决定

SQLite replica 先限制能进入读阶段的 SQL 查询数量，再用私有读写门协调 `Apply`、`Reseed` 与元数据查询。门在读阶段和写阶段之间交接，等待直接受调用 context 控制，不使用轮询、辅助 goroutine 或逐等待者队列。

### SQL 查询先取得名额

`Stat`、`List` 与 `ListBounded` 先取得 SQL 读取名额，再申请共享读阶段。名额数来自创建 reader pool 的同一份 `Options.MaxReaderConnections`，默认 16，不另设一组上限。等待名额的调用不持有读阶段，也不延长写者必须等待的读取集合。

取得名额或进入阶段都受调用 context 控制。等阶段失败时归还名额；查询结束时先退出读阶段，再归还名额。`Position` 不查询 SQLite，直接取得共享阶段；`Apply` 与 `Reseed` 直接取得独占阶段，都不消耗 SQL 读取名额。

### 读写阶段的交接

- 写者先登记等待意图，再等待现有读者退出；之后到达的新读者不能延长这一轮读取。
- 一项写操作结束时，把已经等待的读者划为有限的一批，并在唤醒前为整批预留读名额。后续写者必须等待活跃读者与这批预留读者全部离开。
- 已有写者等待时，随后到达的读者进入下一批，不能加入已预留的一批。没有写者等待时允许读者并发进入。
- 等待取消只撤回调用方尚在等待或已被预留的那个名额，并触发剩余调用需要的交接；已取消调用不留待后台取得锁。

这项次序同时阻止新读者绕过等待的写者，以及连续写者绕过已经等待的读者。多个写者之间不承诺 FIFO；阶段交接也不限制已经获准执行的 SQLite 查询或整个快照灌入需要多长时间。

### 所有权与资源

`Reseed` 在整个灌入期间持有独占门和 SQLite write transaction，直到 `Seeding.Complete` 完成事务或 `Seeding.Close` 中止；`Add` 或 `Complete` 的前置校验失败仍要求调用方执行 `Close`。读者不会观察到半棵树。需要两层同步的操作按 replica 门、commit gate、database health lock 的顺序取得所有权。`Position` 没有 context，等待共享访问；`Replica.Close` 继续把关闭交给其持有的 store。

门只保留固定数量的计数、阶段状态与共享唤醒通道，SQL 名额由容量与 reader pool 一致的通道持有。不按等待调用数保存队列节点，也不为等待创建 goroutine。等待调用仍在调用方的 goroutine 中；这项选择复用 R-INT-3 已有的读取并发上限。

### 范围

本决定补足[元数据复制](../architecture/2026-08-27-metadata-replication.md)的可取消读写准入与推进。它修复的是 R-CON-1 所依赖的本地更新进展；锁本身不给整个复制链路作一秒承诺。

快照重建后过早作答、文件页缓存陈旧与首次订阅取消各有独立的可用性或生命周期条件，仍需分别处理。读写门不改变这些条件，也不引入新的取消错误分类；它保留独立改进这些路径的空间。

## 备选方案

**所有等待写者优先。** 现有读者退出后让写者一直先行，可以保证 follower 推进；持续变更却可能让元数据查询长期不能进入。有限读者批次把这项代价约束在一次阶段交接内。

**`x/sync/semaphore.Weighted`。** 有成熟的 context 等待和队列次序，但需要新增依赖，并为等待者保存队列节点。采用它还须给队列单独定义可配置的资源上限；私有门只需类间交接，不需要逐调用 FIFO。

**直接用 `sync.RWMutex` 阻塞等待。** 标准读写锁会阻挡后来读者，但阻塞调用不能响应 context；为此给每个等待者另起 goroutine，会在取消后留下仍在抢锁的调用和资源。

**用一个互斥锁串行化所有访问。** 可以统一读写次序，却让本可并行的元数据查询相互等待。私有门保留共享读阶段。

**只给观察查询更高优先级。** 可以让 `Stat` 等查询更快通过，却把同一份副本的读取分成不同优先级，也没有缩小已经取得共享阶段、仍在等待 SQL 连接的集合。统一限制进入阶段的 SQL 查询数，直接约束写者必须等待的扫描工作量。

**继续缩短 `TryLock` 轮询间隔。** 只能改变争锁概率，不能阻止新读者持续占住共享访问，也增加空转与定时器活动。

## 后果

持续读负载下，已经登记的写者等待的是受 reader pool 并发数约束的读阶段；其余 SQL 读取先在门外等名额。连续写负载下，已经等待阶段的一批读者在一次写操作结束时取得保留的执行机会。SQL 读取仍能并行，队列不能把一批有限查询扩展成全部在途调用。

一秒可见性由正常运行的真实 HTTP/SSE 全负载验收判定；带 race instrumentation 的并发测试判定阶段交接、取消与死锁，不用其耗时替代生产延迟。整个 tagged replicated package 的串行验收通过；4096 文件和 128 个持续读者下，变更在 316.970969 毫秒可见，计时窗口内另完成 110 次有效列目录。这是该负载的一次观测，不构成所有环境的延迟上限。验收固定在 CI 的串行步骤中执行，夹具与命令见[测试策略](../../../../docs/testing.md#元数据副本的读写交接)。

代价是新读者可能等待一次写操作，后续写者可能等待一批读者；被唤醒但尚未获调度的预留读者也会延后下一项写入。

取消可以结束等门的调用，无法强制中断已经进入的不可取消操作。持有独占权的整次 reseed 仍会阻挡查询。进展还依赖持有者最终退出、预留读者得到调度或取消，因此不承诺 wall-clock 锁等待上限，也不承诺多个写者之间的逐调用公平性。

固定状态避免把公平性变成新的无界等待队列；代价是共享通知可能唤醒多个竞争者，由它们在门内重新检查是否轮到自己。阶段与预留计数共同决定准入，不能只凭收到通知就进入。
