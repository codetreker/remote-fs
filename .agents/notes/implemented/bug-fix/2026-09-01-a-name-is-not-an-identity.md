# Agent Note: 名字不是身份

Status: implemented

## 问题

一个挂载点上持有着打开的文件描述符，另一个挂载点在同一个卷上做**普通的原子保存**——写 `doc.tmp`，然后 `rename` 覆盖 `doc.txt`。那个描述符之后读到的，既不是它打开的那个文件，也不是新文件，也不是错误：

```
before: b'VERSION-ONE-VERSION-ONE\n'   (24 字节)
after:  b'VER'                          (3 字节)
ino:    2 -> 2       size: 24 -> 3
```

**旧文件的字节，按新文件的长度截断。** 没有任何错误信号。

这是 R-CON-3 的字面违反——「其它客户端读到的要么是旧内容、要么是新内容，不存在两者的混合」。而原子保存是编辑器、编译器、包管理器、git 全都在用的模式，不是边角情形。

**不是复制引入的。** 当时关掉复制（`-dir` 后端不建副本）逐字节复现相同，所以它在 `packages/fuse`，与 [元数据复制](../architecture/2026-08-27-metadata-replication.md) 无关。下表保留当时两个后端的观测；`-dir` 已由[移除宿主目录后端](../simplification/2026-09-08-remove-the-host-directory-backend.md)取消：

```
dir   replica=no    -> b'VER'   ino (2,2)  size (24,3)
blob  replica=yes   -> b'VER'   ino (2,2)  size (24,3)
```

## 根因

两个成因，都是**拿名字当身份**。

**一、inode 号按名字记账，而记账只被本挂载点自己的操作更新。**

底下什么都不提供：`storage.Attr` 只有 `Mode / Size / AccessTime / ModTime`，没有任何节点身份。所以 `packages/fuse/identity.go` 自己发号，`identity.children[name]` 是「哪个号属于哪个名字」的记录。

这份记录只有五个更新入口，全部是「这个挂载点自己做了什么」：`Lookup` 返回 ENOENT、`Unlink`、`Rmdir`、`Rename`、以及列目录时的 `keepOnly` 剪枝。**别人做的改名，一个都不经过。** 名字还在，所以 `Lookup` 不返回 ENOENT；本地没有删除或改名；`keepOnly` 只清理「列表里消失的名字」。于是 `doc.txt → 2` 原封不动地活下来，而 2 后面已经是另一个节点了。

`identity.go` 开头的注释**一字不差地描述了这个 hazard**：

> 两个活着的节点报成同一个号，对内核就是一个节点：它会把其中一个按另一个的长度去映射，在那里读的程序吃 SIGBUS。……路径也不能充当身份——改名把一个节点挪到别的名字上并释放它原来那个，而之后在那里创建的是第二个、不同的节点，却会被给到第一个的号。

设计看见了这件事。漏掉的是下一步：「释放它原来那个」只发生在**执行改名的那个挂载点**上。

**二、`Getattr` 按路径作答。**

这才是真正把读截断的那一半。一个已打开的节点被问属性时，`storage.Stat(ctx, n.path())` 问的是**现在占着那个路径的东西**，于是返回新节点的 size=3。内核不会去要它认为不存在的第 4 个字节，所以 `handle.Read` 只被要走 3 个字节——而 `handle` 攥着的是打开时快照下来的旧内容。

对照实验把两半分得很清楚：在**执行改名的那个挂载点**上，`move()` 跑了、记录是对的、inode 从 108 变成 109，而持有的 fd 拿到 `ENOENT`（也不对，但它是**响**的）。在另一侧，inode 172 → 172，静默给出错的字节。

## 决定

**先补需求。** `docs/spec/requirements.md` 里关于文件身份一个字都没有——搜过 identity、inode、唯一性，全都没有。所以这不是「写了没实现」，是需求缺了一条，而仓库规定一切都在 `docs/spec/` 下游。新增 **R-FS-5**：每个节点在其卷内有一个身份，挂载点必须把同一个身份始终呈现为同一个 inode 号，把不同身份呈现为不同的号，且已消失节点用过的号不得再指向别的节点；身份跟随节点走过改名；**这一条在变更由别的挂载点或别的客户端做出时同样成立**。

**当时身份走 `storage.Attr`，不直接用作 inode 号。** 这项选择以当时后端的身份保证为前提。

当时的直觉方案是「直接拿卷的 id 当 inode 号」，把 `identity.go` 整套发号逻辑删掉。它输在 `localdir`：那个后端能给的身份是宿主的 `st_ino`，而**宿主会在节点消失后立刻把号收回去重发**。inode 号一旦交给内核就永远不能再指向第二个节点，`st_ino` 给不了这个保证。该后端已退出交付，现有原生卷提供稳定且不复用的节点 ID。

当时由挂载点自己发出单调且不复用的号，只用卷内节点身份判断同名节点是否变化。[实时文件句柄](../architecture/2026-09-08-live-file-handles.md)改为直接将稳定 node ID 报成 inode 号，使另一个挂载改名到本地从未见过的名字时仍保持同一编号。名字树继续记录成员关系；本地 serial 仅区分列目录前后得知的成员，不作为 inode。第三方也必须兑现节点身份不复用，挂载层不再用另一个计数器代替该义务。

身份本身**早就存在，只是被扔在边界上**——当时 `metastore.Node.Attr()` 用四个字段构造 `storage.Attr`，把 `n.ID` 丢了；该决定落地时，SQLite 的 no-reuse 依据是 `nodes.id` 的 `AUTOINCREMENT`。当时 `localdir` 的 `attrOf` 也已在解 `Stat_t`（为了 `Atim`），`Ino` 就在旁边，两处各一行。SQLite 对 sequence 损坏与回退的持久证明由[显式身份高水位](./2026-09-07-persistent-sqlite-identities-use-explicit-high-water-marks.md)补足，不改变这里的 storage/FUSE 身份分层。

**当时 `Getattr` 在 dirty 或路径身份变化时从 handle 报大小。** 它保留打开时的内容，只有 dirty 或当前路径身份变化时才覆盖卷的大小，因此没有处理同身份覆写后的长度混用。[实时文件句柄](../architecture/2026-09-08-live-file-handles.md)接续这条读取路径：handle 持有同一对象的远端引用，属性与范围读取回到该对象；`ReadAt` 的字节、大小与 EOF 来自一次修订捕获，不再从旧缓冲区与当前路径拼合答案。[缓冲内容与长度](2026-09-07-bind-buffered-reads-to-their-size.md)及[跨句柄页缓存](2026-09-07-prevent-cross-handle-page-cache-staleness.md)分别保留缺陷与验收记录。

**契约里 0 非法。** 一个忘了填的后端会让每次身份比较都相等——也就是把所有节点报成同一个节点，静默地退回今天这个 bug。契约测试套件因此拒绝 0。

## 备选方案

**拿卷的 id 直接当 inode 号。** 上面说了，输在 `localdir` 的 `st_ino` 会被宿主回收，而交给内核的号不能回收。

**让 storage 支持按身份 stat（`StatByID`）。** 这样已打开的节点就能问「我自己」而不是问路径。输在 `localdir` 做不到：没有办法按 inode 号定位一个文件，除非扫整棵树。而 handle 已经握着答案。

**在 `Getattr` 察觉身份变了就答 `ESTALE`。** 诚实，而且是 NFS 的做法。输在它对原子保存的读者没有帮助——那个读者要的是继续读它打开的文件，POSIX 也是这么规定的，`ESTALE` 只是把静默的错换成响亮的错。

**要求 `Write` 保留身份。** 契约本来会更强。输在**在本地文件系统上，原子替换内容和保住 inode 不可兼得**：`localdir` 靠「写临时文件再 rename」满足契约里那句「替换是原子的」，而 rename 必然换 inode；改成就地截断写就丢掉原子性，撞上 R-CON-3。两个后端在这里的行为是真的不同，而且是被逼的，所以契约两个都不要求，并在测试里写明为什么不问。

**要求「删掉再同名创建」得到新身份。** 同理，宿主会立刻把 `st_ino` 收回。代价有界并写了下来：一个被回收的身份只会让比对**漏判**，不会让它**说谎**，而内核看到的号仍然由挂载点发、永不复用。

## 后果

**当时买到的**：跨身份替换后，handle 的属性答复保留其缓冲区长度，并修正「一个名字被改名覆盖之后，在另一侧沿用旧 inode」的问题。该修复留下的同身份长度与页缓存问题由两份独立缺陷记录继续承载；当前按对象实时读取与 directIO 的选择由文件句柄决定拥有，不把原来的有限修复追记成完整验证。

**当时没有修复目录改名后另一侧子树重编号。** 名字索引在新路径下没有记录，child 会新发编号，身份比较只能让已有记录失效。当前直接使用 node ID 去除了这项重新发号的原因；这不证明目录父关系正确，[目录父身份跟进项](../../proposed/architecture/2026-08-20-nothing-pins-an-open-file.md)仍记录延迟 Lookup 与路径派生操作的源码推导竞态。

**当时的代价一：`Write` 在 `localdir` 上会换掉节点身份。** 在该后端的挂载点上写一个文件，inode 号会变；这是当时契约接受的后端差异。该后端已经移除，现有对象存储通过更换内容引用保留节点身份。

**当时的代价二：删掉再立刻同名创建，在 `localdir` 上仍可能沿用旧 inode。** 宿主回收 `st_ino`，比对因此漏判。这一后端缺口随实现移除；它不能成为第三方复用身份的许可，R-INT-11 仍要求不同对象不得被呈现为同一个对象。

**当时的代价三：干净 handle 的时间戳仍来自卷。** 一个跨越身份变化持有的描述符，会报出旧内容的长度配上替换文件的时间。当前 `File.Stat`、`File.ReadAt`、`FileSession.StatNode` 按身份访问；已有引用不因改名、unlink 或同名替换转向替代物，后续读取也不冻结在打开时的内容。

**没有覆盖到的**：两个写者并发。每一处测量都是一个写者——一个挂载点写、另一个读。而这次确认的缺陷本身就是「非发起方那一侧的节点身份」问题，下一个大概也在那里。
