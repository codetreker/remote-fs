# Agent Note: 让测试工作量与判据对应

Status: implemented

## 问题

部分拒绝矩阵在每个子用例重新建立同一套真实后端，但被检查的结果正是“调用失败且状态不变”。副本确认用例则在建立挂载时就延迟事件流，使尚未进入被测确认阶段的初始化也承担等待。它们重复支付了准备成本，却没有增加对应拒绝或确认断言的覆盖。

另一些错误路径取决于两个真实故障谁先返回。响应失败和 follower 失败同时发生时，端到端用例可以正确拒绝修改，却不能稳定覆盖“服务器已成功、随后无法确认”的特定分支。测试需要分别证明具体错误语义与真实双故障交错。公共 storage 原子替换契约的重复写入次数还决定统计暴露与耗时，需要在保留检测证据的前提下单独作取舍。

## 决定

### 拒绝矩阵在不变性检查下复用后端

[SQLite 匿名发布矩阵](../../../../packages/metastore/sqlite/publication_test.go)为 S、X 各建立一份真实 fixture，共两份。每种权限仍按原顺序执行九种操作，共 18 个 leaf；每次调用前后的 List、Space 与 Conflict 分类断言保留。调用前还与该权限 fixture 的初始列表、配额比较，上一项拒绝若污染状态，下一项会明确失败，不能把污染当作新的基线。

[HTTP 构造选项的两个矩阵](../../../../packages/transport/httprest/server_test.go)分别复用各自原有的 failingStorage 包装器。每个子用例从完整 options 值复制后只破坏原定字段，继续调用原来的 Check／constructor。可用配置与零值默认配置仍成功；后端保留真实能力与原错误行为，不能靠换一个总是拒绝的替身让非法选项用例通过。

复用限于这些不应改变后端的拒绝检查。会修改状态、测试构造失败清理或验证持久状态形成的用例保留各自 fixture；没有加入新的 detached 完整性种子复制。

### 确认用例在初始化完成后控制事件交付

[副本 harness](../../../../packages/storage/replicated/harness_test.go)的事件门在真实 bootstrap 时放行，挂载完成后才 arm。在调用 ResponseWriter.Write 之前阻塞，避免字节被 net/http 自动 flush 提前暴露；用例必须先观察门已进入，再执行取消、容量或 Close 断言，并在原有最终到达／结束位置释放。请求 context 取消时，等待返回原 context 错误。

仅五个确认、准入及 Close 用例使用这道门。确认失败的两秒 grace、容量用例的五秒／十秒 grace、二十毫秒 waiter 观察和一秒 Close 上限都保留，服务器调用次数、错误原因、旧副本健康、最终到达、树一致与重连断言不变。其它 delay、snapshot、replay 与全负载可见性用例继续拥有原来的时间条件。

### 确认失败分支有独立的确定性用例

[bookkeeping 用例](../../../../packages/storage/replicated/bookkeeping_test.go)让一次实际进入 change 的发送回调返回成功 barrier，确认开始前 follower 已失败。它分别把本地位置放在 barrier 之前和已经到达的位置，核对发送回调仅调用一次、PathError 的操作与路径、EIO、已发生修改但副本失去更新的诊断，以及 confirmation／waiter 容量全部释放。

原有真实 HTTP 双故障集成用例保持原样，仍允许观察先到达的响应或 follower 错误。它不承担某个竞争分支必然获胜的假设；确定性用例也不能替代真实请求、流断开和副本之间的集成验证。

### 原子替换以 100 次写入保留定量观察

[公共 storage 原子替换契约](../../../../packages/storage/storagetest/storagetest.go)执行 100 次交替写入，保留两个读者、128 KiB／96 KiB 两种内容、没有固定次数上限的读循环、Gosched、原错误接受规则与每次完整值断言。减少的是反复暴露于调度的写入次数，不是对内容完整性、错误或最终结果的要求。

采用较小计数须同时满足配对耗时、每个读者看到两种值、写入 API 区间重叠、非原子负向对照和逐包覆盖集合的检查。它接受较少统计暴露；先前以 200 次写入验证调度的理由与数据保留在[原决定](2026-09-09-reduce-test-work.md)，不把更短运行视为所有竞争场景等价。

## 备选方案

**每个拒绝项重新构造后端。** 自然隔离，但重复准备相同 authority、内容与元数据。按权限或矩阵复用可以减少准备，前提是保留逐项前后断言，并拒绝跨项状态污染。

**从 bootstrap 开始延迟整条事件流。** 它能制造未确认结果，但把初始化也放入无关等待。初始化后控制交付点可以保留确认阶段的真实停顿；专门断言慢 snapshot 或 stream 时序的用例仍使用延迟。

**只依赖真实双故障用例覆盖 follower 失败。** 它保留真实交错，却可能由响应错误先结束调用。独立驱动成功响应后的 follower 失败，才能稳定验证该分支的结果与容量释放；两个用例各自保留。

**保留 200 次写入，只优化准备和等待。** 它保留更长统计暴露，但在两种实际后端上重复付出约两倍工作段时间。采用 100 次同时受正向观察、负向检出与逐包覆盖集合约束，不能单凭少跑一半的速度决定。

## 后果

SQLite 拒绝矩阵的真实准备从 18 份减为 2 份，18 个 leaf、操作次序与每次调用的状态断言不减少；HTTP 两个矩阵分别只准备一次原有包装器。共享后端增加了测试对不变性和正确 cleanup 归属的依赖，不能通过重置或吞掉错误来隐藏污染。事件门减少初始化阶段的等待，不缩短被测 grace 或 Close 上限。

相同 Go 1.26.8、环境与 flags 的各一次普通整包运行中，SQLite 拒绝矩阵从 0.36 秒变为 0.06 秒，HTTP 两个矩阵合计从 0.57 秒变为 0.04 秒，五个副本用例合计从 35.03 秒变为 2.53 秒。这些是单次用例耗时观察，不是隔离的 benchmark，也不能据此推算 CI 作业耗时。

Go 1.26.8、GOMAXPROCS=2 的三组 race 正向配对测量中，带 API 区间采样的 native publication 工作段中位数从 8.2957 秒降为 4.0559 秒（51.11%），unmanaged bounded 从 9.4511 秒降为 4.7105 秒（50.16%），没有更慢的配对。每个读者在写者运行期间看到两种完整值，并与全部写入 API 区间重叠。两种实现、200／100 次写入各十次无额外延迟的非原子负向对照，40 个 leaf 均因实际 torn read 在指定断言失败，未将 panic、race 或其它运行时故障当作检出。

六个相关包按各自测试二进制的默认覆盖统计比较，覆盖块集合逐包与基线相同，共 4887 个已覆盖块；原 2236 个判定名称全部保留，另增加 3 个确定性 follower 失败回归判定。67 个针对修改路径的 race 判定通过。这些是局部验证，新的完整 CI 和端到端耗时各自判定。

覆盖块未减少、有限负向对照通过和 API 区间重叠，都不能证明内部竞争窗口具有相同检出概率。100 次写入减少遇到长尾时序的机会；更窄窗口或新缺陷若不能被稳定检出，应增加定向交错或恢复所需负载。不能以包覆盖率相同掩盖这个统计代价。

这些调整沿用[先前测试工作决定](2026-09-09-reduce-test-work.md)的真实后端与隔离约束；该记录中的历史数据和取舍保留。包划分、两个 CI 作业、race、`-count=1`、错误判定、[包内覆盖门禁](2026-09-09-sqlite-package-local-coverage.md)与执行预算均不放宽。局部准备成本和整条 CI 耗时分别验证，不能把覆盖到同一代码块等同于覆盖所有竞争窗口。
