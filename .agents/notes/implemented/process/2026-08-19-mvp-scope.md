# Agent Note: 第一个可用版本的范围

Status: implemented

## 问题

这次范围决定提出时，`docs/spec/requirements.md` 有 37 条需求。一次全做既不可能也不明智，必须切一刀。

难的不是「哪些功能先做」，而是**切到什么深度**。一个包含了并发校验、断线分级、资源治理、鉴权落点的第一版，仍然可以是一个诚实的最小集合 —— 它的每一条都能论证成「不做就要返工」，而且那些论证多半是对的。它输在别处：它需要的时间足以让「链路到底成不成立」这个问题一直悬着。

第一版的用途是回答那个问题，不是把方案做完备。

## 决定

第一个版本只回答一件事：**这两行命令能不能跑通。**

```
机器 A:   echo hello > /mnt/ws/a.txt
机器 B:   cat /mnt/ws/a.txt        →  hello      （一秒内）
```

其余一切不在范围内。

### 当时的组成

| 包 | 做什么 |
|---|---|
| `packages/storage` | 一份命名空间的接口，以及它的 errno 词汇 |
| `packages/storage/storagetest` | 这份接口的契约测试套件，住在任何实现之外 |
| `packages/storage/localdir` | 把接口落到一个真实目录上 |
| `packages/transport/httprest` | 一个 `http.Handler`，与一份走 HTTP 的 storage 实现；消息形状两端共用 |
| `packages/fuse` | go-fuse 适配：把一份 storage 呈现为本地目录 |
| `cmd/remote-fs-server`、`cmd/remote-fs` | 两个二进制 |

该组成表与本文的原始测量保留当时如何验证链路的依据。[移除宿主目录后端](../simplification/2026-09-08-remove-the-host-directory-backend.md)已经取消 `localdir` 与 `-dir`：当前独立服务端提供 localstore 与 Azure Blob，两者共享对象命名空间与 SQLite；存储契约、挂载层与传输的分层继续成立。

### 不在范围内

鉴权、权限、凭据 · 乐观并发校验、写锁 · 断线分级（观察中／中断／断裂）、保留窗口、事件重放、日志化身 · 未确认写入的保留与清单 · 暂存预算、稀疏暂存、按区间读 · 分页 · 不透明节点身份 · workspace 的生命周期（R-WS-1～4：长期存在、频繁挂载与卸载、冷重挂、冷挂载后的响应速度）· 新建符号链接与硬链接 · 多挂载点、daemon 控制面 · gRPC、WebSocket

当时 `.agents/notes/proposed/architecture/` 下的九份 note 覆盖了上面绝大部分；这次范围切分没有否决它们。[显式文件锁](../architecture/2026-09-07-file-locks.md)已经部分替代其中推迟写锁的决定：S/X、Session / Owner、有界动作历史与重启保护进入交付范围。普通内容版本校验、FUSE `Open` 自动取得权限与失败本地写入的保留仍是各自的未完成工作。

### 没有缓存，因此也没有变更推送

`packages/fuse` 把内核的 entry、attr 与负项超时都设为 0，每一次内核调用都变成一次 storage 调用。

于是 R-CON-1「一秒内可见」自动成立：**没有缓存，就没有会过期的东西。** 机器 B 的每一次 `stat` 都打到服务端，看到的永远是当前事实。

这条是可执行的：`TestEveryLookAtTheNamespaceReachesIt` 用一个计数的 storage 断言连续两次 `stat`、两次 `ls`、两次读都各自到达了命名空间。把三个超时改成 1 秒，它变红。

变更推送的存在理由是让缓存失效。没有缓存就没有要失效的对象，所以事件流整个不在第一版里 —— 它不是被推迟的功能，而是一个此刻没有作用对象的机制。

代价：每一次 `ls`、每一次 `stat` 都是一个网络往返。**能跑，但在真实负载下不可用。** 缓存与变更推送是同一件事的两半，必须一起做，那是这一版之后最先做的事。

### 唯一保留的纪律：不掩盖错误

这不是功能，也不增加代码量 —— 写一个 fallback 比不写多几行。

够不到底层就返回错误。不返回空目录、不返回「文件不存在」、不返回过期内容而不加说明（R-ERR-1、R-ERR-2）。

保留它的理由与工作量无关：一个文件系统在够不到服务端时报告「文件不存在」，会让跑在它上面的东西执行破坏性动作 —— 重新生成、传播删除、覆盖写入 —— 而且不可恢复。这类口子一旦在代码里开了，事后要一处一处找回来，而每一处都是静默的。

同一条纪律的另一面是**不报告一个没有发生的改变**：`chmod` 不静默成功，`statfs` 不编造容量，扩展属性不说成「这个文件没有」，`fsync` 不在内容还留在本进程内存里时答「落盘了」。

同样地，**鉴权不做，且不做半套**：不留形同虚设的校验分支、不留默认放行的开关、不打印会让人误以为受保护的日志。半个鉴权比没有鉴权更危险 —— 没有鉴权时部署的人知道自己在裸奔，半个鉴权时他不知道。

## storage 契约

整个系统压在一个接口上。server 侧的实现真正持有数据，`packages/transport/httprest` 的那一份把每一次调用变成一次网络请求，挂载层只认这个接口、不知道自己拿到的是哪一个。R-INT-6 还要求第三方照着它接入自有存储。

光有义务交不出去：没有操作清单、没有说标识是路径还是不透明的节点身份、没有说读是整文件还是按区间、没有错误词汇。**实现者首先需要的是词汇，不是义务。** 更麻烦的是，词汇里几乎每一个位置都有第二个合理答案：路径寻址还是节点身份寻址、整文件读还是按区间读、提交带不带版本、删除是一个操作还是两个。每一对都是两个称职的工程师会分道扬镳的地方，而分完之后它们互不兼容。

`storage.Storage` 是一份命名空间 —— 一棵目录与文件的树，用相对于根的斜杠分隔路径寻址，根是空字符串 `""`。

### 十个操作

| 操作 | 形状 | 备注 |
|---|---|---|
| `Stat` | 路径 → 属性 | 报告名字上的那个节点，不跟随符号链接 |
| `SetAttr` | 路径, 变更 → — | 变更逐项命名，未命名的不动 |
| `List` | 目录路径 → 条目 | 每个条目内联携带属性，按名字排序 |
| `Read` | 路径 → 字节 | 整个文件 |
| `Write` | 路径, 内容 → — | 文件不在则创建；替换是原子的 |
| `Create` | 路径 → — | 该处已有任何东西则 `EEXIST` |
| `Mkdir` | 路径 → — | |
| `Remove` | 路径 → — | 目标是目录则 `EISDIR` |
| `RemoveDir` | 路径 → — | 目标是文件则 `ENOTDIR`；目录非空则 `ENOTEMPTY` |
| `Rename` | 旧路径, 新路径 → — | 覆盖目标处已有的文件 |

每个操作接受一个 `context.Context`，一律返回 `error`。基础数据操作没有远端打开文件或写会话，一次调用完成一次操作；当前显式占有通过独立的锁控制接口维护 Session、Owner 与 Grant，不把它们藏进普通 `Open`。

契约此后长出了第十一个操作 `Space`，见[workspace 的容量上限](../architecture/2026-08-21-space-limit.md)。这里的十个是当时定下的那十个。

### 属性既能读也能写

`Attr` 是 `{Mode fs.FileMode, Size int64, AccessTime, ModTime time.Time}`，`Entry` 是 `{Name, Attr}`。属性随条目一起返回，因此列出 n 个条目花一次调用，而不是一次列目录加 n 次取属性 —— 这个差别在本地目录上看不出来，跨网络时是决定性的。

`SetAttr` 是读的那一侧的对称物，不是一项新功能：不对称本来就摆在那里，读的一侧早就有 `Mode` 与 `ModTime`，缺的只有写的一侧。没有它，挂载层只能对 `chmod`、`chown`、`utimens` 一律 EPERM，而实测的代价是 `git init`、`touch`、`tar -x`、`cp -p`、`gzip`、`rsync -a`、`install -m` 全部不能用 —— 不是慢，是失败。

`AttrChange` 的三个字段是指针，nil 表示「这一项不动」。**必须是指针**，因为没有任何值能代表「不动」：mode 0 正是 `chmod 000` 要的，零值 `time.Time` 也是一个正常的时刻。内核把 chmod 与 utimens 分成两次请求送来（实测 Linux 6.8：chmod 是 `FATTR_MODE` 单独一次，utimensat 是 `FATTR_ATIME|FATTR_MTIME`），谁都不能清掉对方刚设好的东西。

可设的位是 `SettableMode = ModePerm | ModeSetuid | ModeSetgid | ModeSticky`，正好是 `os.Chmod` 在 Unix 上认的那一组。其余的位说的是「这是个什么东西」，而节点的种类不是调用方能改的属性 —— 一个目录不会因为被 chmod 而变成文件。带了种类位的请求**被拒绝，而不是被掩掉**：掩掉等于对「把文件变成目录」这个请求报告成功。判定住在 `storage.AttrChange.Check()` 里而不是各实现内部，因为每一个实现都欠调用方同一句拒绝。这条守卫做过回归验证：把 `Check` 改成掩码，`localdir` 与 HTTP 两侧的同一个契约用例一起变红。

一次命名多项的变更**不是原子的**：失败时可能已经应用了其中一部分。上层不依赖它原子，因为内核本来就把 mode 与时间分开发；契约把这一点写明，而不是留给人猜。

显式 `SetAttr` 的 mode、atime 与 mtime 遵守文件锁的修改权限；S 持有者自己也不能只凭 S 改属性。普通读取可能产生的平台 atime 副作用不在冻结承诺内，S 保护的是内容、存在性与逻辑身份。

POSIX uid/gid 所有权不进属性契约，`packages/fuse` 把每个节点都报成挂载者所有（R-SEC-1）。锁控制的 Owner 表示持有授权的能力主体，与 inode 属主、挂载者 uid 或本地写会话不是同一个概念。

atime 是**收下就要存住**的：接受一个访问时间再丢掉，调用方读回来会得到它从没要求过的值，那正是「报告一个没有发生的改变」。而 `cp -p`、`tar -x` 本来就把两个时间设成不同的值，所以「拒绝 atime」也不成立 —— 那会让 `SetAttr` 想救的工具原地不动。

### 报告的是名字上的那个节点，操作的也是

一个名字被报告成持有什么，指的是**在那个名字上的那个节点**，绝不是它所指向的那个。符号链接因此被 `Stat` 与 `List` 一致地描述成链接 —— 自己的 mode、自己的长度，也就是它持有的那个名字的长度 —— 两者都不解析它。

跟随会**悄悄地把另一个对象放到调用方写下的那个名字底下**：上面没有任何东西能看出这件事发生过，而随后的读、写、删除全部落在一个调用方从来没有命名过的东西上。这正是这个系统存在的理由所要禁止的那一类答案，所以它是契约的规则，不是某个实现的选择 —— 报告的一侧和操作的一侧必须给同一个答案，否则一个路径上「读到的是谁」和「改到的是谁」就分家了。

| 一个符号链接上 | 答案 |
|---|---|
| `Stat`、`List` | 链接自己的 mode 与长度 |
| `Read`、`Write` | ELOOP |
| `SetAttr` 的时间 | 落在链接自己身上，成功 |
| `SetAttr` 的 mode | EOPNOTSUPP |
| `Remove` | 删掉链接，它指向的东西不动 |

时间是符号链接唯一能自己持有的属性，`utimensat` 也是这里唯一一个放得进去的调用：带 `AT_SYMLINK_NOFOLLOW` 时它在链接上成功，并且不碰链接指向的东西（实测 Linux 6.8）。

**当时 Linux 后端选择拒绝链接的 mode 变更。** Linux 没有 `lchmod`；`chmod(2)` 与 `fchmodat(2)` 都跟随；唯一不跟随的 `fchmodat2(2)` 对一个链接返回 EOPNOTSUPP（实测 Linux 6.8，裸系统调用与 `unix.Fchmodat` 两条路都是）。而 `fchmodat2` 要 Linux 6.6 才有，在没有它的内核上 `unix.Fchmodat` 会对**每一个**节点报 EOPNOTSUPP，那会让该后端的每一次 mode 变更都失败。因此当时 `localdir` 先识别链接，再以 EOPNOTSUPP 拒绝。这个 syscall 取舍属于已移除的后端；名字指向哪个节点、就报告并操作哪个节点的规则仍约束 storage。

`Write` 的 ELOOP 是**被命名的，不是被引发的**。引发它要用一次写打开，而那次打开会连调用方的权限一起查 —— 查在提交的时刻，而不是调用方发起 `open` 的那一刻，于是一个以 0444 建出来、经自己的描述符写入的文件会在写回时失败。

**基础契约套件不能自己构造符号链接。** 套件只拿得到一份 `storage.Storage`，而契约里没有建符号链接的操作。当时九条 `localdir` 用例与一条 `cmd` 端到端用例用 `os.Symlink` 从旁边种链接，后者穿过 `localdir → httprest → packages/fuse`，从 lookup 与列目录两侧断言节点仍是链接。宿主目录后端移除后，其 syscall 用例随之退出；FUSE 与 HTTP 的属性夹具继续验证链接种类、长度与不解析链接的行为。它们不是第三方实现创建链接的能力证明，通用套件的构造缺口仍在「后果」中保留。

### 标识是路径

路径按词法清洗：重复的斜杠、末尾的斜杠、`.` 与 `..` 段都被归并，根的各种写法（`""`、`.`、`./`、`a/..`）归一到 `""`。绝对路径、以及任何爬出根的路径，一律 `EINVAL`。

十个操作各自解析自己的路径，因此每一个都是一次单独的越界机会。契约用例逐个验证它们都拒绝，而不是只验证其中一个。路径守卫是被验证过的，不是被假定的：删掉 `CleanPath` 里对「爬出根」的那一处拒绝，契约用例连同 `localdir` 的越界用例一起变红，装回去再变绿。

### 根不能被删除、移动或替换

空路径命名的是根。对内核来说根只是一个普通目录，于是 `rmdir(2)` 把整份命名空间从磁盘上删掉，不会有任何抱怨；此后每一个操作都答 ENOENT。**那句话说的是「那个文件不在」，而事实是「整个命名空间不在」。** 而且这不需要一个本地的库调用方：任何能连上 HTTP 服务端的远端调用方，发一个 `path=` 为空的 `removedir` 就能做到。

于是 `RemoveDir("")`、`Rename("", to)`、`Rename(from, "")` 一律 `EBUSY`。

EBUSY 是实测出来的，不是照着记忆写的：本机上 `rmdir("/")` 与两个方向的 `rename` 都是 EBUSY，`rmdir(".")` 是 EINVAL，`unlink("/")` 是 EISDIR。EBUSY 拒绝这个目录，**是因为它是什么，而不是因为它被怎么写、或者它里面还剩什么** —— 这正是此处的情形。ENOTEMPTY 说的是「先把它清空就能删了」，把一条规则报告成一个可以扫除的障碍；EINVAL 在这份契约里已经有职务（「这个路径我拒绝解释」），而空路径恰恰是一个合法路径，指着一个真实存在的节点。

空路径上的其余操作不需要新词汇：根是一个已经在那里的目录，`Remove` 与 `Write` 是 EISDIR，`Create` 与 `Mkdir` 是 EEXIST，与内核逐条吻合。它们仍然进了契约用例，因为空路径是一条别的用例都不走的进入路线。守卫检验的是解析之后的路径，不是字面的 `""`：`RemoveDir(".")` 与 `RemoveDir("a/..")` 同样删掉整份命名空间。

`SetAttr("")` 则是允许的，和任何别的目录一样 —— `rsync -a src/ mnt/` 会设置目标根目录的权限与时间，而 EBUSY 保护的是根的存在，chmod 不威胁它的存在。

### errno 词汇表是闭集

storage 的已命名错误可以被包裹并保留 `errors.Is`。挂载与 HTTP 编码通过 `storage.ErrnoOf` 共用分类：纯请求取消为 `EINTR`，deadline 与未知错误为 `EIO`；当前错误节点的 `Classification() error` 拥有其子树，独立故障分支优先于取消。是否接受取消由掌握操作阶段的组件决定，不能把已有副作用或未知提交改为可重试的请求中断。具体规则由[请求中断](../bug-fix/2026-08-22-eio-from-a-freshly-mounted-mountpoint.md)拥有。

词汇表在 `packages/storage/errno.go` 里，30 个名字。它属于契约而不属于任何一种传输，因为它是一个实现被允许给出的答案的集合。**表外的 errno 只能被当作 EIO 携带**，因为没有任何东西能命名发生了什么。别名被刻意排除在外 —— Linux 上 `EWOULDBLOCK` 就是 `EAGAIN`、`ENOTSUP` 就是 `EOPNOTSUPP`，两个名字指向同一个 errno 会让映射不再是双射；map 字面量里的重复键编译不过，这一条因此由编译器守着。

**判定不了就报告判定不了。** 够不到后端、超时、内部错误，都不得被替换成 `ENOENT` 或者一个空目录（R-ERR-1、R-ERR-2）—— 这两者对上层读起来都是已确认的事实，而据此行动会毁掉数据。

## 契约是一套可执行的测试

`packages/storage/storagetest` 的 `Run` 就是这份契约：一个实现是正确的，当且仅当它通过 `Run`。

套件住在任何实现之外，于是对象命名空间与网络另一端的实现跑的是同一批用例。当时用 `localdir` 与 HTTP 两个实现验证这种归属；删除一个后端不把套件搬进其余任何实现。**同一套用例约束不同实现，才能证明接口是一层共同抽象。**

用例覆盖根的各种写法、十个操作的成功路径、每个操作的错误码、属性的读写往返，以及路径越界。数目与覆盖率见下面「量出来的数」。

### `Write` 的原子性也在里面

R-CON-3 要求替换是原子的：并发的读者成功时看到的要么是旧内容的全部，要么是新内容的全部。这条义务写在 `storage.Storage` 的文档里；当前对象命名空间先持久保存完整对象，再通过 metastore 提交切换内容引用。文件锁在暂存完成后、原生最终转换处判断发布权限，不把上传时长算作保护期限的延长。下述原地截断实验是当时对 `localdir` 的验证；对象回收竞争允许的可辨别读取失败由[读可以输给写者](../architecture/2026-09-01-a-read-may-lose-to-a-writer.md)拥有。

**散文写下的义务不算防护。** 除了这一条用例，套件里没有任何一条能把兑现它的实现和不兑现它的实现分开：把 `Write` 换成 `os.OpenFile(host, O_CREATE|O_WRONLY|O_TRUNC)` 再写入，其余用例一条不落地通过。原因是所有用例都在写入返回之后才读 —— 那个时刻两种实现给出的结果完全一样。差别只在一个地方可见：**一个正在写入进行中的读者。**

用例的形状：一个写者在两份内容之间交替 200 次，两个读者一直循环 `Read` 直到写者结束，每一次观测都必须逐字节等于其中一份。两份内容长度不同、字节也不同（128 KiB 的 `'a'`、96 KiB 的 `'b'`），因为撕裂有两种形状 —— 读到某一份的前缀、或者新内容盖在旧内容的尾巴上 —— 长度和字节各挡一种。文件在读者启动之前先写一次，于是读者读到 ENOENT 是一条发现，而不是「文件还没被创建」。

它可靠，不是一场多半会输的竞态，理由是它**不对称**：一步替换内容的实现在任何交错下都不可能失败，因为每一个瞬间文件里都恰好是两份内容之一；先截断的实现在最初几次观测内就失败，因为「清空文件」到「填满文件」之间的空档就是整个写入的绝大部分。实测：对原地截断的实现连跑 20 次，20 次全红；对交付的实现连跑 20 次、并带 `-race`，20 次全绿。同一条用例经 HTTP 跑在远端实现上时同样抓得住原地截断的实现 —— 原子性是契约的义务，不是本地目录的特权，而这份证据只有让用例住在实现之外才拿得到。

最后一条：**读者若从未同时观测到两份内容，用例判自己失败。** 那意味着它们整段跑在两次写入之间，上面的断言一次也没被真正施加过；一个恰好什么都没检验的用例，读起来和一个通过的用例一模一样。

## 当时的 `localdir`：把契约落到一个真实目录上

这一节记录已移除后端的原始取舍。它的 `New` 当场拒绝一个不存在的根、或者一个不是目录的根。放着不管的话每个操作都会以 `ENOENT` 失败 —— 那句话说的是「那个文件不在」，而事实是「整个命名空间不在」，调用方对这两件事的反应完全不同。当前本地持久形态由 [localstore](../architecture/2026-09-04-local-disk-object-store.md)提供，其私有存储根不能被解释成直接发布的目录树。

当时 `Write` 把内容写进目标同一个目录里的临时文件再 rename 到位，目的是让暂存与目标位于同一个文件系统。新文件拿 0644；已存在的文件保持它原有的**每一个可设的位**，不只是九个权限位 —— 只搬 `Perm()` 会让一个 setuid 文件在写完之后悄悄失去 setuid。取消该后端也取消了独立 StateRoot 与目录暂存配置；这些机制不是当前对象命名空间的发布路径。

**模式要在内容之后才加到暂存文件上。** 往一个文件里写会清掉它的 setuid 位（除非写的人有 `CAP_FSETID`），先设模式就留不住。暂存文件在被填满的整个过程中都只有属主可读写，随后才恢复目标模式（R-SEC-3）。

`Remove` 直接调 `unlink(2)`，不走 `os.Remove`：后者在 unlink 失败时会退回 rmdir，于是会删掉一个契约要求以 `EISDIR` 失败的目录。

`Stat` 用 `os.Lstat`；`List` 的 `os.ReadDir` 也是一次 lstat，于是两者对「这个名字上是什么」的答案一致。

## HTTP 传输

`packages/transport/httprest` 在同一个包里定义 client、handler 与共用的 wire messages，只依赖 `net/http`。两端共享类型和严格 decoder，使一端单方改变消息形状时另一端必然失败，不会把陌生字节解释成 namespace 事实。

普通 storage operation 仍是一次操作对应一次 request/response，没有与文件描述符同生灭的远端写会话。复制另有 subscribe、resubscribe 与 snapshot 三个 SSE endpoint；change stream 与 snapshot 各走自己的 connection，大块快照不与实时变更共用一条有队头阻塞的 TCP flow。显式锁控制另有有界 JSON POST：Session / Owner 管理跨请求权限与动作历史，TCP 断开不解除已确认的保护。

当前 wire protocol 是 **v3**。此前 [mutation barrier](../architecture/2026-08-27-metadata-replication.md#mutation-barrier写完立刻看得见)把 v1 的空 mutation success body 改成 v2 的严格 JSON `MutationResponse`，因而同时移动 path prefix 与 response header，拒绝旧路由与双版本回退。v3 保留该 response 形状，增加显式锁控制与 mutation scope；所有数据与控制端点都要求 `/v3/` 和 `Remote-Fs-Protocol: 3`，v2 不能被当作省略权限检查的兼容路径。

### 操作在 URL 路径里，操作数在 query string 里

```
GET  /v3/stat?path=notes%2Fone+two.txt
GET  /v3/list?path=
GET  /v3/read?path=a%2Fb
POST /v3/write?path=a%2Fb           请求体是文件内容
POST /v3/setattr?path=a%2Fb         请求体是变更
POST /v3/create|mkdir|remove|removedir?path=…
POST /v3/rename?path=<源>&to=<目标>
GET  /v3/subscribe
GET  /v3/resubscribe?incarnation=<日志标识>&position=<位置>
GET  /v3/snapshot
```

基础 namespace 操作的路径走 query string。`http.ServeMux` 会在 handler 看到之前把 `a//f` 归并成 `a/f`、把 `a/b/../f` 解析成 `a/f`，并把 `..` 变成一个 404 重定向 —— 而这三种写法正是契约用例要求逐字送到 server 侧去判定的东西。URL path 段里的 `%2F` 也无法与分隔符区分。`url.Values` 的转义则对任意字节序列都可逆，包括不是合法 UTF-8 的那些。锁控制中的 Resolve 以 JSON `Bytes` 传递路径；Session、Owner 与 Grant 能力不进入 URL，完整编码见[文件锁设计](../../../../docs/design/server/file-locks.md#http-v3-编码)。

路径原样送出，清洗与越界判定全部在 server 侧的 storage 里做。client 不复制一份路径规则，也就没有第二份规则可以漂移。

根是 `path=`：一个存在且为空的操作数。query 解析失败、必需操作数缺失或重复、或出现该 operation 不接受的操作数，都是请求错误。`url.Values` 会把损坏 query、缺失值与空值压成相似形状，而空 path 恰好是根；因此 decoder 必须校验存在性与基数，不能用宽容默认对整个 namespace 执行操作。`SetAttr` 的 change 使用必需 JSON body；`resubscribe` 另设独立 operation，不把 resume point 做成可选字段，避免一次损坏请求退化成「从当前尾位置开始」并静默丢掉中间变更。

### 一个成功只有 200，一个 errno 只有 422

`200` 是唯一的成功状态。`422` 是唯一承载 storage errno 的状态，errno 以符号名（`"ENOENT"` 而不是平台相关的数字）放入严格 JSON error body。状态码空间与 errno 空间不同构；其它状态码都只能说「未得到这个协议定义的 operation outcome」，不能被猜成 namespace 事实。例如中间网关的 404 不是 storage 报出的 `ENOENT`。

每个 response 还必须带唯一可接受的 `Remote-Fs-Protocol: 3`。client 在解释状态码和 body 之前先要求 `Header.Get("Remote-Fs-Protocol") == "3"`；缺少或返回其它值都以 `EIO` 失败。这个标记阻止代理、强制门户或鉴权网关用自己的 200 body 冒充服务端答案。

基础 namespace 操作的 200 body 由 operation 唯一决定：`Read` 是原始字节；`Stat`、`List` 与 `Space` 是拒绝缺失必需字段或不自洽数值的 JSON；mutation 是严格 JSON `MutationResponse`。无日志 handler 返回 `{}`；带日志 handler 返回 `{"barrier":{"incarnation":…,"position":…}}`，incarnation 必须非空且有界，position 必须非负。普通 public mutation 方法解码后可以丢弃 barrier；`*WithBarrier` 方法要求它存在。空 body、`null`、未知字段、缺失或非法 barrier、截断 JSON 都不是成功结果。锁控制使用各自的严格 envelope；授权方失败仍以 422 承载 errno，并保留 `lockCode`、`recorded` 与已接纳动作的原结果，不能只凭 errno 猜测是否曾经授予。

client 对无法证明为协议结果的故障返回 `EIO`：建连、DNS、TLS 或 transport 失败；protocol header 不匹配；状态不是 200/422；422 body 或 errno 非法；200 body 的分帧、长度、单体上限或 operation-specific decode 失败。已知过大的 `Read` 按契约返回 `EFBIG`。请求在 HTTP `Do` 前被取消，或已经发出的只读请求接受取消时返回 `EINTR`；mutation 一旦进入 `Do`，没有得到权威结果时仍为 `EIO`。deadline 不归入可重试取消。

**transport 底层 errno 不进入 namespace 错误链。** 网络原因以渲染好的文本供诊断；请求取消保留的原因不得突破操作阶段确定的分类。经 Unix socket 访问一个没在运行的服务端时，`net` 的底层错误会带 `syscall.ENOENT`：

```
dial unix /run/remote-fs.sock: connect: no such file or directory
```

把它留在链里，`errors.Is(err, syscall.ENOENT)` 会在服务端不在时对每个 path 都答「文件不存在」。保留文本诊断而隔离 errno 链，才能让不可达稳定地表现为 `EIO`。

### 完整性按分帧方式判定

一个读到一半断开的响应，和一个恰好那么长的文件，字节完全相同。下游没有任何办法把两者分开 ——「读短了的文件」仍然是一个文件。所以这件事只能在响应本身还能说话的时候判定，也就是取决于分帧。三种分帧能自报早停：

| 分帧 | 提前结束时 |
|---|---|
| `Content-Length: N` | 传输层知道该收多少，短了就是错误；收完再把字节数与 `N` 比一次 |
| `Transfer-Encoding: chunked` | 末尾的零长度 chunk 是终止符，缺了就是错误 |
| 传输层解码过的 `Content-Encoding` | gzip 的尾部带着长度与 CRC32，解码器会校验它们 |

由连接关闭定界的 HTTP/1.x 不能：没有长度、没有分块，body 在连接结束处结束，于是中途掉线与完整答复是同一串字节。判据因此是三个字段一起看，且**在读 body 之前**就拒绝：

```go
resp.ContentLength < 0 && len(resp.TransferEncoding) == 0 && !resp.Uncompressed
```

**完整的那种响应与被截断的那个一并拒绝。** 它们是同一串字节，拒绝一个好答复是拒绝那个坏答复的唯一方式。判据对所有响应一视同仁，不只对 `Read`。

server 侧同理：请求体必须先完整到齐，才允许落到 storage。一个提前结束的请求体不会让读取报错，而把到货的那一部分写进去，就是用文件自身的前缀替换掉这个文件，并回报成功。

这条规则不拒绝我们自己产生的任何东西：handler 在每一条响应路径上都显式声明长度，包括 `Read` 的响应 —— 不交给 transfer encoding 去定，正是为了让上表第一行那条最强的判据总是可用。这不是读代码得出的结论：用例包住传输，在 HTTP/1.1 与 HTTP/2 上各跑一遍全部操作与失败路径，任何一条响应的 `ContentLength < 0` 即失败，并且断言协商到的协议版本，否则 HTTP/2 那一组可能其实跑在 HTTP/1.1 上。

后果最重的是这一条：挂载层把 `Read` 的结果填进打开文件的缓冲，并在关闭时把缓冲写回。一个「读出来、改一改、写回去」的程序会把文件替换成它自己读到的那个前缀，静默且不可恢复。

### 缺席必须与零值分得开

`storage.Attr` 的零值不是一个无效值，而是一个合理的节点：`Mode: 0` 没有类型位，于是 `IsRegular()` 为真、`IsDir()` 为假。一个 200 却没有携带属性的响应解出来就是它，并且带着 nil error 交出去 —— 目录变成 0 字节的普通文件，有内容的文件变成空文件，每个节点的时间都是 1970。上面那一层看不出任何异常。

因此线上的属性字段是指针：**缺席有了形状。** 线上字节不变，非 nil 的指针字段与值字段编码相同。

**拒绝写在 `UnmarshalJSON` 里**，`StatResponse`、`Entry`、`ListResponse` 各一处：一个没有携带属性的 body 根本解不出来，于是没有任何读者需要记得去检查。「响应没有携带列表」是同一处的第三条拒绝，于是 `{"entries":null}` 与 `{}` 都不是空目录。

**不能用值去判断。** 「mode 必须非零」这类检查会拒掉 `chmod 000` 的文件，而那是一个合法答案，它的属性恰好就是零值。只有形状能把「没有拿到属性」和「拿到的属性全是零」分开。

### 节点时间走秒 + 秒内纳秒

线上的节点属性时间是一个带 `unix_sec` 与 `nanos` 两个字段的对象。锁控制的期限另用授权方单调时钟内的毫秒 tick 与保守剩余间隔，不能按节点墙钟时间解码或比较。

`time.Time.UnixNano` 在 1678-09-21 到 2262-04-11 之外未定义，而它在越界时不报错，给出的是另一个完全合理的日期：零值 `time.Time` 变成 1754-08-31，9999 年变成 1816 年，2500 年变成 1915 年。mtime 会被上面的东西拿去做判断 —— 构建系统据此决定什么过期了，归档工具据此决定什么变了 —— 一个看起来没问题的错误日期正是这个系统最承受不起的那种答案。秒 + 秒内纳秒覆盖 `time.Time` 的全域，于是没有越界这回事，也就没有错误路径要设计。

**嵌套成一个对象**而不是两个平铺字段，理由来自 `AttrChange`：那里一个时刻可以整个缺席，两个可空的半边会互相矛盾，一个可空的对象不会。

### 目录条目的名字走 base64

`Entry.Name` 的类型是 `[]byte`，`encoding/json` 因此把它编码成 base64。Linux 上的文件名是任意字节序列，不是文本；`encoding/json` 写字符串时会把不是合法 UTF-8 的字节替换成 U+FFFD，于是 `List` 返回的名字将不再指向它被读出来的那个文件 —— 拿它去 `Read` 会得到 `ENOENT`。

### Path 与 header 同时标识 protocol v3

每个 request path 以 `/v3/` 开始，每个 response 带 `Remote-Fs-Protocol: 3`。path segment 让旧 route 无法被新 handler 误解，header 则让 client 在读状态码前证明答案来自讲同一协议的 peer。代理、强制门户或鉴权网关可能自行返回 200，但不会同时猜中这个应用标记。

v2 引入 mutation barrier 时没有与 v1 协商；v3 增加显式权限时沿用同一规则。旧 prefix 没有兼容 route，旧 header value 也不是可接受的降级。如果未来再次改变成功 body 或其它无法由旧 decoder 安全拒绝的 wire shape，就继续同时移动 prefix 与 header version。

`Remote-Fs-Mutation-Scope` 只向修改携带调用方明确给出的不可变 Owner / Grant proof 集合；读取不携带它，普通读取成功也不声称 grant 有效。handler 要求 namespace 与其原生发布授权方配对，不能单独挂一个锁服务却把数据修改交给未受保护的后端。控制请求有独立 admission；排队 Acquire 返回 Pending，不占住长期 HTTP 控制名额。完整边界由[文件锁决定](../architecture/2026-09-07-file-locks.md)拥有。

### 不缓存，也不让别人缓存

handler 不缓存命名空间回答。每个响应带 `Cache-Control: no-store`：一个缓存住的答案就是一个过期的答案，而它读起来和当前的答案一模一样。授权方跨请求持有 Session、Owner、Grant 与有界动作历史，是显式权限状态，不是允许复用旧读取答案的缓存。

超时策略属于调用方：`httprest.Dial` 要求传入 `*http.Client` 而不是自己造一个默认的。一个文件系统挂多久才算失败是部署方的决定，而 `http.DefaultClient` 根本没有超时。

### 「不打印」这条守卫必须真的会失败

这些包会被链进别人的进程，打印出来的东西落在那个进程的输出里，而它的运维没有同意过（R-INT-2）。

在进程内替换 `os.Stdout` 与 `os.Stderr` 变量的守卫，抓不到这条规则最典型的违反方式：一个在 init 时构造的包级 logger 持有它当时拿到的那个 `*os.File`，之后改变量到不了它。这样的守卫在库真的往终端打印时依然报 PASS —— 它证明不了任何事。

于是 `packages/transport/httprest` 的守卫把测试二进制当作一个普通程序重新执行一遍，断言那个进程的输出为空。捕获的是进程真正的文件描述符，因此它覆盖 init 时就抓走 stderr 的 logger，也覆盖依赖库写的任何东西。同一个机制顺带覆盖「不得结束调用方的进程」：子进程把结束状态写进一个文件，文件不在就说明进程在库用完之前就没了。

`packages/fuse` 的两道守卫弱一档，缺口写在「后果」里。

## FUSE 在这一层终止

包按它适配的协议命名。`packages/fuse` 是整个系统里唯一说 FUSE 协议的地方：往上是内核，往下只有 storage 接口，两侧都不知道对方存在。建在 hanwen/go-fuse v2.11.0 的 `fs` 层上（选型见 [`docs/research/fuse-libs.md`](../../../../docs/research/fuse-libs.md)），仅 Linux。

这条边界决定了契约的形状。`storage` 的使用者有两类，拿到的是同一份接口 —— `packages/fuse`，以及直接调用它而不挂载的程序（R-INT-5）。后者不依赖 FUSE，因此也不受 Linux 限制。内核要而命名空间没有的东西，由这一层自己建立并持有：节点身份、打开的文件的内容、挂载的生命周期。**它们不下沉到契约里** —— 把内核的形状写进 `storage`，等于让不挂载的那条路径为一个它不使用的协议买单，也等于让每一种未来的 storage 实现去回答一个只有内核在问的问题。

### 每个打开的描述符一个缓冲区

storage 的读与写以整文件为单位；内核的读与写以 128 KiB 为单位。直接对上，`cat` 一个 N MB 的文件就是 N/0.125 次整文件读取，代价随文件大小平方增长。于是：

```
Open    → 读回整个文件，放进这个描述符的缓冲区
Read    → 从缓冲区切片
Write   → 打补丁或扩展缓冲区，标记为未提交
Flush   → 未提交则 storage.Write 整个缓冲区
Release → 丢弃缓冲区
```

缓冲区属于描述符而不是节点：两个程序同时打开同一个文件时，各写各的副本。当时选择后提交者覆盖；当前普通 `Open` 仍不取得权限，没有活动保护冲突且未做内容版本校验的提交仍可能覆盖此前的修改。显式 S/X 则约束实际受影响文件的最终修改，S 持有者自己也不能只凭 S 修改；X proof 不会验证取得保护之前已经读入的缓冲区。

三个附带的决定：

- **`Create` 立刻调用 `storage.Create`**，不等提交。同机另一个程序去找这个文件时，它已经在了。因此新建的描述符持有的缓冲区是**已提交**的：文件已经是空的，没写过任何东西就关闭，无事可做。
- **`O_TRUNC` 从空缓冲区开始，不取回任何东西**，并立即标记为未提交 —— `> f` 一个字节都不写，截断本身仍然必须被提交。为此挂载时额外协商 `CAP_ATOMIC_O_TRUNC`，让内核把 `O_TRUNC` 带进 `Open`；没协商上时它会变成一次单独的 `Setattr`，两条路都要能走通。
- **`Setattr` 的大小变更，有描述符时落在缓冲区里，没有描述符时直接写穿。** `truncate(2)` 没有可以推迟到的地方。

### 提交发生在 Flush

`Flush` 对应 `close(2)`，是失败还能被告知给发起者的最后时刻。`Release` 在它之后，返回值被内核丢弃。关闭线程的取消不会终止 `Flush` 的一次完成尝试：独立 context 保留请求值与较早 deadline，`Options.FlushTimeout` 缺省为 30 秒，零值选择默认，负值拒绝。预算在等待句柄 mutex 前计算，等待消耗该 deadline，至多一次底层 `Write` 且不自动重试；它不界定 mutex 等待或卸载耗时。`Fsync` 使用同一提交逻辑，但保留请求取消。这个生命周期区别由[请求中断](../bug-fix/2026-08-22-eio-from-a-freshly-mounted-mountpoint.md)拥有。

**经描述符设置时间，要先把缓冲区提交。** `futimens(3)` 到达文件系统时是「对描述符那条路径的 `utimensat`」，**没有任何东西说明它是哪个描述符**（实测 Linux 6.8：请求里没有 `FATTR_FH`）。而 `tar -x` 与 `cp -p` 都是「写完、经还开着的描述符定日期、再关闭」。所以节点自己记着开在它上面的描述符，设时间之前先把未提交的缓冲区写下去 —— 否则关闭时的那次写会把命名空间自己的修改时间盖到调用方刚要求的时间上。

### 单个文件的大小上限

`Options.MaxFileSize` 是单个文件的字节数上限，零值取 `DefaultMaxFileSize` = 1 GiB，负值在 `New` 处直接报错。**没有「不设上限」这个取值**：需要更大的调用方去命名一个数，那是一个决定，而一个省略是一次疏忽。

没有它，`resized` 会用 `make([]byte, size)` 去满足调用方的 `truncate`，挂载点上一条 `truncate -s 1T` 就让 Go 去要 1 TB。Go 对分配不出来的内存的回答是 `runtime: out of memory` —— 那是 `throw` 不是 `panic`，`recover` 抓不住，go-fuse 的 `PanicHandler` 也抓不住，宿主进程当场死掉，`defer` 与 `t.Cleanup` 都不执行，挂载点留在系统里。这个包要被链接进别人的 daemon（R-INT-1、R-INT-2），所以任何能访问挂载点的用户，一条普通命令就能杀掉那个进程。**这不是资源治理的锦上添花，是「失败」与「崩溃」的区别。** R-INT-3 要求「任何会累积的资源都必须有可配置的上限」，而打开的文件的内容是这个包唯一会累积的资源。

超过就返回 **EFBIG，且拒绝发生在分配之前**。五条会按大小分配的路径逐一堵住：`ftruncate` 落在缓冲区上的改长、`truncate` 无描述符时的改长、`truncate` 为了保留前缀而取回整个文件、`write` 越过末尾的扩展、`open` 取回命名空间报告为超大的文件。后两条要先 `Stat` 问大小才能判断，因此**打开一个文件从一次 storage 调用变成两次**。

两处不是被逼出来的选择：

- **`write` 整次被拒，不截短为部分写入。** POSIX 与内核在「还塞得下一部分」时都倾向于部分写入（内核 `*count = min(*count, max_size - pos)`）。选整次拒绝，是因为部分写入只说了到了多少字节，没说剩下的为什么没到；EFBIG 说了。
- **截到 0 即使文件超限也成功。** 截到 0 之后原内容一个字节都不留，因此不需要取回 —— 与 `Open` 对 `O_TRUNC` 的处理同一个道理。不这样做的话，`> 大文件` 会在一件我们其实做得到的事情上失败。

错误码选 EFBIG 而不是 EOVERFLOW：`truncate(2)` 的 EFBIG 是「请求的长度超过了文件系统的最大文件大小」，内核自己的 `inode_newsize_ok()` 对 `offset > s_maxbytes` 返回的就是 `-EFBIG`（[fs/attr.c#L254-L282](https://github.com/torvalds/linux/blob/a4ff2be345d0abc943da8dd8da98151843b750dc/fs/attr.c#L254-L282)，`-EINVAL` 在那里只留给 `offset < 0`）；`open(2)` 的 man page 里 `EFBIG  See EOVERFLOW`，而那条 EOVERFLOW 说的正是「文件大到打不开」，且 2.6.24 之前 Linux 对这种情形返回的就是 EFBIG。

### 节点身份是一棵名字树，不是一张路径表

内核认一个节点靠一个编号，而且它拿这个编号去对齐它被告知过的关于这个节点的一切。契约里没有这个编号，因此它由这一层分配，并记在一棵**名字树**里：每个被解析过的名字一条记录，记着编号、节点的类型，以及它底下那些名字的记录。每个 `*node` 直接持有自己那条记录，所以解析一个名字是一次 map 查找，改名是摘下一条记录再挂上去（底下的记录跟着走，编号一个都不变），删除是一次 `delete`（整棵子树随之释放），**只有列目录会遍历，而且只遍历它列的那一个目录**。

换成一张扁平的 `map[路径]编号`，上面每一条都要变成前缀扫描：改一个目录的名字要扫全表把 `d/` 开头的记录逐条改写，`rm -rf` 一棵深目录树是每层一次全表扫描。

**号取自一个只增的计数器，永不复用。** 根是 1，之后每发一个加一；一个节点消失之后，它的号不指向任何东西，永远。这比真实文件系统更强 —— ext4 的 inode 号在文件删掉之后会被回收再用 —— 而取更强的那一档，是因为这一层没有真实文件系统用来判断「可以安全回收了」的那些东西：没有链接数，没有「还有几个描述符开着」的账。真实文件系统能算出一个 inode 彻底自由的时刻，这里算不出，所以干脆不回收。要走到 FUSE 库自己发号的区间（从 `1<<63` 开始）需要 2^63 次分配。

**同一个新名字被两个 goroutine 同时解析，两次必须拿到同一个号** —— 一个名字解析出两个号就是两个节点。一个裸的计数器给不出这个保证，而记录就是买回它的东西：`child` 在**一把锁**里完成「查已有的记录，没有就发一个新号并记下」，两个并发调用因此得到同一条记录、同一个号；FUSE 库随后按号把两个 `*Inode` 收敛成一个。反过来说明为什么这一步不能省：FUSE 库能把**一个号对应的两个 inode** 合并成一个，但没有任何东西能把**一个节点的两个号**合并回去 —— 收敛只在号这一层发生，所以号必须在更早的地方就是唯一的。锁是一个挂载一把，且**从不跨越 storage 调用或 FUSE 库调用**，临界区只有几次 map 操作；解析一个名字本来就要花一次 storage 往返，一把无竞争的互斥锁在它旁边不构成成本。

**种类是身份的一部分。** 一个名字底下的节点换了类型 —— 文件被换成目录 —— 那是另一个节点，发一个新号。不这么做会真的坏掉：走掉的那个节点只要还有人开着就仍然活着，而 FUSE 库的去重键里带着类型位，于是新旧两个 `*Inode` 同时活着并共用一个 `st_ino`。

记录在五处被丢掉，每一处都连同底下的整棵子树：`Unlink`／`Rmdir` 成功、`Rename` 的源名字、`Rename` 的目标名字、`Lookup` 拿回 ENOENT、列目录时不在列表里。

**不在 `OnForget` 回收。** 这个挂载的三个超时都是 0，内核因此**一直在遗忘** —— 它被明确告知不许留住任何东西。若把「内核忘了」当成回收信号，一个文件的 inode 号会在相隔一秒的两次 `stat` 之间改变，`os.SameFile` 会说这是两个不同的文件，`find` 的环路检测和 `git` 索引里存的 `st_ino` 都会跟着错。**编号跨遗忘保持稳定，值得那点内存。** 另外 go-fuse 自己写明 `OnForget` 会被 `RmChild`／`AddChild` 虚假触发一次。

**列目录的收缩需要一道闸。** 一次列目录是关于一个目录的全部事实，因此它能发现「别人删掉的名字」而不必有人指名去问 —— 这是唯一一处不用问就能知道的。但列表是在某个时刻拍下来的：`Readdir` 在调用 `storage.List` **之前**先读一次已发出的最后一个号，随后只丢弃号不高于它的名字。号比它高的名字，是在这次列目录动身之后才拿到身份的，也就是在列表被拍下来的那一刻还不存在 —— **这次列目录没有资格说它已经没了**；丢掉它会让那个活着的节点在下一次查找时拿到第二个号。

### 答不上来的问题一律拒绝

| 被问到 | 回答 | 因为 |
|---|---|---|
| 改所有权给别人 | EPERM | 属性契约没有可设置的 POSIX uid/gid；请求的正是挂载者本人时答应它，那件事本来就成立 |
| 本文件系统不认识的 FATTR 位 | EPERM | 包括 `FATTR_KILL_SUIDGID`：丢掉它会让一个内核判定该失去 setuid 的文件留着 setuid |
| 新建符号链接、硬链接 | 不实现 | 契约里没有对应的操作 |
| 一个符号链接指向哪里 | EOPNOTSUPP | 答成「不是链接」或者答成目标的内容，都会让读写落到另一个对象上 |
| 扩展属性 | EOPNOTSUPP（`DisableXAttrs`） | 默认答案是 ENODATA，那是一句关于**文件**的断言；真相是这个文件系统根本没有扩展属性 |
| `statfs` | ENOSYS | go-fuse 的默认是回一个全零结构，读起来是「一块没有剩余空间的盘」 |
| `renameat2` 的 `RENAME_EXCHANGE` / `RENAME_NOREPLACE` | EINVAL | 两者都要求原子性，这里给不出 |
| 无法命名类型的节点 | EIO | 当成普通文件呈现，就是在邀请读写一个不知道是什么的东西 |

表里 `statfs` 那一行此后被[workspace 的容量上限](../architecture/2026-08-21-space-limit.md)推翻：容量改由命名空间自己报出，只有自己没有容量可报的那一种才仍以 ENOSYS 拒绝。当时拒绝的理由没有作废 —— go-fuse 的全零默认读起来是一块满盘，那个答案两边都要躲开。

一个已经在命名空间里的符号链接**被如实报告成符号链接**，长度是它持有的那个名字的长度。报成普通文件会把另一个对象放到那个名字下面：瞄准链接的读写会落到它的目标上，而一个复制整棵树的程序会用目标的副本替换掉链接。

`Nlink` 一律为 1。这里没有硬链接（R-FS-4），1 是诚实的计数；它同时避开了另一件事 —— 目录报 2 会让 `find` 这类工具据此断定「这个目录没有子目录」而不再下降。没有变更时间可报，`st_ctim` 用修改时间填，那是最接近真的那个东西：命名空间能记录的每一种改变都是内容的改变。

`NullPermissions` 是打开的。不打开的话 FUSE 库会把「一个权限位都没有的 mode」在送给内核之前替换成 0644（目录 0755），于是命名空间里存着 0000 的文件被报成可读 —— 一个检查自己能不能读某个东西的程序会据此行动。

### 作为库

`Options.Logger` 为 nil 时日志丢弃，没有默认目的地可选，因为可选的那几个都是调用方自己的输出（R-INT-2）。不注册信号处理、不调用进程退出、包加载时不做任何事。

挂载点在交给 go-fuse 之前先自查存在且是目录：go-fuse 启动 `fusermount` 时把本进程的标准错误传给了它（[`mount_linux.go` 中的 `callFusermount`](https://github.com/hanwen/go-fuse/blob/423b377e1452ab7b3522229185a3047f72e3f966/fuse/mount_linux.go#L143-L146)），自查把最常见的失败挡在它前面。挡不住的那些见「后果」。

## 两个二进制

当时 `cmd/remote-fs-server` 接受一个监听地址与一个目录，把那个目录作为命名空间通过 HTTP 发布。当前 Azure Blob 与本地持久对象存储都发布与锁授权方配对的 namespace；`-dir` 及其独立 StateRoot、目录限额与重数配置已经取消，启动与恢复约束见[文件锁设计](../../../../docs/design/server/file-locks.md)。`cmd/remote-fs` 接受一个服务端 URL 与一个挂载点，把那份命名空间呈现为本地的一棵目录树，运行到被中断为止。

两者都是薄的：解析命令行、把包接起来、装信号处理、报告失败、决定退出码。R-INT-2 约束的是包，不是这两个程序 ——「不得注册信号处理、不得写 stdout/stderr、不得调用进程退出」正是一个程序存在的理由，把这三件事留在这一层，是包得以不沾上它们的方式。**为了让二进制跑起来，没有往任何一个包里加过任何东西** —— 需要往包里加东西才能跑通，本身就是包的边界划错了的信号。

失败要响、要具体、不能是 traceback、不能是 0。以下是当时二进制的诊断样本，其中 `-dir` 与直接目录校验已经随该入口移除：

```
remote-fs-server: stat /srv/absent: no such file or directory
remote-fs-server: listen tcp 127.0.0.1:25471: bind: address already in use
remote-fs-server: -dir is required: the directory to serve
remote-fs: mount /mnt/a-file: not a directory
remote-fs: client: "nowhere" needs a scheme and a host
```

全部退 1。命令行本身写错时由 `flag` 完整地报告一次并打印用法，`main` 不再用另一套措辞说第二遍 —— 说两遍会让读的人去找第二个错误。一条 panic 抵达操作员，意思是程序不知道这件事会发生，而操作员得读着 traceback 去猜自己敲错了什么；因此二进制的输出里不允许出现 `panic:`、`goroutine ` 或者 `.go:`，这一条是被断言的，不是被期望的。

`-timeout` 默认 30 秒，同时设置 HTTP 操作超时与 FUSE `FlushTimeout` 的完成 context 预算；后者在等待句柄 mutex 前起算，不承诺 mutex 或卸载的总耗时。传输层拒绝凭空发明一个超时，理由是包不知道调用方是谁；**而二进制就是那个调用方**，超时策略正是它要做的决定之一。不设超时的话，一个打到已经消失的服务端的操作会永远等下去，而**一个会挂起的文件系统比一个会报错的文件系统更难处理** —— 报错的那个至少让上层能够失败并退出，挂起的那个会把每一个碰到这个路径的进程一起拖进 D 状态。

`remote-fs` 在挂载前对根做一次 `Stat`。不探测在正确性上完全站得住（够不到服务端时每一个操作都以 EIO 失败，没有任何东西被编造出来），但它呈现出来的样子是「挂载成功了，但这个文件系统好像是坏的」，而事实是「那个服务端从来就没被连上过」。探测把这句话放在操作员正盯着终端的那一刻说出来。代价是：**服务端与挂载点同时写错时，先报告的是服务端** —— 探测排在 `fuse.New` 之前，而挂载点的校验属于 `fuse.New`。

信号处理在挂载之前就装好 —— 装晚了会留出一个窗口，信号在这个窗口里到达时进程按默认处置被杀掉，而挂载点已经挂上、没有人在服务它。收到信号后反复请求卸载，直到 10 秒的宽限期走完；**每一种失败都重试，而不是只重试「还有人在用」那一种**，因为 `Server.Unmount` 报告的是 fusermount 打印的文本，里面没有这一侧可以匹配的 errno。重试一个永远不会好转的错误，代价是操作员等完宽限期；不重试一个本来会好转的错误，代价是操作员多一个挂载点。宽限期走完仍然失败时，报告失败并告诉操作员用 `fusermount3 -u` 收拾，退非 0（R-ERR-5）。卸载前先解除信号处理：等不下去的操作员按第二次 Ctrl-C 时，进程应当像平常那样被杀掉。服务端那一侧对应地给在途请求 5 秒 `Shutdown` —— 一个被中途切断的写入，让调用方无法判断它到底发生了没有。

## 端到端的判据

当时每一半各有自己的证明：契约套件走 `client → HTTP → handler → localdir`，一个挂载点都没有；挂载层挂在 `localdir` 上跟一个普通目录逐操作对拍，一段网络都没有。**两份加起来仍然说明不了这条链路成立** —— 它们各自缺的那一段恰好是对方，而这个项目存在的理由就住在那两段的接缝上。当前直接 FUSE 与 HTTP 夹具改用 SQLite 与内存对象，独立二进制覆盖 localstore 与 Azure Blob；端到端判据仍须覆盖完整链路，分层测试不能代替它。

判据就是上面那两行命令。R-CON-1 说一秒，而这一秒**从哪里量到哪里**在这里被钉死：**从挂载点 A 上 `close()` 返回的那一刻，到挂载点 B 上一次成功的读返回的那一刻。** 这是一个人真正会等的那一段 —— 写在 `close()` 返回时结束，读在字节回来时被回答。

**B 上的读只做一次，永不重试。** 重试会把断言变成「它最终会可见」，而 R-CON-2 禁止的正是这个：可见性不得取决于任何轮询间隔是否走完。一个会重试的判据无法把「立刻可见」和「一秒后才可见」区分开，于是它只证明得了 R-CON-1 的一个弱化版本。同理，测量前不做预热读：预热会把第一次访问的成本挪出测量区间，而那个成本恰恰在真实使用里是有人付的。

当时验证还走**第三条路径**。两个挂载点和服务端可以彼此完全一致，而三者一起是错的 —— 它们跑的是同一份代码，一致只说明它们没有互相矛盾。因此同一批字节另用普通 `os` 调用从被发布的目录里读一次，那条路径不经过被测实现。取消宿主目录后端也取消了这个物理布局前提：对象存储的私有根不是可直接读取的 namespace，不能沿用原路径拼接作为验收。当前判据从另一挂载点及存储接口核对内容，持久根与对象内容的独立验证由 localstore 的持久性测试负责。原来的旁路读证据仍属于当时，不转移成当前夹具的证明。

服务端停掉之后，挂载点上的每一个操作都以 **EIO** 失败：读、stat 一个存在的名字、stat 一个不存在的名字、创建、删除、建目录、改名。特别地，stat 一个不存在的名字也是 EIO 而不是 ENOENT ——「那个文件不在」是一句关于命名空间的断言，而事实是我们够不到命名空间。

**列目录失败，而不是返回一个空列表** —— 这一条比整条成功路径都重要。一个空列表读起来是「这份命名空间里什么都没有」，是一句已确认的事实，而跑在上面的东西会据此重新生成、把删除传播出去、覆盖写入；这些动作都不可恢复，而且事后无法从任何地方看出它们是基于一句谎话做的。成功路径出错，人会发现；这一处出错，没有人会发现。判据因此写成两层：先拒绝 `err == nil`，无论返回了几个条目；再要求 errno 恰好是 EIO。第一层单独成立。

判据里的「两台机器」是两个挂载点，各自有自己的 client，都指向同一个服务端。**它没有覆盖两台主机之间的那段网络** —— 真实的时延、MTU、丢包、连接被中间设备掐断，以及跨主机的时钟不可比（这也是「一秒」必须在单机上量的原因：跨机器量这一秒需要一个两边都同意的时钟，而那是另一件要单独解决的事）。原始链路覆盖挂载 A 的 FUSE 适配、A 侧的 HTTP、handler、`localdir` 的原子替换、B 侧的 HTTP、挂载 B 的 FUSE 适配，以及两侧为 0 的内核元数据超时。对象命名空间与复制加入后，当前验收还必须经过它们；原始测量不证明这些新增部件的行为。

泄漏检查会自己变红：一个故意不卸载的挂载让 `TestMain` 报告 `left behind: a mount` 与 `left behind: a FUSE connection` 并退 1；一个把 `List` 答成「空且无错」的 storage 让「列目录必须失败」那条断言变红。**没做过这一步的防护测试等于没有。** 挂载相关的判据用 `net.Listen` 加 `http.Server` 起服务端而不是 `httptest`，为的是「服务端在测试里的起法和在 `cmd/remote-fs-server` 里的起法是同一种」；泄漏检查当时靠一份运行前的 FUSE 连接集合去减，理由是 `/sys/fs/fuse/connections/` 全机器共享 —— 那个办法后来被证明会把并行跑的另一个包的挂载算成本次运行漏的，已改为按本次运行专属的临时根归属，见 [挂载属于挂它的那一次运行](../testing/2026-08-22-a-mount-belongs-to-whoever-attached-it.md)。

## 备选方案

### 范围

**一个完备的第一版。** 保留四条保证（跨机器一秒可见、并发写不静默丢失、故障暴露为故障、提交失败不丢数据）与三条形状约束，按「推迟的代价是以后加，还是以后重做」把当时的 37 条需求逐条筛过，配七条验收判据。那套论证是成立的 —— 并发校验事后加确实要改整条写入路径，断线分级事后加确实要改缓存的全部判断依据。它输在别处：**它交付的是一个完备的方案，而第一版要交付的是一个能跑的东西。** 返工的代价是真的，但它小于「做了很久之后才发现链路根本不成立」这个风险。那套筛选没有作废，它是这一版之后的排序依据。

**只读挂载。** 砍掉整条写入路径，更快跑通。输在它证明不了系统存在的理由 —— 核心场景是「A 写，B 看到」，只读版本连场景都覆盖不了。

**保留缓存与变更推送，哪怕只配一个很短的超时。** 一秒的属性超时能把 `ls -l` 的往返砍掉一个数量级，而 R-CON-1 要的也正是一秒。输在它把这一版从「没有会过期的东西」变成「有，只是过期得快」，于是[内核缓存与不可达](../../proposed/architecture/2026-08-19-kernel-cache-and-unreachable.md)里那一整套问题立刻全部成立 —— 负项缓存尤其，它的生存期在 go-fuse 里是挂载级常量，逐响应控制不了。而且「一秒」是个没有依据的数：它不是「多久之后重新确认」，是「够不到服务端之后内核还能替我们撒谎多久」。两者必须成对出现 —— 单独的变更推送没有失效对象，单独的缓存会返回过期内容 —— 而这一对是这一版之后最先做的事，不是被无限期推迟。

**实现 `FileLookuper`，让 READDIRPLUS 从目录句柄已经取到的那份列表里回答每个名字。** 这是 `ls -l` 上单点收益最大的改动，[`docs/research/fuse-libs.md`](../../../../docs/research/fuse-libs.md) 的 G6 专门指出了它。输在它是缓存的一种：从 readdir 到最后一个 lookup 之间的窗口里，答案可能已经不对了，而这一版的前提是没有任何东西被本地持有。

### storage 契约的形状

**不透明的节点身份，而不是路径。** [storage 契约的操作词汇](../../proposed/architecture/2026-08-19-storage-operation-vocabulary.md)提的就是它：跨改名稳定、变更事件可寻址、改名与查询交错时键不会指向错误的对象。三条好处都要求存在一条变更流，而这一版没有变更流。真正拦下它的是边界：契约里没有任何字段标识一个节点，要有就得加，而那正是**把内核的形状压进 `storage`** —— 一个只有内核在问的问题，会变成每一种 storage 实现都得回答的义务，也会落到不挂载的那条使用路径头上（R-INT-5、R-INT-6）。这条边界比一个更稳定的 `st_ino` 值钱。那份提案不是被否决的，它是这一版之后的形状，整份仍然有效；将来换过去要动 storage 契约与挂载层的寻址，而那正是变更流落地时无论如何都要动的两处。

**`Write` 携带调用方所依据的版本。** 提交时校验，不符则拒绝，于是并发写不会静默丢失（R-CC-1）。在 `localdir` 里这只有 3 行：比较版本 → 写临时文件 → rename。输在两条：版本一旦进了 `Write` 的参数，它上面的每一层都要记住并传递它，包括内核根本给不出版本的那些路径；而它挡的是并发写同一个文件这个小概率事件，属于边界情况。**第二条理由只对这里看得见的那一半成立** —— 同一个检查还挡着另一件事，触发它的是别人对一个不相干的名字做的改名或删除，受害者是一个从头到尾只碰自己那个文件的程序。[打开之后没有任何东西把文件钉住](../../proposed/architecture/2026-08-20-nothing-pins-an-open-file.md)把这条决定反转过来，并给出第一条理由在挂载层交付之后的实际大小：一个字段，加上两处没有描述符的读-改-写。

**按区间读。** 同一份提案里的另一条：读一个 10 MB 文件的头 4 KB 不该传 10 MB。输在它买的是往返次数与带宽，而这一版不追求其中任何一个。它是纯增量 —— 将来添一个按区间的操作，不必改动已有的十个。

**只带名字的列目录，属性逐条去取。** 传输量最小，且「只想看文件名」的场景没有浪费。输在往返：n 个条目要 n+1 次调用，而这个系统里往返是货币，传输量不是。

**`Remove` 与 `RemoveDir` 合成一个「删除」。** 少一个操作，且调用方不必先知道目标是文件还是目录。输在错误码：`unlink` 与 `rmdir` 对同一个误用报告不同的错误，一个合并的操作为了挑出该报哪一个，每次删除前都得先 `Stat` 一次 —— 纯粹为了选错误码而付一次往返。

**自成一套错误类型。** 输在它要求每一层做一次翻译：`localdir` 从 errno 翻成它，挂载层再从它翻回 errno 交给内核。两次翻译各是一次把不同错误压平成同一个的机会，而压平错误正是这个系统最怕的事（R-ERR-2）。

**分成 `Chmod` 与 `Chtimes` 两个操作。** 每个操作各自更简单，签名里没有指针。输在同时设两者要两次往返，而且不再是一次请求 —— 一次 SETATTR 被拆成两次，中间的窗口里别人看得见半个改动。

**`SetAttr` 用 `Valid` 位掩码加一组值**，也就是内核自己的形状。输在它允许一种不该存在的状态：掩码说「有 mode」而 mode 字段是垃圾。指针把「有没有」和「是多少」绑成一件事。

**把 mode 掩成可设的位再应用。** 少一条错误路径。输在它对「把文件变成目录」这个请求报告成功。

**拒绝任何带 atime 的请求，或者收下 atime 然后丢掉。** 两者都保住「不给 `Attr` 加字段」。前者输在 `utimensat(2)` 一次设两个时间，`touch`、`tar -x`、`cp -p` 全都会带上 atime，拒绝它等于 `SetAttr` 什么都没救到；后者唯一能不算撒谎的前提是「本文件系统的 `st_atim` 不表示访问时间」，而挂载层偏偏在那个字段里报 mtime：调用方设了 A、读回来是 M。

**给 `Create`／`Mkdir` 加上 mode 参数，而不是建完再设一次。** 少一次往返，也没有那个短暂窗口。输在它要改动两个操作的签名与线路形状，而属性写入口这件事本身已经完整。记为跟进项：契约里一个「建节点顺带带上属性并返回属性」的操作，能同时解决这里的第三次往返和下面「建完还要再 `Stat` 一次」那一条。

**让操作跟随符号链接，像 `open`、`chmod` 这些调用默认做的那样。** 一行 flag 都不用加，而且这是宿主上每个工具的默认行为。输在它把契约最核心的那句话作废：一个名字被报告成持有什么，和一次操作落到什么上，会指向两个不同的对象，而上面没有任何东西能发现这件事。用 `fchmodat2(2)` 去设链接自己的 mode 也不成 —— 它对链接返回 EOPNOTSUPP，而且要 Linux 6.6 才有，在更老的内核上 `unix.Fchmodat` 会对每一个节点都报 EOPNOTSUPP，于是这份 storage 上的每一次 mode 变更一起失败。拒绝一件内核本来就做不到的事，比让 mode 变更整体不可用便宜得多。

**根的守卫放进 `CleanPath`，或者放在 HTTP 服务端。** 前者一处改动挡住所有操作，后者挡住了这个缺陷唯一的实际触发路径。前者输在空路径本来就是根的合法写法 —— `Stat("")`、`List("")` 是这份契约的日常，在归一化里拒绝它等于让根不可寻址。后者输在它挡不住把 `localdir` 当库直接用的调用方，而 R-INT-6 明说第三方要照着这个接口接入自有存储：**守卫属于实现，不属于传输。**

**`Rename("", "")` 保持成功，并给 `Create("")`、`Mkdir("")`、`Write("")`、`Remove("")` 也各立一条规则。** 表面上整齐。前半输在它是一处没有规则的角落：底下的答案随宿主而变（Go 的 `os.Rename` 在这里给 EEXIST，而 POSIX 说改名到自身是成功），而一份没有规则的角落对第二个实现毫无约束力。后半输在它们本来就有答案 —— 根是一个已经在那里的目录，各操作对这种节点的规则就把它们定死了；为已经被定死的行为再添一条词汇，是让契约变长而不是变严。

### 契约测试

**把契约写成散文文档，而不是可执行的用例。** 输在无法验证：第二个实现是否真的合规，只能靠人一条一条读着比对，而契约里最容易被漏掉的恰恰是错误码这种散文里一句话带过的东西。

**契约用例（包括原子性那一条）放进 `localdir` 自己的测试里。** 少一个包，而且在那里能同时用 `os` 调用从另一侧验证，写起来更直接。输在归属：一套住在某个实现里的用例会慢慢长成对那个实现的描述，而这套用例存在的理由正是它要独立于任何实现。具体到原子性，放在 `localdir` 里就把 R-CON-3 变成了本地目录的特权，而 HTTP 那一侧同样欠着这条义务、并且才是真正会被并发读写的部署形态 —— 实测也确实经 HTTP 抓住了原地截断的实现。

**用例检查实现的手法，而不是它的义务。** 断言写入过程中目标目录里出现过一个临时文件、或者断言 `rename` 被调用过。输在它把「怎么做」当成了契约：网络另一端的实现根本没有临时文件，却同样欠着这条义务；而一个照着手法写、绕过手法造假的实现会通过。

### `localdir`

**`New` 不校验根，让操作自己失败。** 少几行代码。输在它把「命名空间不在」报告成「文件不在」，而这正是 R-ERR-2 点名的那类谎话。

**`Write` 原地打开并截断。** 少一个临时文件、少一次 rename。输在原子性：并发的读者会读到写了一半的文件（R-CON-3）。

**`Write` 一律把模式设成 0644，或者只搬 `Perm()` 那九位。** 少一次 `Stat`，或者少想一件事。前者输在它让「替换内容」顺手改掉了权限位 —— 一个把文件设成 0600 的人，会在下一次写入之后发现它变回了 0644。后者输在 setuid：一个 setuid 文件写完之后 setuid 没了，而且没有任何提示；在「`Perm()` 之上的位既不能设也看不见」的时候这个缺陷是隐形的。

### 传输

**gRPC，因为它工具链最成熟。** 流式与错误模型都现成。输在塑形：一条连接上的多路复用会把传输抽象带成「一条双向连接」，而 R-INT-9 要求的三种方式里 SSE + REST 天然是两条独立连接，做不出那种形状。第一版连事件流都没有，REST 这一侧仍然按「将来要加事件流」来选。

**把 errno 映射到 HTTP 状态码。** 不需要在 body 里放错误字段，`curl` 看起来也自然。输在状态码空间与 errno 空间不同构：`ENOTDIR`、`EISDIR`、`ENOTEMPTY`、`EINVAL` 挤在 400 一带，`EEXIST` 与 `ENOTEMPTY` 都想要 409，而 `ENOENT` 想要的 404 恰恰是每一个丢了路由的中间设备都会返回的那个数。

**errno 用数字。** 少一张表。输在两点：数字是平台相关的，一个非 Linux 的第二实现会把 2 读成别的东西；以及「这个数字我不认识」在代码里没有天然的表达，而闭集的名字表让它成为查表失败这一件事。

**改动类操作用 204，读类用 200。** 更贴 HTTP 语义。输在判据的简单性：「成功当且仅当 200」是一条可以一眼核对的规则，而多一个成功状态就多一处可以被中间设备撞对的地方。

**一次请求携带多个操作。** 挂载层的一次 `ls` 是一次 `List` 加若干次 `Stat`，合并能把往返数压下去。输在两点：它需要一个「部分成功」的结果模型 —— 第三个操作失败时前两个已经发生了，而契约里的每个操作都是一次完整的操作，没有位置放这件事；以及它买的是往返次数，而属性已经内联在目录条目里，最大的那一笔往返已经在契约层面省掉了。

**响应体流式，而不是整文件。** 读一个大文件不必先在两侧各攒满内存。输在契约：`Read` 返回 `[]byte`，`Write` 接受 `[]byte`，两侧都必须持有完整内容，流式在这两个签名之间没有落点。改成流式要先改契约。

**路径放进 URL path。** `GET /v2/files/a/b` 读起来更像 REST，也更好在日志里认。输在 `http.ServeMux` 会先把路径归并掉，而契约用例明确要求那几种写法逐字送到 server 侧去判定。绕开 ServeMux 自己匹配也不行 —— path 段里的 `%2F` 与真正的分隔符解码后无法区分。

**变更走 query operand 而不是 body。** 少一个消息类型。输在 operand 是「一个都不能少」的，可选 operand 会拆掉那道判定，而那道判定挡的是「query 坏掉之后被读成对整个命名空间的请求」。

**目录条目名走 JSON 字符串。** 日志里可读，不必 base64。输在 `encoding/json` 会把不是合法 UTF-8 的字节替换成 U+FFFD，于是一个这样命名的文件在 `List` 之后就再也读不到了。自己发明一套转义能保住可读性，但那是一份要自己维护、自己测试的格式。

**不加 `Remote-Fs-Protocol` 头，只看状态码。** 少一个约定。输在改动类操作：它们的响应体没有人读，于是一个中间设备回的 200 与服务端回的 200 无法区分，而这个区分不出来的东西是「文件写进去了没有」。

**client 自己清洗路径，越界的直接返回 `EINVAL`，不发请求。** 省一次往返。输在它是第二份路径规则：`storage.CleanPath` 已经是一份，两份会漂移，而漂移的结果是两侧对「哪些路径合法」的判断不一致。

**把底层原因保留在 `errors.Is` 链里（`Unwrap() []error`）。** 调用方既能拿到 `EIO`，又能拿到 `context.DeadlineExceeded` 这类可分辨的原因，诊断更好。输在它会漏 errno —— 见上文 Unix socket 那一段。诊断信息改为以文本形式保留。[请求中断](../bug-fix/2026-08-22-eio-from-a-freshly-mounted-mountpoint.md)在保留网络 errno 隔离的前提下，区分被接受的取消与未知结果。

**`httprest.Dial` 不要求传 `*http.Client`，缺省用一个自带的。** 调用方少写一行。输在超时策略：一个文件系统挂多久才算失败是部署方的决定，而 `http.DefaultClient` 根本没有超时。把它做成必填，这个决定就一定有人做过。

**接受由连接关闭定界的响应，尽力读完就算数。** 少一条限制，也不必假定对端一定声明长度。输在它读不出「提前结束」：这种分帧下 `io.ReadAll` 对半截 body 返回 nil error，于是一次被腰斩的 `Read` 会以一个更小的、完整的文件的样子交上去 —— 正是最看不出问题的那种坏数据。

**把判据收紧成「一律要求 `ContentLength >= 0`」，或者把传输层解码过的响应也算作不能自报。** 判据少一个字段，也确实堵住了 close-delimited。前者输在它同时拒绝 chunked，而任何一个普通反向代理都会产生 chunked，那等于把这个客户端排除在绝大多数部署之外 —— 而 chunked 本来就能自报截断。后者输在 gzip 的尾部带着长度与 CRC32，截断时解码器会报错（用例里那个被砍掉尾部的 gzip 响应确实变成了错误），拒绝它不多买到任何东西。

**只对 `Read` 施加分帧判据，因为只有文件内容是任意字节。** 输在 mutation 成功同样有严格 body：它必须是完整的 JSON `MutationResponse`。没有日志的 handler 返回 `{}`；带日志的 handler 返回经验证的 barrier object，普通 public mutation 方法可以在解码后丢弃它。空 body、截断 JSON 或非法 barrier 都不能被解释为成功；分帧与完整解码必须覆盖每一种 response。

**属性字段用值而不是指针，缺失靠值来判断（mode 非零，或者时间非零）。** 少一层解引用，JSON 也更朴素。输在零值有含义：`Attr` 的零值 `Mode: 0` 读起来是一个普通文件，于是一个 `{}` 的响应会让一个目录以 0 字节文件的样子抵达，且 error 为 nil；而「mode 必须非零」会把 `chmod 000` 这个合法答案报告成一次失败。

**缺失判断放在 client 里，每个操作解码之后自己检查一次。** 输在两处：listing 里逐条 entry 的检查，要么在 client 里把转换循环重写一遍，要么留下一个 nil 解引用给任何忘了先检查的调用方；而把判断收进一个返回 error 的转换函数，仍然是「每一个调用点都要记得处理」。解码时拒绝把这条约束变成解不出来，谁也忘不掉。

**mtime 越界就报错，或者把它夹取到可表示范围。** 保留 `UnixNano`，少改线路形状。前者输在报错只能发生在编码侧，客户端无从发现；而且一份 mtime 越界的文件（篡改过的归档会产生）会让整个 `ls` 失败，而不是只让那一个时间不可用。后者输在夹取产生的正是「看起来合理的错误答案」，与 `UnixNano` 悄悄给出 1754 年是同一类东西，只是错得没那么远。加宽编码没有这些问题，也更少代码。

**继续用进程内替换变量的守卫，只是多跑几个操作。** 输在多跑多少个操作都不会让它变红：它抓不到的是 logger 什么时候拿到的 `*os.File`，与跑了哪些操作无关。

**用静态检查代替运行时守卫** —— 扫 AST，禁止 `os.Stderr`、`log.*`、包级的初始化调用。它比运行时守卫更早，也覆盖没有任何用例走到的代码。输在它看不见依赖库打印的东西，而那正是运行时守卫在看的。两者互补，不是二选一：`packages/fuse` 两样都有，只是它的运行时那一半用的是替换变量的做法，缺口写在「后果」里。

### 挂载层

**不要缓冲区，每次内核读都直接调一次 `storage.Read`。** 代码少一半。输在算术：storage 只能整文件读，内核一次要 128 KiB，读一个 3 MB 的文件就是 24 次整文件读取 —— 72 MB 的传输量。这不是优化，是正确性成本的问题。

**在 `Release` 提交而不是 `Flush`。** `Flush` 在每一个复制出来的描述符关闭时都会发生，`Release` 只在最后一个引用消失时发生一次；按次数算 `Release` 才是对的，[写会话与稀疏暂存](../../proposed/architecture/2026-08-19-write-session-and-staging.md)整篇就在处理这件事。输在 `Release` 的返回值被内核丢弃：提交失败将无处可报，而这一版没有未保存写入清单可以兜底。多提交几次的代价是多写几次相同的内容；少报一次失败的代价是静默丢数据。

**暂存到本地磁盘的临时文件，而不是内存。** 一个 10 GB 的文件现在根本打不开。输在它引出一整串这一版没有回答的问题：临时文件放哪、权限怎么定（R-SEC-3）、进程被杀之后谁清理、冷挂载时的既有状态算什么（R-WS-3）。那些是[暂存预算与清偿](../../proposed/architecture/2026-08-19-staging-budget-and-discharge.md)的内容。内存版本的边界清楚：进程没了，暂存也没了，没有残留。

**让 `chmod` 与 `utimens` 静默成功。** 实测这一条能让 `touch`、`tar -x`、`cp -p`、`gzip`、`git`、`rsync`、`install` 全部恢复正常，它是可用性上最大的一块。输在它就是这个仓库唯一不肯做的那件事：报告一个没有发生的改变。

**只在请求的值与当前值相同时接受 `chmod`。** 这条不是撒谎 —— 调用返回时后置条件确实成立。有了 `SetAttr` 之后 mode 这一半不需要它了，**但这个形状在 chown 上活了下来**，因为所有权确实无处存放：请求的正是已经成立的那个属主时答应它，其余拒绝。

**`statfs` 交给 go-fuse 的默认。** 默认会成功返回一个全零的结构，`df` 于是显示一块 0 字节、0 剩余的盘。输在它是编造出来的事实，而且是最坏的一种：先检查空间再写入的程序会认为磁盘满了。

**让根继续报 0。** 不设 `RootStableAttr` 就是这个结果，因为 FUSE 库从 embedder 的零值 `StableAttr` 里取根的号。输在 0 是文件系统用来说「这个节点没有身份」的值，而按 `find`、`du`、`tar` 的读法，一个没有身份的目录是不该出现在树里的。根是这棵树里的一个节点，和别的节点一样有号。

**建在 go-fuse 的 raw 层而不是 `fs` 层。** 输在 FORGET 与 lookup 计数的记账，那是 raw 层最容易出错的一处，而 `fs` 层已经做完并有专门的测试。

**自己调用 `fusermount` 以控制它的标准错误。** 这能彻底解决「挂载失败时写到调用方 stderr」那处缺口。输在它要复制 go-fuse 内部的挂载选项拼装（`optionsStrings` 不导出），并且用 `/dev/fd/N` 挂载之后卸载路径也要自己接管；抄错一处比留下一行诊断输出更糟。go-fuse 侧也没有干净的开关：`DirectMount` 在 `syscall.Mount` 失败时回退到 fusermount（非特权下必然回退），`DirectMountStrict` 没有回退，于是非特权挂载整个不可用。

### 大小上限

**零值表示不设上限。** 保持现有调用方一行不改。输在它把崩溃原样留给了「没想过这件事」的那个调用方 —— 而那正是这个包的默认处境：被链接进别人的进程。

**上限按可用内存推算。** 不必让人挑一个数，也不会在大内存机器上误伤。输在两点：结果不可预测、不可测试（同一条命令在两台机器上一成一败）；而且读 `/proc/meminfo` 去推断，是拿一个进程级的事实替调用方做决定。

**不在 `Open` 处设卡，只挡住 `truncate` 与 `write`。** 少一次 `Stat`，打开仍然是一次调用。输在漏了一半：命名空间报告一个 10 TB 的文件时，`storage.Read` 在我们这一层之下把它整个读进内存，崩溃点只是从 `resized` 挪到了 `os.ReadFile`。

**读回内容之后再检查长度。** 不必多一次 `Stat`。输在检查发生在分配之后 —— 而分配就是要防的那件事。

**EOVERFLOW 用于「文件本来就超限」。** POSIX 的 `open` 页只列 EOVERFLOW，现代 Linux 的 `generic_file_open()` 用的也是它，而且它能让调用方区分「这个文件本来就太大」与「你的请求会让它太大」。输在两处：POSIX 把 EOVERFLOW 限定为「大小无法用 `off_t` 表示」，那是 ABI 问题，不是我们的情形；以及它印出来是「Value too large for defined data type」，会把人引去查 32 位 `_FILE_OFFSET_BITS`。「File too large」说的是实际发生的事。

### 节点身份

**路径的 FNV-64a 哈希。** 免费拿到并发一致 —— 两边各算各的，算出同一个答案 —— 也免费拿到跨遗忘稳定，不需要任何记录，不占内存。输在它把身份绑在**名字**上，而节点会离开名字：改名之后 FUSE 库把原来那个 inode 挪到新名字上，它带着按**旧路径**算出来的号走；旧路径随即空出来，下一个建在那里的节点算出同一个号。两个活节点一个号，内核拿其中一个的长度去映射另一个，读它的程序收到 SIGBUS。这不是概率事件，也不是碰撞概率的问题，而是同一条路径在两个时刻属于两个不同的节点：`git` 把 `.git/config.lock` 改名盖到 `.git/config` 上，随即又建一个新的 `.git/config.lock`，拿到的正是同一个号，对 `config` 的内存映射于是落在 `config.lock` 的长度 0 上 —— `git init` 每次都以 `Bus error (core dumped)`、退出码 135 结束。

**扁平的 `map[路径]编号` 加一把锁。** 同样解决 SIGBUS，写起来比树少几十行。输在每一次子树操作都成了全表前缀扫描：改一个目录的名字要把 `d/` 开头的每条记录改写，删一个目录要把它底下的残留扫掉，而 `rm -rf` 是每个目录来一次。记录规模乘以目录数。

**身份只挂在 `*Inode` 上，不建任何记录。** 最省：`GetChild` 命中就复用它的号，没命中就从计数器取一个新的，改名和删除都不用做任何事。输在同一个新名字的两次并发 Lookup 会各取一个号 —— `GetChild` 在两边都返回空，而 FUSE 库要到 `addNewChild` 才把子节点挂进树里，那已经是我们返回之后了。加锁也救不了：加锁的那段时间里，树根本还不知道这个名字。这条反对意见是成立的，它正是那棵记录树上那把锁买回来的东西。

**在 `OnForget` 里回收。** 记录的规模会被压到「内核当前还记着的节点数」，是所有方案里最省内存的。输在这个挂载的三个超时都是 0，内核被明确要求不许留住任何东西，因此遗忘是持续发生的日常事件 —— 编号会在相隔一秒的两次 `stat` 之间改变。那不是身份。再加上 go-fuse 写明 `OnForget` 会被 `RmChild`／`AddChild` 虚假触发，一次虚假回收就让一个活着的号被第二个节点拿走，SIGBUS 原样回来。

**哈希打底，只为「号被别的活节点占着」的名字建记录。** 想同时拿到哈希的免费稳定和分配的正确性：记一张「号 → 活节点」的表，发号时若 `H(路径)` 已被占着就改用 `H(路径, 1)`、`H(路径, 2)`。输在探测结果取决于探测那一刻的表的状态，于是同一个名字在不同时刻可能探到不同的号 —— 稳定性又丢了，而且只在被回收过的名字上丢，是最难复现的那一类。而「号 → 活节点」这张表的维护仍然要靠 `OnForget`，上一条的问题一并继承。

**身份里不带类型。** 少一个字段，`child` 少一次比较。输在一个名字底下的节点换了类型时（别的 client 把文件换成目录），老节点只要还有人开着就仍然活着，而 FUSE 库的去重键里带类型位，不会把新旧两个 `*Inode` 合并 —— 于是两个活节点共用一个 `st_ino`，正是这套记录要防的那件事。

**节点消失之后回收它的号。** 真实文件系统就是这么做的，ext4 的 inode 号删掉之后会再发出去，因此这条不算激进。输在这一层算不出「彻底自由」的那一刻：没有链接数，没有跨 client 的「还有几个描述符开着」的账，唯一知道的是这个挂载自己做过什么。回收就只能靠猜，而猜错一次就是两个活节点共用一个号。号是 64 位的，不回收不构成任何实际压力。

### 二进制与端到端

**位置参数，像 `mount source target` 那样。** 与系统上同类命令一致，敲起来短。输在报错：位置参数搞反了的时候，程序无法说出「你把服务端 URL 放到了挂载点的位置」，它只能报告挂载点不存在。统一用 flag，于是每一个必填项缺失时都能指名道姓。

**让操作员自己传超时，不给默认值；或者干脆不设超时。** 前者与传输层的立场一致。输在那不是同一个位置的同一个问题：包不能替调用方决定，是因为包不知道调用方是谁，而二进制就是那个调用方，把决定往上推给每一次命令行输入只是让它变成一件必须每次重复的事。后者输在挂起 —— 见上文 D 状态那一段。

**在二进制里先 stat 一次挂载点，好让两个错误里更廉价的那个先被报告。** 输在归属：挂载点的校验是 `fuse.New` 的义务（它必须留着，因为它是一个库），在二进制里再抄一遍，是为了调整报错顺序而把一个已有的契约复制到第二个地方。

**卸载只试一次，或者只重试 EBUSY。** 前者最简单，后者最精确。前者输在 Ctrl-C 的那一刻挂载点里往往还有东西 —— 操作员自己的 shell 的工作目录、还没退干净的子进程 —— 而这些通常在几百毫秒内就散了，试一次就放弃等于把一个会自愈的情况变成一个需要人工收拾的挂载点。后者输在拿不到 EBUSY：`Server.Unmount` 返回的是 fusermount 打印的文本，`errors.Is` 匹配不到任何 errno，要么按文本匹配（脆），要么全部重试。

**卸不掉时退回 `fusermount3 -uz` 强行卸载。** 一定不留挂载点。输在它把「有人正在用」变成一次静默的、对方无从察觉的抽离。宽限期走完仍然卸不掉，说明那不是一个会自愈的情况，此时正确的动作是把事实和收拾办法告诉操作员并退非 0，而不是替他们做一个破坏性的决定。

**`flag.ExitOnError`。** 少几行。输在 `run` 不再可被当作函数调用与观察，而这两个程序的错误路径正是要被逐条断言的东西。改用 `ContinueOnError` 加一个 `errUsage` 哨兵。

**端到端的判据放进某个包里。** 少一个只有测试文件的包。输在它不是关于任何一个包的事实 —— 它恰恰是「这些包接起来之后成不成立」这个问题，放进其中任何一个包都会让它读起来像那个包的性质。它跟它验证的交付物放在一起：`cmd/`。

**只用一份 shell transcript 证明二进制可用。** 真实入口、真实进程、真实输出。输在它不会在下一次改动时自己跑一遍。两者都做：`TestTheBinariesServeAndMount` 把两个二进制当作进程构建并驱动，包括 SIGINT 与事后的挂载检查。

**两台真机器，或者两个容器。** 覆盖主机之间的网络。输在它把一条本该在任何机器上都能跑的判据，变成一条需要编排的判据 —— 而这一版要回答的问题是链路成不成立，不是网络行为如何。跨主机的验证是缓存与变更推送落地时无论如何都要建的东西，那时候一起建。

## 后果

### 当时买到的与保留的接口

- **一条端到端可跑的链路**，且它作为一条完整链路被验证过，而不是两半各自被验证过。当时一个符号链接穿过 `localdir → httprest → packages/fuse` 之后仍然是符号链接，长度仍然是它持有的那个名字的长度；现有属性夹具继续验证传输与挂载对这些值的保留。
- 一份实现者能据以动工的词汇 —— 十个操作及其形状、属性的字段与可设的位、路径规则、根的规则、errno 的闭集，外加一套跑得起来的用例。第三方接入自有存储不必追问（R-INT-6）。
- 当时 `localdir` 与 HTTP 那一侧跑同一套契约用例，验证 storage 的共同抽象；契约与实现分离，因此对象命名空间接续同一套义务。
- 一个能被普通程序当作普通目录使用的挂载点，与一份对拍测试 —— 同一串操作施加在挂载点和一个普通目录上，比较每一步观察到的结果、错误码，以及之后两棵树。普通目录是行为依据；挂载侧当前直接使用对象命名空间，链路里没有网络。
- **`git` 能用了**：`init`、`add`、`commit`、`status`、`log`、`diff`、`gc`、`fsck` 全部退 0，对着真实二进制验证过。`touch`、`tar -x`、`tar -c`、`cp -p`、`cp -a`、`gzip`、`rsync -a`、`install -m`、`sed -i`、`make`、`mv`、`truncate`、追加写、`find | xargs chmod` 与普通目录一致。
- 够不到服务端时的行为是被逐条测过的，而不是被假定的：十个操作、十余种失败形态，每一种都断言了「是 `EIO`」和「不是任何一个会被当成事实的 errno」两件事。
- 复制流已作为 `/v3/subscribe`、`/v3/resubscribe` 与 `/v3/snapshot` 三个端点与普通 request/response 共存。handler 仍是裸的 `http.Handler`，集成方可以用 `http.StripPrefix` 挂进已有 server（R-INT-1），不引入外部框架；发布的 namespace 必须与其锁授权方配对。
- 两个可部署的二进制（R-INT-4），它们的失败路径被作为真实进程逐条驱动过：每一个都退非 0、指名道姓、且被断言输出里没有 traceback。

### 会毁数据的

下面记录原有路径提交留下的问题。显式文件锁在保护期内阻止不具权限的修改，普通 FUSE 打开没有自动取得这种保护，内容版本与打开目标绑定仍未补齐。

- **没有连续保护的旧内容提交仍可能覆盖别人的修改。** 没有内容版本就不能识别所依据的字节是否过时，R-CC-1 仍未完成。活动占有冲突会让匿名修改失败；显式修改必须在暂存后的原生最终转换处持有有效 X proof，过期后尚未获准的上传不能因为没有竞争者就继续发布。
- **提交落在打开时那个路径上，而不是打开时那个对象上。** 别的 client 在这中间把另一个对象改名到这个路径，缓冲区就落在它上面，原有内容被替换；别的 client 把这个路径删掉，`storage.Write` 的「文件不在则创建」会把它**重新造出来**，内容是某个程序在很早之前读到的那份字节。触发它的是别人对一个不相干名字做的改名或删除，受害者是一个只碰自己那个文件的程序。出路见[打开之后没有任何东西把文件钉住](../../proposed/architecture/2026-08-20-nothing-pins-an-open-file.md)。
- **`unlink()` 之后的提交仍缺少已打开对象的寻址方式。** 提交写到 `Inode.Path`，而 go-fuse 对一个走不到根的 inode 拼出 `.go-fuse.<随机数>/deleted`；`storage.CleanPath` 原样放行它，因为它是一个合法的相对路径。普通目录的描述符仍能访问已经没有名字的 inode，当前路径操作没有表达这种对象的词汇。当时 `localdir` 因暂存目录不存在而以 ENOENT 拒绝 `close`，同一占位路径也使已删除但仍打开的描述符 `fstat` 失败；原范围还指出，若一个实现把任意路径直接当作对象键，它可能成功写出无人再读、也无人清理的键。这是对后端形状的约束，不能据此断言当前树形对象命名空间会创建那个键。打开目标绑定仍由[独立提案](../../proposed/architecture/2026-08-20-nothing-pins-an-open-file.md)处理。

后两条是同一对互斥诉求的两个方向：**提交必须用现在的路径**（文件可能在打开之后被改了名，内容属于文件而不属于名字，`TestAnOpenHandleFollowsItsFileThroughARename` 守着这一条），**同时必须用当时的路径**（名字可能已经没了，而写入仍然要落到那个节点上）。本地文件系统两条都满足，靠的是描述符钉在 inode 上；这一层没有 inode 可钉，因为契约里没有句柄。现在选的是跟着改名走。

### 安全

- **部署鉴权仍由集成方提供。** 文件锁的 Session、Owner 与 Grant 是不可伪造的能力，阻止把别人的授予当作自己的权限；它不引入身份提供者，普通读取也不因 X 变成访问控制操作。部署方仍须控制 enrollment 与 namespace 的访问，不能把占有保护当作对不可信客户端开放全部内容的依据。
- **当时 `localdir` 的部分错误携带宿主路径。** `Remove` 与 `RemoveDir` 使用命名空间路径，其余操作直接返回 `os` 的错误，handler 再转交 `err.Error()`，远端因此能看到服务端的目录布局。删除该后端消去了这条具体来源；可替换存储仍须自行约束错误中的私有路径与凭据，HTTP 不替实现者消除敏感内容。

### R-INT-2 上一处已知的、未解决的缺口

**挂载失败时 `fusermount` 会往调用方进程的标准错误写一行诊断。** `fuse.New` 的自查挡掉了「挂载点不存在」和「不是目录」，挡不住其余的（例如目录无法进入）。go-fuse 在**挂载**时把本进程真实的描述符交给 fusermount（`Files: []*os.File{os.Stdin, os.Stdout, os.Stderr, remote}`），而它在卸载路径上是把 stderr 收进 buffer 的 —— 只有挂载这条路径漏。

用一个仓库之外、只 import 这些包、自己什么都不打印的程序复现，在同一个挂载点上挂第二次：

```
=== what the program meant to say ===
second mount: fusermount exited with code 256
=== what reached the process's stdout ===
=== what reached the process's stderr ===
/usr/bin/fusermount3: failed to access mountpoint <挂载点>: Permission denied
```

一处漏洞，两个后果：R-INT-2 被违反；而且**包返回的错误里没有真正的原因** —— `fusermount exited with code 256` 说明不了任何事，真正的那句话去了调用方够不到的地方。

现有的两道守卫都抓不到它：`TestNoProcessWideStateIsTouched` 是语法树上的静态检查；`TestNothingIsWrittenToTheProcessOutput` 是运行时的，但它替换的是 `os.Stdout`／`os.Stderr` 这两个 Go 变量，而这行字是一个子进程写到真正的 fd 2 上的。出路见备选方案最后一条，或者去 go-fuse 上游让它接受一个 writer。

### 成本与形状

- 每一次 `ls`、每一次 `stat` 都是一个网络往返，不带连接复用之外的任何优化。
- 读一个 10 MB 文件里的任意一个字节要传 10 MB；改其中一个字节要上传 10 MB，且两侧各攒一份完整的 10 MB。
- 基础数据操作仍没有区间读写或远端打开文件状态；显式占有另有跨请求的 Session / Owner / Grant，不承担本地 dirty 缓冲区的归属或保留。
- **缺省 1 GiB 的上限会拒绝命名空间真的持有的大文件。** 一个 4 GiB 的镜像在零值 `Options` 下打不开，调用方必须显式调高；`cmd/remote-fs` 没有暴露这个开关，二进制拿的就是缺省值。这是一个真实的错误答案，只是它响、且改一个字段就能修。
- **打开一个文件是两次 storage 调用**（先 `Stat` 再 `Read`），建一个节点是三次（`Create`／`Mkdir`、`SetAttr`、`Stat`），而且建节点有一个短暂窗口里节点带着命名空间的默认权限存在。`Stat` 与 `Read` 之间也有窗口：文件在这两次调用之间变大的话，取回的仍然是变大之后的整个文件。关掉这些需要契约里的按区间读与「建节点顺带带上属性并返回属性」。
- **请求体与 response materialization 都有显式上限。** `Write` request 使用独立的 `MaxWriteBytes`，零值继承一般 `MaxBodyBytes`；`SetAttr` 使用一般 body 上限。两类 request body 都有并发数、waiter 与 aggregate byte admission，bodyless 操作不接受额外内容；non-streaming response 也必须装进单次上限。server 要求 `storage.BoundedStorage`，把 Read 预算传进 backend，并让 List 逐 entry 填充 caller-owned bounded result；server 与 client 另有独立的 response operation、waiter 与 aggregate retained-byte admission。完整形状见[有界地产生 Read 与 List 响应](../architecture/2026-09-04-bounded-read-and-list-responses.md)。
- **未提交的写入只能通过写它的那个描述符看见。** 同机另一个进程 `stat` 同一个路径，在提交之前看到的是旧的大小与时间 —— 除非那次 `stat` 恰好被内核带上了一个本挂载点内已打开的描述符。这与 R-CON-4 不完全相符，是「提交发生在关闭时」的直接后果。
- **当时 `localdir` 上只读打开也会推进 atime。** 挂载层在 open 时取回整个文件，宿主已经完成一次读取；普通目录上的程序则要到真正读取时才影响 atime。这是当时测得的后端副作用，不是对象命名空间的访问时间规则。惰性取回仍会改变失败的报告点：从 `open()` 挪到第一次读。
- **对一个别人还开着并且写脏了的文件 `touch`，会顺带提交别人的缓冲区**（见「提交发生在 Flush」）。这比本地文件系统更早，而不是更晚。
- 改名让一切以路径为键的东西作废。这一版没有以路径为键的缓存，所以此刻不痛；缓存进来的那一刻就痛。
- **`st_ino` 跨卸载重挂不稳定**，因为计数器属于这一次挂载。同一次挂载内部稳定，跨改名稳定，跨内核遗忘稳定。真正的节点身份是[变更日志与节点身份](../../proposed/architecture/2026-08-19-change-log-identity.md)的内容。
- **这个挂载解析过的每个名字占一条小记录**，只要那个名字还在它的目录里、这个挂载还活着，记录就在。别的 client 删掉的名字，要等到有人再问起它、或者列一次它的父目录，记录才被丢掉。
- 目录的 `st_size` 是 0、`st_nlink` 是 1、`st_blocks` 由大小推算，于是 `du` 与 `ls -l` 的 `total` 与普通目录不同；`df`、`stat -f`、`os.statvfs` 报「功能未实现」。这是拒绝编造容量与链接数的直接代价。（容量这一半后来由[workspace 的容量上限](../architecture/2026-08-21-space-limit.md)偿还。）
- 以 root 运行的 `tar -xp`、`cp -a --preserve=ownership` 在这里保留不了属主。
- **chown 一个同时是 setuid 和 sticky 的文件，这里会丢掉 sticky 位**，普通目录不会。这不是两边任何一方的决定：内核会把「它希望留下的那个 mode」附在 chown 上，而对 FUSE 的 inode，它附上的那个 mode（`0100755`）连 sticky 一起没了。要复现普通目录的行为，就得无视内核明确要求的那个 mode 的一部分 —— 那比这点差异更糟。
- **命名空间能保存的时间范围是它自己的。** 当时 `localdir` 使用宿主文件系统的范围与精度，例如 ext4 的 1901-12-14 到 2446-05-10，超出即被截断。删除该后端不把宿主范围变成对象命名空间的限制；契约仍只承诺「`Stat` 报告的是被保存下来的那个时刻」，不承诺「你设什么就是什么」。
- **当时同目录暂存会把临时名字短暂暴露给列目录。** 这是直接目录后端用 rename 原子替换的成本；该后端及其树外 StateRoot 方案均已取消。对象命名空间在元数据提交时发布内容引用，物理对象暂存不属于逻辑目录树。
- **只接受能报出自己提前结束的分帧。** 一个把响应改成由连接关闭定界的中间设备会让每一次调用都变成 `EIO`。这是刻意的，但它意味着这条链路对重新分帧的代理毫不宽容，排查的人需要先知道有这条规则；同时「每一条响应路径都声明长度」从一个实现细节变成一条约束，新增响应路径时用例会抓住，写的人要知道为什么。
- 线上的 `mode` 是 Go 的 `io/fs.FileMode` 位布局，不是 POSIX `st_mode`；非 Go 的第二实现要先做一次转换。errno 的名字表是闭集，扩表是加一行，但那要求两侧同时升级。
- 没有包记日志。server 侧的失败原因只出现在返回给该次请求的响应里，没有连上的人看不到任何东西。
- 挂载相关的判据需要 `/dev/fuse` 与 `fusermount`，缺任何一个就整体跳过；`httprest` 的「不打印」守卫要重新执行测试二进制，因此在不能 fork/exec 的环境里跑不起来。
- **符号链接被如实报告，但建不出来、也问不出它指向哪里。** 契约里没有建链接的操作，挂载点上 `readlink` 是 EOPNOTSUPP。命名空间里已经有的链接则处处被当作链接对待（见「报告的是名字上的那个节点，操作的也是」），代价是**一个符号链接在这份命名空间上是只读的**：内容读不了、写不了，mode 也设不了，能改的只有它的时间。一个把整棵树复制进来的程序会在链接上停下，而不是悄悄把目标复制成一个普通文件。
- **「不跟随」这条义务没有通用的后端构造用例（R-INT-6）。** 造一个符号链接需要契约没有的操作，所以基础套件问不出这个问题。当时两个实现另有宿主用例；当前属性夹具能守住 HTTP 与 FUSE 的行为，仍不能证明第三方 backend 操作真正的链接时不会跟随。一个跑绿全部基础用例的第三方仍可能违背这条义务。三条出路：给契约加一个建链接的操作；让 `storagetest.Run` 多收一个「在旁边种一个链接」的函数，代价是宿主的形状进了套件的签名；或者在 `Run` 旁边加一个**配套入口**，专收这类需要旁路准备的义务，同样接一个「种一个」的函数，让 `Run` 的签名不动。

断线反而不付代价：没有缓存，所以断了就重连，重连之后不需要做任何事。这是「不做缓存」顺带买到的，也是它将来被撤销时要一并还回去的。
