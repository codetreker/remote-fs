# Agent Note: 用 Makefile 收拢构建与测试

Status: implemented

## 问题

`go build ./...` 在这个仓库里会做一件不明显的事。模块有两个 main 包，而 `go build` 拿到不止一个 main 包时，把产物**写进当前工作目录**——于是在仓库根跑一次构建，根目录里就多出 `remote-fs` 和 `remote-fs-server` 两个文件。它们没有后缀，`.gitignore` 的 `*.exe`、`*.so` 那几条都盖不住，于是它们出现在 `git status` 里，等着被谁顺手 `git add -A` 进去。

这不是假想。写这份 note 之前，主工作区里就躺着一个这样来的 `remote-fs`。

命令本身也散着。`AGENTS.md` 的「Checks」一节列了一份，`.github/workflows/ci.yml` 又各写一遍。第三份在人的记忆里，而那份通常最不准。

## 决定

`make build` 与 `make test`，产物落在 `bin/`，`bin/` 与 `vendor/` 一同被忽略。

`build` 显式给出 `-o bin/` 与两个 main 包的路径，因此产物的落点不再取决于是在哪个目录下敲的命令。`clean` 删掉 `bin/`——有了产物目录就得有拆掉它的办法，否则第一个想从干净状态重来的人会自己 `rm -rf` 一个路径，而那个路径写错一次就不只是删掉产物。

`test` 就是 `go test ./...`，不多不少。它在没有 `/dev/fuse` 的机器上会让挂载层与端到端层自己跳过并报 `ok`——**这是给人用的判据，不是给门禁用的**。CI 不接受这个答案：它用 `assert-every-test-ran.sh`，任何一次 skip 都让那一轮变红，因为一次什么都没证明的运行不许报出与一次证明了一切的运行相同的绿。两者的分工写在 Makefile 的注释里，就在 `test` 上方。

`vendor/` 也在这次一并忽略。目录存在时 Go 自动按 `-mod=vendor` 构建，不存在时走模块缓存；两种都工作，而仓库不该记录哪一种正在被用。

## 备选方案

**不加 Makefile，继续敲 go 命令。** 少一个文件，也少一层间接。输在上面那两件事都不会自己好转：产物照样散在根目录，命令照样有三份且会漂移。

**用一个 shell 脚本代替 Makefile。** 对这么少的目标够用。输在惯例——Go 项目里 `make build` 是不用问就知道怎么敲的那个，而 `./scripts/build.sh` 要先被发现；`.PHONY` 与目标依赖也得自己重造。

**让 Makefile 包住全部检查：vet、gofmt、race、覆盖率门禁、链接检查。** 一条 `make check` 就能跑完 CI 跑的东西，很诱人。当时它需要把 CI 的理由一起搬进来，包括 `-count=1`、当时采用的跨包覆盖口径与 `--ci` 的阈值出口。现行包内统计和门禁由 [AGENTS.md](../../../../AGENTS.md) 与 `ci.yml` 拥有；把这些规则搬进 Makefile 注释会增加一份随策略漂移的副本。构建与测试是每天敲很多次的两条，其余是推送前敲一次的，把它们捆在一起并不省事。

**让 `ci.yml` 也调用 `make`。** 没有被否决，只是不在这次范围内。CI 那两条命令外面还包着 skip 检测与覆盖率门禁，要让 Makefile 承担它们，Makefile 就得知道什么是「必需的状态检查」——那是 CI 的职责，不是构建工具的。

## 后果

**买到的：** 仓库根目录不再因为一次构建而变脏；构建与测试各只有一个入口，且那个入口在版本控制里。

**付出的：**

- 命令仍有两处：`build` 与 `test` 在 Makefile，`vet`、`gofmt`、`race` 仍在 `AGENTS.md` 的列表里。漂移的可能被压小了，没有被消除。
- `make test` 与 CI 的 `test` 不是同一件事，而它们名字一样。在没有 `/dev/fuse` 的机器上前者报绿而后者会红，知道这件事的人才不会被它骗过一次。
- `bin/` 被忽略之后，一个真的想提交某个产物的人得显式 `git add -f`——这是刻意的。
