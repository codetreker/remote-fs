# Agent Note: 读可以输给写者，契约认下它

Status: implemented

## 问题

`storage.Storage` 的原子性义务写的是：并发的读者看到旧内容的全部、或新内容的全部。对象存储那份实现给不出这两个答案之外的第三个吗？给得出——它的读是两步，先问树这个名字指向哪个对象，再去取那个对象；写入落在这两步之间，把树指向新对象并把旧对象交给后台清扫，清扫若在取回之前删掉它，读者手里的键就没了。它重来，重来的次数有上限，上限用尽报 `EAGAIN`。

这条代价在[把命名空间放进对象存储](./2026-08-21-namespace-in-an-object-store.md)里记下来了，也有一份提案[在途的读者与清扫器](../../proposed/architecture/2026-08-21-readers-in-flight-and-the-sweeper.md)要消掉它。中间空着三件事：

**契约没说过它。** `EAGAIN` 在 `docs/spec/`、`docs/design/` 和 `storage.Storage` 的注释里一个字都没有。它是一个实现被允许给出、并且真的会给出的答案，而调用方没有任何一份文档告诉它要准备这个答案。

**契约用例禁止它。** 「a reader never sees a write in progress」把任何一次读失败都判为 finding。而那条用例是 200 次背靠背的写入加两个不停顿的读者——**它构造的正是实现文档里说会产生 `EAGAIN` 的那个条件**。用例写于只有 `localdir` 的时候，那里的读是一次 `os.ReadFile`，没有这个窗口；对象存储接过这套用例之后，矛盾就一直潜伏着。

**没有任何东西验证过它到了用户态是什么样。** 端到端那一层跑的是 `localdir` 后端，所以「挂载点上一次读拿到 `EAGAIN` 会怎样」这件事，整个仓库没有一个用例走到过。

它在 CI 上兑现了一次：覆盖率闸门把整个 module 跑一遍，一个读者连输五次，用例判红。这不是抖动——用例把竞争压到最大，实现给重试设了一个有限的上限，两者相遇之后剩下的只是概率什么时候兑现。跑得够多它一定会再来。

## 决定

**契约认下这件事，而不是把它当缺陷修掉。**

三处，一起改：

- **R-CC-5** 进了 `docs/spec/requirements.md` 的并发一节：读一个正在被反复覆盖的文件可以失败；这类失败必须说的是「这一次没读到，再试可能就读到了」，且必须与「文件不存在」和「命名空间弄丢了它声称持有的字节」分得开；绝不允许因此答出半新半旧的内容。「读永远成功」不是需求。
- **`storage.Storage` 的 `Read` 注释**点名 `EAGAIN`，说清它是关于这一次尝试的报告而不是关于文件的，以及它与 `ENOENT`、`EIO` 各自说的是什么。`docs/design/architecture.md` 那张义务表里，原子性那一行加上第三种许可的结果。
- **契约用例容忍 `EAGAIN` 并计数**。撕裂检测原样保留；「两个值都要被观察到」那道自检也保留，它同时挡住了新的退化——每次读都输的那种运行，`total` 是空的，用例判自己失败。

## 测出来的：四个候选 errno 到用户态没有区别

用 `mountFaulty` 挂一个真实的 FUSE 挂载点，对 `Read` 分别注入四个 errno，看普通程序拿到什么：

| 注入 | `cat` / `head` / `cp` | 耗时 |
|---|---|---|
| `EAGAIN` | exit 1，`Resource temporarily unavailable` | 1–2 ms |
| `EBUSY` | exit 1，`Device or resource busy` | 1–2 ms |
| `EIO` | exit 1，`Input/output error` | 1–2 ms |
| `ESTALE` | exit 1，`Stale file handle` | 1–2 ms |

四个都干净地失败，消息可读，没有一个挂起或自旋。担心「`EAGAIN` 被当成 readiness 信号，把一次失败的读变成一次挂起」是不成立的。

原因是失败落在 `open(2)` 而不是 `read(2)`：`packages/fuse/node.go` 在 `Open` 时就把整个文件读进缓冲区，之后每次 `read(2)` 都从缓冲区里出。而 `EAGAIN`（Linux 上 `EWOULDBLOCK` 就是它）与 `EBUSY` 都在 `open(2)` 的文档错误列表里。

## 为什么是 EAGAIN

`azblob` 的映射表已经给了 `EAGAIN` 一个精确定义：「服务没有开始做，什么都没发生，同一个请求过一会儿可能就成了」。读者输掉竞争逐字对上这句话。

`EBUSY` 在这个仓库里已经有两个主人——根上不提供的操作，以及 blob 上的租约（「对象在那里，租约没了它就会接受这个操作」）。给它第三个含义，会让 `Read` 返回的 `EBUSY` 分不清是租约挡着还是输给了写者，而租约那条将来真用上就会出现在同一条路径上。而且「忙」暗示有一个持有者，读者输掉竞争时没有任何人持有任何东西，只是内容一直在变。

## 备选方案

**实现宽限期，让这场竞争不再发生。** [在途的读者与清扫器](../../proposed/architecture/2026-08-21-readers-in-flight-and-the-sweeper.md)已经把它设计好了，验收标准就是「一次 `EAGAIN` 都不出现」，而且它消掉的不止这一条——还有每次输掉的竞争白花的那次取回。它没有输，它仍然值得做；它只是不该由一次 CI 变红来驱动。价钱是：判定一个垃圾对象够不够老，需要知道它**何时变成垃圾**，而 `objects` 只有创建时刻这一列，语义不对。迁移机制已经走过 v1→v2→v3；这项能力仍需新增 `garbage_since` 一类的列与 v4 migration，并按[元数据复制](./2026-08-27-metadata-replication.md)的规则同时为 v3 建历史见证。

**换成 `EBUSY`。** 见上一节：把一个准确的词换成一个不准确、且已经有两个主人的词。用户态那边毫无收益，四个 errno 的表现一模一样。

**换成 `EIO`。** 每个工具都当硬错误处理，这是它的好处，也是它唯一的好处。输在 `EIO` 在这个系统里已经有一个非常具体的含义——命名空间弄丢了它声称持有的字节——而那是一个持久的缺陷，与「你输给了写者，再试一次大概就好」完全是两回事。把两者合并，等于让上层没有办法区分一个该报警的故障和一次该重试的竞争。

**调高重试次数。** 把一个概率往后推，不改变任何结构，而且推多少全凭猜。这个仓库对写入路径的整个设计就是为了不做这类猜测。

**让用例里的写者停顿一下。** 用例就不再红了，代价是它不再压满竞争——而它存在的全部理由就是压满竞争。这是把温度计砸了。

## 后果

买到的：

- **一个实现真的会给出的答案，第一次出现在契约里。** 此前 `EAGAIN` 只活在两份 note 和一行代码里，调用方无从得知要准备它。
- **契约用例不再断言一件契约没要求的事。** 它此前顺带要求「读永远成功」，那是 `localdir` 的性质，不是契约的。
- **那条用例仍然不可能空转通过。** 三条防护各自被打破验证过：返回撕裂的内容、每次读都 `EAGAIN`、读失败但不是 `EAGAIN`——三种都让它变红，第二种的消息里带着输掉的次数。

付出的：

- **一个存在的文件，读它可以失败。** 这是交付出去的行为，不再是一条内部代价。宽限期落地之前它一直成立。
- **`EAGAIN` 这条路径在挂载那一层仍然没有用例。** 端到端跑的是 `localdir`，产生不了它；上面那张表是用故障注入量出来的，不是从一个真实的对象存储命名空间上跑出来的。
- **R-CC-5 是一条允许失败的需求。** 它容易被读成「读不可靠也没关系」。它说的不是那个：它要求失败必须可分辨、可重试，并且绝不以撕裂的内容代替。
